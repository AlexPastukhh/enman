# Chapter 3. Implementation

Status: draft

## 3.1. Технологический стек

Web-приложение проектируется и реализуется на основе клиент-серверной архитектуры.

Backend:

- ASP.NET Core;
- C#;
- Entity Framework Core;
- SQL Server;
- MediatR;
- FluentValidation;
- Swagger/OpenAPI для проверки API во время разработки.

Frontend:

- React;
- TypeScript;
- Vite;
- React Router;
- React Query;
- React Hook Form;
- Zod.

Тестирование:

- интеграционные тесты backend-среза;
- Playwright для возможной проверки пользовательских сценариев web-интерфейса;
- Vitest для frontend-тестов.

## 3.2. Архитектура решения

Система разделена на несколько логических частей:

- доменный слой, содержащий основные сущности и правила предметной области;
- backend-приложение ASP.NET Core, предоставляющее API;
- слой приложения с обработчиками команд;
- слой хранения данных на базе EF Core;
- frontend-приложение React/TypeScript.

Такое разделение позволяет развивать бизнес-логику независимо от пользовательского интерфейса и инфраструктурных деталей.

## 3.3. Реализованный L1-срез

[IMPLEMENTED] В реализованном L1-срезе представлены следующие основные сущности:

- `ClientAccount` — клиентский аккаунт;
- `IndividualApplicantParty` — заявитель-физическое лицо;
- `ConnectionRequest` — заявка на подключение.

Клиентский аккаунт содержит email, хеш пароля, роль, признак активности и дату создания. Заявитель-физическое лицо связан с аккаунтом клиента и содержит ФИО, email и телефон. Заявка связана с заявителем, содержит тип заявки, статус, описание и адрес объекта.

## 3.4. Backend API

[IMPLEMENTED] В L1 API реализованы endpoints для:

- регистрации клиентского аккаунта;
- создания заявителя-физического лица;
- создания заявки.

[IMPLEMENTED] В основном контуре аутентификации также присутствуют операции регистрации, входа и получения данных текущего пользователя. В финальном тексте ВКР нужно аккуратно описать, какой именно контур используется в демонстрации.

При создании заявки система проверяет, что выбранный заявитель существует и принадлежит текущему клиентскому аккаунту. Это предотвращает создание заявки от имени чужого заявителя.

## 3.5. Хранение данных

[IMPLEMENTED] Для L1-среза настроены таблицы:

- `L1Accounts`;
- `L1ApplicantParties`;
- `L1ClientRequests`.

Для аккаунтов, заявителей и заявок используются связи по идентификаторам. Адрес объекта хранится как составное значение с отдельными полями для почтового индекса, региона, города, улицы, дома, корпуса и квартиры.

## 3.6. Frontend

[DESIGNED/IMPLEMENTED PARTIALLY] Frontend-часть строится на React и TypeScript. Целевая структура пользовательского интерфейса должна включать:

- страницу регистрации;
- страницу входа;
- страницу создания заявителя;
- страницу создания заявки;
- список заявок клиента;
- страницу заявки;
- рабочее место сотрудника;
- страницу проверки заявки;
- страницу создания проекта договора или документа;
- страницу просмотра документов клиентом.

Фактический статус каждой страницы необходимо проверить перед финальной сдачей.

## 3.7. Сценарий сотрудника

[DESIGNED] В полной версии сотрудник видит список заявок, выбирает заявку, берет ее в обработку, проверяет данные вручную и принимает решение. При одобрении заявки сотрудник создает проект договора или документа. При отклонении указывает причину отклонения.

Если этот функционал еще не реализован в коде, в ВКР его следует описывать как проектную часть или как направление ближайшей доработки, а не как завершенную реализацию.

## 3.8. Email-уведомления

[PLANNED] После одобрения заявки или создания проекта договора клиент должен получать email-уведомление. В реализации для этого может быть выделен отдельный сервис уведомлений, вызываемый после успешного изменения состояния заявки или создания документа.

Если отправка email пока отсутствует в коде, ее нужно описывать как запланированное расширение или как проектное решение, а не как реализованную функцию.

## 3.9. Тестирование

[IMPLEMENTED] Интеграционные тесты L1-среза проверяют:

- регистрацию клиента;
- создание заявителя;
- создание заявки;
- передачу идентификаторов между сущностями;
- обработку ошибки дублирующего email;
- обработку отсутствующего аккаунта;
- обработку отсутствующего заявителя;
- обработку пустого описания заявки.

Эти тесты подтверждают работоспособность базового клиентского сценария и корректность взаимодействия API с базой данных.
