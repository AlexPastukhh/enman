# General Info

## 1. Назначение проекта

Проект представляет собой web-приложение для выпускной квалификационной работы на тему:

**«Разработка web-приложения для автоматизации ведения документооборота и обработки клиентских заявок в сетевой компании ООО „ЗСК“»**

Основная цель проекта — разработать систему, которая позволяет клиентам подавать заявки через сайт, а сотрудникам организации — просматривать, проверять, одобрять или отклонять эти заявки, формировать обратную связь и вести связанный документооборот.

Приложение не должно реализовывать полноценный юридически значимый электронный документооборот. В рамках диплома система ограничивается приемом и обработкой заявок, формированием проекта договора/документа и отправкой обратной связи клиенту.

Frontend React/TypeScript
        ↓ HTTP/REST

## 4. Главная бизнес-логика

Основной бизнес-процесс:

```text
Клиент регистрируется
→ входит в систему
→ создает заявителя
→ подает заявку
→ сотрудник видит заявку
→ сотрудник берет заявку в обработку
→ сотрудник вручную проверяет данные
→ сотрудник одобряет или отклоняет заявку
→ система формирует обратную связь
→ система отправляет email
→ при одобрении создается проект договора/документа
```

В первом слое сотрудник не выполняет автоматических проверок. Он просто открывает заявку, вручную проверяет данные и принимает решение.

* описание use cases;

## L1 — обязательный минимум

Цель L1 — получить минимально полноценное приложение, которое уже можно защищать как дипломный проект.

### Пользовательский функционал L1

Клиент:

* регистрация;
* авторизация;
* просмотр базового профиля;
* создание заявителя типа ФЛ;
* подача заявки;
* просмотр своих заявок;
* просмотр статуса и результата обработки.

Сотрудник:

* авторизация;
* просмотр всех заявок;
* просмотр необработанных заявок;
* просмотр обработанных заявок;
* открытие карточки заявки;
* взятие заявки в обработку;
* ручная проверка заявки;
* одобрение заявки;
* отклонение заявки;
* ввод комментария / причины отказа.

Система:

* сохранение заявки в БД;
* смена статусов;
* создание результата рассмотрения;
* создание простого проекта договора при одобрении;
* отправка email-уведомления клиенту.

### Типы заявок L1

* `Connection` — технологическое присоединение;
* `MeteringDevice` — установка, замена или эксплуатация приборов учета.

### Статусы заявки L1

* `Submitted` — заявка подана;
* `InReview` — заявка взята в обработку;
* `Approved` — заявка одобрена;
* `Rejected` — заявка отклонена;
* `ContractDraftSent` — проект договора/документа направлен клиенту.

## L2 — хороший диплом

Цель L2 — сделать систему похожей на полноценную систему электронного документооборота.

Что добавляется:

* расширенный профиль заявителя;
* поддержка заявителей ФЛ / ИП / ЮЛ;
* сохранение snapshot данных заявителя в заявке;
* прикрепление документов к заявке;
* типы документов;
* история изменений заявки;
* комментарии;
* статус `NeedClarification`;
* запрос уточняющих данных;
* расширенный поиск и фильтрация заявок;
* mock-сервис межведомственной проверки данных;
* шаблоны обратной связи;
* шаблоны договоров;
* версионирование проектов договоров;
* генерация PDF договора;
* подтверждение email;
* более серьезная обработка ошибок через ProblemDetails.

### Mock-проверки L2

Реальные интеграции с государственными сервисами не выполняются. Вместо них используется mock-сервис, который имитирует:

* проверку паспортных данных;
* проверку ИНН;
* проверку ОГРН;
* проверку ОГРНИП;
* проверку адреса;
* проверку обязательных документов.

Возможные результаты:

* `Verified`;
* `Failed`;
* `ManualReviewRequired`;
* `ServiceUnavailable`.

## L3 — production-like расширение

Цель L3 — приблизить проект к промышленной эксплуатации.

Что может входить:

* анонимная заявка;
* Windows-аутентификация сотрудников через Negotiate;
* rate limiting;
* временная блокировка входа по email + IP;
* учет попыток входа;
* email о подозрительной активности;
* outbox для надежной отправки уведомлений;
* повторные попытки отправки email;
* аудит действий пользователей;
* security events;
* кэширование справочников;
* health checks;
* production-настройки;
* Docker / docker-compose;
* SMS-уведомления;
* личные сообщения в системе.

### Что не входит даже в L3

Не реализовывать в рамках диплома:

* полноценную электронную подпись;
* юридически значимый ЭДО;
* реальную СМЭВ-интеграцию;
* реальную проверку паспортов / ФНС;
* платежный контур;
* полноценное подписание договора онлайн.

Эти элементы можно описывать как перспективы развития.

## 7. Ключевые доменные классы

## Identity / Accounts

### `Account`

Базовая учетная запись пользователя.

Содержит:

* `Id`;
* `Email`;
* `PasswordHash`;
* `Role`;
* `IsActive`;

Наследники:

* `ClientAccount`;
* `EmployeeAccount`.

### `ClientAccount`

Аккаунт клиента.

### `EmployeeAccount`

Аккаунт сотрудника.

Содержит профиль сотрудника и в L3 может быть связан с Windows-учетной записью.

## Applicant Parties

### `ApplicantParty`

Базовый класс заявителя.

Это важное архитектурное решение: ФЛ, ИП и ЮЛ — это не разные аккаунты, а разные типы заявителя.

Наследники:

* `IndividualApplicantParty`;
* `EntrepreneurApplicantParty`;
* `LegalEntityApplicantParty`;
* `AnonymousApplicantParty` в L3.

### `IndividualApplicantParty`

Физическое лицо. Используется уже в L1.

### `EntrepreneurApplicantParty`

Индивидуальный предприниматель. Добавляется в L2.

### `LegalEntityApplicantParty`

Юридическое лицо. Добавляется в L2.

### `AnonymousApplicantParty`

Анонимный заявитель. Добавляется в L3.

### `ApplicantSnapshot`

Снимок данных заявителя на момент подачи заявки. Добавляется в L2.

Нужен для того, чтобы изменение профиля пользователя не изменяло исторические заявки.

## 12. Границы договора

В рамках диплома договорный контур ограничен проектом договора.

L1:

* создать простой проект договора;
* связать его с заявкой;
* отправить уведомление по email.

L2:

* шаблоны договоров;
* версии договора;
* PDF;
* подтверждение ознакомления;
* запрос корректировки.

Не реализуется:

* электронная подпись;
* юридически значимое подписание;
* платежи;
* реальный ЭДО.
