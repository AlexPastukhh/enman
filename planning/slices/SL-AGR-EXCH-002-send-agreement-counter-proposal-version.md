# SL-AGR-EXCH-002 — Send Agreement Counter-Proposal Version

Status: planned slice boundary / full implementation draft pending  
Package: `[L2] Agreement Proposal Exchange`  
Slice type: backend/API command slice with two actor branches + future client command sidecars  
Primary purpose: current actor sends the next proposal version inside an existing exchange

## 1. Scope Boundary

This slice implements both directions of counter-proposal exchange.

```text
Active exchange
  -> current actor sends agreement document + optional comment
  -> active proposal is superseded
  -> next proposal version is created
  -> turn switches to the other side
```

This slice does not start a new exchange. Initial employee proposal/version 1 belongs to `SL-AGR-EXCH-001`.

| ID | Status | Question | Decision / current direction | Impact |

## 3. Behavior Coverage

| Behavior item | How slice covers it | Status |
|---|---|---|
| Client sends counter-proposal when awaiting client | service calls client branch; domain validates client participant/turn | planned |
| Employee sends counter-proposal when awaiting employee | service calls employee branch; domain validates active employee/turn | planned |
| Next version is generated by exchange | domain computes max existing version + 1 | planned/current domain direction |
| Active proposal is superseded | domain marks previous active proposal as superseded | planned |
| Turn switches to the other side | domain changes exchange status | planned |
| Wrong client cannot act on exchange | domain checks `ClientAccountId` | planned |
| Employee access is not tied to responsible employee | no `ResponsibleEmployeeId` guard | planned |

## 4. Actor Branches

Client branch:

```text
AwaitingClientConfirmation
active proposal author = Employee
current client.Id == exchange.ClientAccountId
  -> ClientSendOwnVersion(...)
  -> AwaitingEmployeeResponse
```

Employee branch:

```text
AwaitingEmployeeResponse
active proposal author = Client
employee.EnsureCanSendAgreementProposal()
  -> EmployeeSendNewVersion(...)
  -> AwaitingClientConfirmation
```

## 5. Endpoint Direction

Actor boundaries may use separate endpoints:

```http
POST /api/l1/requests/{requestId}/agreement-exchange/proposals
POST /api/employee/requests/{requestId}/agreement-exchange/proposals
```

A shared application service is still preferred:

```text
Controller resolves actor from session.
Application service loads aggregate and branches by actor.
Domain method validates business transition and participant/lifecycle invariants.
```

## 6. Domain / Application Responsibility

```text
Controller:
  authenticated role/session, DTO shape boundary, command construction.

Application service:
  load actor;
  load exchange/request;
  create AgreementDocumentRef;
  create optional ProposalComment;
  branch by actor;
  save.

AgreementProposalExchange:
  client participant ownership;
  current turn;
  active proposal author side;
  status/lifecycle guard;
  version creation;
  superseding active proposal.
```
