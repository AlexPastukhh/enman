# Architecture Decision Notes

Status: active accepted-decision registry  
Scope: current accepted architecture decisions that guide planning/implementation and may support diploma text

## 1. Client / Server Contract Decisions

| ID | Decision | Current accepted direction | Rationale / trade-off | Affected artifacts | ADR promotion |
|---|---|---|---|---|---|
| ADN-080 | Two-channel client/server contract | OpenAPI owns structural contract; generated constants JSON owns semantic constants. | Avoids DTO/route guessing while keeping stable error codes explicit. | planning/api, CC-API-001, CC-CONST-001 | Likely ADR |
| ADN-081 | OpenAPI is source for API/DTO shape | Endpoint paths, methods, DTOs, statuses and response schemas are generated through OpenAPI. | Prevents client DTO drift and manual route/DTO guessing. | Shared/openapi.json, openapi-types.ts | Likely ADR |
| ADN-082 | Generated constants JSON is source for semantic constants | Error codes, ProblemDetails extension names and ServerError field names live in generated constants artifacts. | OpenAPI does not model domain/client semantic code lists well. | Shared/constants.json, Shared/errorcodes.json | Likely ADR |
| ADN-083 | Generated artifacts are explicit-command artifacts | `Shared/openapi.json`, OpenAPI types and constants are generated by explicit commands and checked in; normal server startup does not write them. | Keeps startup side-effect free and makes contract changes visible in diffs. | Tools/scripts, Shared artifacts | Candidate |
| ADN-084 | Route constants are temporary during OpenAPI transition | Existing legacy route constants may remain while client migration is incomplete, but new route contract should move to OpenAPI. | Supports gradual migration without preserving bad duplication forever. | Shared/constants.json, client API layer | Candidate |
| ADN-085 | L1 endpoints are target contract for new slices | New L1 slices should target L1 endpoints; legacy AuthController endpoints remain current support until migration. | Allows incremental migration without blocking auth/client support. | parent slice API sections, OpenAPI inventory | Candidate |
| ADN-086 | OpenAPI quality metadata is required | Client-facing endpoints should have explicit response types, ProblemDetails statuses and stable operation ids where practical. | Generated client types are only useful if metadata is precise. | server controllers, Shared/openapi.json | Candidate |
| ADN-087 | Types-only OpenAPI generation first | Generate TypeScript DTO/types first and keep thin handwritten client API wrappers. | Reduces risk while aligning DTOs and preserving frontend architecture. | client API layer | Candidate |

## 2. Cross-Cutting / Helper Slice Decisions

| ID | Decision | Current accepted direction | Rationale / trade-off | Affected artifacts | ADR promotion |
|---|---|---|---|---|---|
| ADN-061 | Cross-cutting/helper slices are allowed | Technical/support work with behavior, implementation flow and tests can be documented as cross-cutting/helper slice. | Avoids burying implementation-ready support work in generic workflow notes. | slice workflow docs | Candidate |
| ADN-062 | Implementation flow detail filter | Include classes/methods/code snippets only for key decisions/boundaries/non-obvious behavior; keep routine code high-level. | Keeps slice files readable while still useful for diploma/implementation. | slice docs, client docs, cross-cutting slices | Candidate |
| ADN-071 | Cross-cutting/helper slices use same format as business slices | Source requirements -> behavior items -> concern flow -> implementation flow -> tests/checks -> coverage/questions/ADR impact. | Keeps technical concerns traceable and consistent with business slices. | cross-cutting README, slice guide | Candidate |
| ADN-072 | Concern-derived behavior items are first-class behavior items | Security/API/tooling/testing/infrastructure-derived items are valid and must be covered by concern flow. | Prevents technical behavior from being hidden only in implementation notes. | behavior item docs, cross-cutting slices | Candidate |

## 4. CSRF / Antiforgery Decisions

| ID | Decision | Current accepted direction |
|---|---|
| ADN-073 | CSRF/antiforgery is a cross-cutting slice | `CC-CSRF-001` is the primary implementation-ready slice for antiforgery token/session behavior. |
| ADN-074 | CSRF behavior items are security-derived | Create behavior items even though CSRF is not a business scenario. |
| ADN-077 | Antiforgery failure normalized by always-run result filter | Convert framework antiforgery failure into project ProblemDetails. |
| ADN-078 | Antiforgery filter checks failure marker/result, not generic HTTP 400 | Avoid mislabeling ordinary bad requests as CSRF failures. |
| ADN-079 | Client does not blindly replay unsafe commands after token refresh | Explicit user retry for unsafe commands. |
