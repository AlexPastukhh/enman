# Clean Domain Model

Status: draft

## Общая модель

Доменная модель системы описывает основные сущности процесса обработки клиентских заявок и документооборота в сетевой компании ООО «ЗСК».

## Реализованные сущности L1

### ClientAccount

Статус: [IMPLEMENTED]

Назначение: учетная запись клиента.

Основные данные:

- email;
- хеш пароля;
- роль;
- признак активности;
- дата создания.

### IndividualApplicantParty

Статус: [IMPLEMENTED]

Назначение: заявитель-физическое лицо, связанный с клиентским аккаунтом.

Основные данные:

- идентификатор клиентского аккаунта;
- ФИО;
- email;
- телефон.

### ConnectionRequest

Статус: [IMPLEMENTED]

Назначение: заявка клиента на подключение или связанную услугу.

Основные данные:

- заявитель;
- тип заявки;
- статус;
- описание;
- адрес объекта;
- дата создания.

## Проектируемые сущности полной версии

### Employee

Статус: [DESIGNED]

Назначение: сотрудник сетевой компании, который рассматривает заявки.

### RequestReview

Статус: [DESIGNED]

Назначение: результат ручной проверки заявки сотрудником.

Должен хранить решение, комментарий, дату решения и связь с сотрудником.

### DocumentProject

Статус: [DESIGNED/PLANNED]

Назначение: проект договора или документа, созданный после одобрения заявки.

Должен быть связан с заявкой и клиентом.

### EmailNotification

Статус: [PLANNED]

Назначение: уведомление клиента о результате обработки заявки или появлении документа.

## Жизненный цикл заявки

Проектный жизненный цикл:

```text
Created / Submitted
-> InProcessing / InReview
-> Approved / Rejected
```

В текущем коде L1 начальный статус заявки может быть представлен как `Submitted`. В проектных сценариях рассмотрения используется смысловой статус ожидания проверки. В финальном тексте нужно выбрать единое название или явно пояснить соответствие.

## Жизненный цикл документа

Проектный жизненный цикл документа:

```text
Draft
-> SentToClient
-> Viewed / Accepted / RequiresChanges
```

На текущем этапе этот жизненный цикл относится к проектируемой или планируемой части системы.

## Инварианты

- Клиентская заявка должна иметь заявителя.
- Заявитель должен принадлежать клиентскому аккаунту.
- Одобрение или отклонение должно фиксироваться как результат проверки.
- Проект договора не должен создаваться до одобрения заявки.
- Email-уведомление не должно отправляться до успешного сохранения соответствующего события.
