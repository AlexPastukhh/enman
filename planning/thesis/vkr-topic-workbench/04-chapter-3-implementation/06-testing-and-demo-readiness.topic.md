# Тема: Тестирование и готовность к демонстрации

**Статус:** быстрый topic-драфт v1 / глава 3 / закрывает доказательную часть для преддипломной / нужен repo-check по unit tests, API tests, frontend checks, manual demo, запуску проекта и стабильному demo-flow.

1. Зачем тема нужна

Эта тема показывает, как проверялась реализация и что можно продемонстрировать на преддипломной.

Главная мысль:

Для допуска важно показать не только наличие кода, но и проверяемость реализованных сценариев. Тестирование должно подтвердить основную цепочку приложения: создание заявки, рассмотрение, принятие решения, договорный обмен, загрузку и получение файла.

2. Что нужно доказать

Минимально для допуска:

1. Приложение запускается.
2. Backend и frontend связаны через API.
3. Основные сценарии проходят вручную.
4. Есть unit-тесты domain/application logic, если они есть.
5. Есть API/integration tests, если они есть.
6. Есть проверка upload/download файлов.
7. Есть demo-flow, который можно показать комиссии.
8. Есть screenshots / evidence.
3. Виды проверок
1. Unit tests
   Проверяют domain/application rules без UI и БД.

2. API / integration tests
   Проверяют endpoints, DTO, validation, access, persistence.

3. Frontend manual checks
   Проверяют страницы, формы, кнопки, ошибки.

4. File scenario checks
   Проверяют upload, metadata, download, safe errors.

5. End-to-end manual demo
   Проверяет всю пользовательскую цепочку.

Рабочий текст:

Проверка реализации выполняется на нескольких уровнях. Unit-тесты позволяют быстро проверить бизнес-правила, API-проверки подтверждают корректность взаимодействия frontend/backend, а ручной demo-flow показывает работоспособность приложения как целого.

4. Unit tests

Особенно важно, если есть выделенный domain layer.

Что тестировать:

- нельзя одобрить заявку в неправильном состоянии;
- нельзя отклонить заявку без review, если это правило есть;
- reason обязателен для reject, если это правило есть;
- после approve возможен договорный обмен;
- новый файл создаёт новую proposal version;
- повторное действие возвращает ошибку состояния.

Тезис:

Unit-тесты domain layer ценны тем, что проверяют бизнес-правила быстро и независимо от UI, БД и файловой системы.

5. API / integration tests

Что проверять:

- create applicant;
- create request;
- list requests;
- request details;
- start review;
- run data check;
- approve request;
- reject request;
- start exchange;
- send proposal version;
- upload file;
- download file;
- forbidden / not found;
- validation errors.

Тезис:

API-проверки подтверждают, что frontend может выполнять сценарии через backend-контракт, а backend корректно возвращает success, validation errors и business-state errors.

6. Manual scenario testing

Для преддипломной manual testing особенно полезен, потому что его можно быстро подтвердить скриншотами.

Основная цепочка:

1. Войти как клиент.
2. Создать заявителя.
3. Создать заявку.
4. Увидеть заявку в клиентском списке.
5. Войти как сотрудник.
6. Открыть список заявок.
7. Открыть карточку заявки.
8. Начать рассмотрение.
9. Выполнить проверку данных.
10. Одобрить заявку.
11. Начать договорный обмен.
12. Отправить версию предложения с файлом.
13. Войти как клиент.
14. Открыть договорный обмен.
15. Скачать файл.

Сжатый demo-flow:

создать заявку
→ start review
→ approve
→ start exchange
→ upload proposal file
→ download file
7. Проверка ошибок

Минимально проверить:

- пустая форма заявки → validation errors;
- reject без причины → validation error, если reason обязателен;
- повторный approve → business-state error;
- устаревшее действие → ActionNoLongerAvailable / аналог;
- чужая заявка → forbidden/not found;
- чужой файл → forbidden/not found;
- missing file → safe file error.

Тезис:

Проверка ошибок важна, потому что приложение должно корректно работать не только в успешном сценарии, но и при неверных данных, устаревшем состоянии или отсутствии доступа.

8. Проверка файлов

Проверить:

1. Upload создаёт physical file.
2. Upload создаёт metadata.
3. Metadata связана с proposal version.
4. UI показывает originalFileName.
5. Download идёт через backend.
6. Frontend не получает storage path/storage key.
7. Чужой пользователь не может скачать файл.
8. Missing file возвращает safe error.

Тезис:

Файловые сценарии подтверждают storage-boundary: physical file хранится отдельно, metadata связывает файл с договорным процессом, а download выполняется через backend и проверку доступа.

14. Черновой текст

Для проверки реализации использовались несколько уровней тестирования. Бизнес-правила, вынесенные в domain layer, могут проверяться быстрыми unit-тестами без запуска frontend, БД и файловой системы. Это позволяет убедиться, что ключевые переходы заявки и договорного обмена выполняются только в допустимых состояниях.

Кроме unit-тестов, важную роль играет проверка API-сценариев. Через backend API выполняются создание заявки, начало рассмотрения, одобрение, отклонение, начало договорного обмена, загрузка и получение файла. Такие проверки подтверждают, что frontend и backend взаимодействуют через согласованный контракт.

Для преддипломной также подготовлен демонстрационный сценарий, проходящий по основной цепочке приложения: клиент создаёт заявку, сотрудник рассматривает и одобряет её, затем начинается договорный обмен и отправляется версия договорного предложения с файлом. Этот сценарий показывает, что реализованы не отдельные экраны, а связанный процесс.
