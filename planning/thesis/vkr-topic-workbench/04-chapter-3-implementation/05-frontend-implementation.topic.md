# Тема: Реализация пользовательского интерфейса

**Статус:** быстрый topic-драфт v1 / глава 3 / нужен repo-check по routes, страницам, компонентам, forms, API client, guards, UI states, upload/download UI.

1. Зачем тема нужна

Эта тема показывает, как во frontend реализованы пользовательские сценарии клиента и сотрудника.

Главная мысль:

Frontend реализует интерфейс для двух ролей: клиента и сотрудника. Клиент создаёт заявителей и заявки, отслеживает состояние заявки и работает с договорным обменом. Сотрудник просматривает заявки, выполняет рассмотрение, принимает решение и сопровождает договорный этап. Все действия выполняются через backend API, а frontend не управляет бизнес-состоянием напрямую.

2. Что нужно доказать

Для допуска быстро показать:

1. Есть frontend-приложение.
2. Есть маршруты / страницы клиента.
3. Есть маршруты / страницы сотрудника.
4. Есть формы создания заявителя и заявки.
5. Есть список и карточка заявки.
6. Есть UI для review / approve / reject.
7. Есть UI договорного обмена.
8. Есть upload/download файлов.
9. Есть обработка loading / validation / business errors.
10. UI вызывает backend API, а не работает напрямую с БД/файлами.

Frontend может быть описан через блоки:

routes / pages;
layouts;
forms;
lists;
details pages;

state management;

UI components;

Рабочий текст:

Frontend-часть приложения организована вокруг страниц и компонентов, соответствующих пользовательским сценариям. Страницы получают данные через read API, отправляют пользовательские действия через command API и отображают результат пользователю.

4. Клиентская зона

Клиентская зона реализует:

- личный кабинет клиента;
- список заявителей;
- создание заявителя;
- создание заявки;
- список моих заявок;
- карточку заявки;
- просмотр статуса;
- просмотр результата рассмотрения;
- просмотр причины отказа;
- переход к договорному обмену после одобрения;
- просмотр версий предложения;
- скачивание файла.

Рабочий текст:

Клиентский интерфейс реализует сценарий подачи заявки и отслеживания её состояния. Клиент видит только собственные данные и не получает доступ к действиям сотрудника.

5. Зона сотрудника

Сотрудническая зона реализует:

- рабочий список заявок;
- карточку заявки;
- блок рассмотрения;
- запуск проверки данных;
- одобрение заявки;
- отклонение заявки;
- ввод причины отказа;
- начало договорного обмена;
- отправку версии договорного предложения;
- загрузку файла;
- просмотр истории версий.

Рабочий текст:

Интерфейс сотрудника является рабочей зоной обработки заявок. Через него сотрудник открывает заявку, запускает review, выполняет проверку данных, принимает решение и переходит к договорному обмену.

6. Карточка заявки

Карточка заявки — основной экран frontend.

Она может показывать:

данные заявки;
данные заявителя;
текущий статус;
review state;
результат проверки;
decision;
rejection reason;
availableActions;
переход к agreement exchange;
file metadata, если договорный этап начат.

Для клиента:

экран отслеживания состояния.

Для сотрудника:

рабочий экран обработки.

Рабочий текст:

Карточка заявки объединяет данные процесса и показывает пользователю доступные действия. Для клиента это экран отслеживания, а для сотрудника — рабочий экран рассмотрения.

7. Формы frontend

Основные формы:

форма создания заявителя;
форма создания заявки;
форма причины отказа;
форма отправки версии предложения;
форма upload файла.

Frontend отвечает за:

сбор данных;
локальную проверку обязательных полей;
показ validation errors;
loading state;
disable кнопки при submit;
отправку command API;
показ результата.

Backend отвечает за:

окончательную validation;
проверку доступа;
business rules;
изменение состояния.

Рабочий текст:

Формы frontend помогают пользователю заполнить данные и отправить команду, но окончательная проверка и изменение состояния выполняются backend-ом.

8. AvailableActions и кнопки

Frontend может показывать кнопки на основе availableActions или похожих полей read DTO.

Примеры:

StartReview;
RunCheck;
Approve;
Reject;
StartExchange;
SendProposalVersion;
UploadFile;
DownloadFile.

Важно:

availableActions помогают UI;
кнопки можно скрывать или disable;
backend всё равно проверяет command повторно;
stale UI должен обрабатываться через business-state error.

Рабочий текст:

Доступные действия используются frontend для отображения кнопок, но не являются механизмом безопасности. Если состояние объекта изменилось, backend отклоняет команду и frontend обновляет экран.

Экран договорного обмена показывает:

Не показывает:

Рабочий текст:

В договорном обмене frontend отображает версии предложения и metadata документов. Physical file получается через download API, а не через прямую ссылку на файловую директорию.

10. UI states

Frontend должен показывать:

loading;
empty state;
success;
validation errors;
business-state errors;
forbidden / not found;
file unavailable;
unexpected error.

Примеры:

загрузка списка заявок;
пустой список;
ошибка формы;
действие уже недоступно;
файл недоступен;
нет доступа к заявке.

Рабочий текст:

Реализация frontend должна учитывать не только успешные сценарии, но и промежуточные и ошибочные состояния. Это особенно важно для command API, потому что read DTO может устареть.

11. Связь frontend с API

Frontend вызывает:

read API для списков и карточек;
command API для действий;
file upload API;
file download API.

Текст:

Frontend не содержит бизнес-правил lifecycle. Он отображает данные, полученные от backend, и отправляет пользовательские действия через API. Решение о допустимости действия остаётся на backend.

15. Черновой текст

Frontend-часть приложения реализует пользовательские сценарии клиента и сотрудника. Клиентская зона предназначена для создания заявителей и заявок, просмотра статуса заявки и работы с договорным обменом после одобрения. Сотрудническая зона предназначена для обработки заявок, выполнения проверки данных, принятия решения и сопровождения договорного этапа.

Основным экраном является карточка заявки. Она отображает текущее состояние процесса, данные заявки, результат рассмотрения и доступные действия. Для сотрудника карточка содержит действия обработки, а для клиента — информацию о ходе рассмотрения и результате.

Frontend взаимодействует с backend через API. Для получения данных используются read-запросы, а для изменения состояния — command-запросы. Frontend не устанавливает статус заявки самостоятельно: он отправляет команду, а backend проверяет доступ и бизнес-правила.

Отдельно реализуется работа с файлами договорного обмена. Интерфейс показывает имя файла и кнопку скачивания, но не раскрывает storage path или storage key. Получение файла выполняется через backend API.
