# Тема: Структура пользовательского интерфейса и навигация

**Статус:** быстрый topic-драфт v1 / первый драфт блока 2.6 / нужен repo-check по frontend routes, страницам клиента, страницам сотрудника, navigation layout, guards, role-based UI, request/exchange screens.

---

## 1. Зачем тема нужна

Эта тема открывает блок **2.6 “Проектирование пользовательского интерфейса”** и объясняет, как UI организован вокруг ролей и сценариев.

Главная мысль:

> Пользовательский интерфейс проектируется не как набор отдельных страниц, а как сценарная навигация для двух основных зон: клиентской и сотруднической. Клиент работает с заявителями, заявками, статусами и договорным обменом. Сотрудник работает со списком заявок, карточкой заявки, рассмотрением, решением и договорным этапом.

## 3. Основные зоны интерфейса

Интерфейс делится на две пользовательские зоны:

```text
1. Клиентская зона.
2. Зона сотрудника.
```

### Клиентская зона

Нужна для:

```text
создания заявителей;
создания заявки;
просмотра своих заявок;
просмотра статуса заявки;
просмотра результата рассмотрения;
просмотра причины отказа;
перехода к договорному обмену после одобрения;
просмотра версий договорного предложения;
загрузки/скачивания файла, если действие доступно.
```

### Зона сотрудника

Нужна для:

```text
просмотра списка заявок;
открытия карточки заявки;
начала рассмотрения;
запуска проверки данных;
одобрения заявки;
отклонения заявки;
начала договорного обмена;
отправки версии договорного предложения;
просмотра истории версий.
```

Рабочая формулировка:

> Структура интерфейса разделяется по ролям пользователя. Клиентская зона ориентирована на подачу и отслеживание заявки, а зона сотрудника — на обработку заявки и сопровождение договорного этапа.

---

## 4. Навигационная логика клиента

Основной клиентский путь:

```text
вход в систему
→ личный кабинет
→ заявители
→ создание заявки
→ список заявок
→ карточка заявки
→ статус / результат
→ договорный обмен, если заявка одобрена
→ версии предложения / файлы
```

Что важно:

```text
клиент видит только свои данные;
клиент не видит сотруднические действия;
клиент не меняет статус заявки напрямую;
клиент запускает только доступные действия;
клиент получает файл через backend, а не по прямой ссылке.
```

Тезис:

> Клиентский интерфейс должен вести пользователя от создания заявки к отслеживанию её состояния и дальнейшему договорному обмену, не раскрывая служебные действия сотрудника.

---

## 5. Навигационная логика сотрудника

Основной путь сотрудника:

```text
вход в систему
→ рабочая зона сотрудника
→ список заявок
→ карточка заявки
→ начало рассмотрения
→ проверка данных
→ решение: одобрить / отклонить
→ договорный обмен после одобрения
→ отправка версии предложения
→ история версий
```

Что важно:

```text
сотрудник видит действия обработки;
сотрудник не должен работать через клиентские формы;
решение принимается отдельной командой;
mock-проверка не принимает решение автоматически;
договорный обмен начинается только после одобрения.
```

Тезис:

> Сотруднический интерфейс строится вокруг обработки заявки: просмотр, рассмотрение, проверка, решение и переход к договорному обмену.

## 7. Карточка заявки как центральный экран

Карточка заявки — центральный экран UI.

Она может показывать:

```text
данные заявки;
данные заявителя;
текущий статус;
состояние рассмотрения;
результат проверки;
решение;
причину отказа;
доступные действия;
ссылку на договорный обмен после одобрения.
```

Для клиента карточка заявки отвечает на вопрос:

```text
что происходит с моей заявкой?
```

Для сотрудника:

```text
что нужно сделать с этой заявкой?
```

Тезис:

> Карточка заявки должна быть центральной точкой навигации, потому что через неё пользователь видит текущее состояние процесса и доступные дальнейшие действия.

## 8. Available actions в UI

Frontend может показывать кнопки на основе `availableActions` или похожих полей read DTO.

Примеры кнопок:

```text
Начать рассмотрение;
Проверить данные;
Одобрить;
Отклонить;
Начать договорный обмен;
Отправить версию предложения;
Скачать файл;
Загрузить файл.
```

Важно:

```text
кнопка может быть скрыта или disabled;
frontend показывает доступность действия;
backend всё равно проверяет command повторно;
stale DTO может привести к business-state error.
```

Тезис:

> Доступные действия помогают сделать интерфейс понятным, но не являются источником бизнес-правил. UI показывает кнопку, а backend подтверждает возможность действия при выполнении команды.

## 9. Role-based UI

Интерфейс должен учитывать роль пользователя.

Клиент не должен видеть:

```text
список всех заявок;
кнопку начать рассмотрение;
кнопку одобрить;
кнопку отклонить как сотрудник;
служебные данные обработки.
```

Сотрудник не должен действовать как клиент:

```text
создавать заявку от имени клиента без отдельного сценария;
редактировать клиентские данные напрямую;
принимать решение через клиентский экран.
```

Тезис:

> Role-based UI помогает не перегружать пользователя лишними действиями, но не заменяет backend-проверку роли и доступа.

---

## 10. UI states

Для каждого действия frontend должен показывать состояния:

```text
loading;
success;
validation error;
business-state error;
forbidden/not found;
file unavailable;
empty state;
disabled action.
```

Примеры:

```text
загрузка списка заявок;
пустой список заявок;
отправка формы заявки;
ошибка заполнения формы;
кнопка approve disabled;
файл недоступен;
действие уже недоступно, обновите страницу.
```

Тезис:

> UI должен отображать не только успешные состояния, но и ошибки, пустые списки, загрузку и недоступные действия. Это делает сценарии понятными для пользователя.

## 11. Навигация после command

После выполнения команды frontend может:

```text
обновить текущую карточку;
повторно запросить read DTO;
перейти к списку;
перейти к договорному обмену;
показать success message;
показать business-state error и обновить данные.
```

Примеры:

```text
после создания заявки → открыть карточку заявки;
после одобрения → обновить карточку и показать действие “начать договорный обмен”;
после начала exchange → перейти к экрану договорного обмена;
после upload файла → обновить историю версий.
```

Тезис:

> После command API интерфейс должен синхронизироваться с backend-состоянием: либо через command result, либо через повторный read-запрос.

---

## 12. Работа с файлами в UI

UI не должен показывать storage path или storage key.

Показывать можно:

```text
originalFileName;
дата загрузки;
отправитель;
кнопка скачать;
статус загрузки;
ошибка файла.
```

Не показывать:

```text
storage path;
storage key;
server directory;
public uploads URL;
internal file name.
```

Тезис:

> В интерфейсе файл отображается как документ версии предложения, а не как путь в файловой системе.

## 14. Черновой текст

Пользовательский интерфейс проектируется вокруг двух основных ролей: клиента и сотрудника. Клиентская зона предназначена для подачи заявки и отслеживания её состояния, а зона сотрудника — для обработки заявок, принятия решений и сопровождения договорного обмена.

Центральным экраном интерфейса является карточка заявки. Для клиента она показывает состояние его обращения, результат рассмотрения и переход к договорному этапу. Для сотрудника эта же карточка становится рабочим экраном обработки: через неё запускается рассмотрение, проверка данных, одобрение или отклонение.

Навигация интерфейса должна соответствовать жизненному циклу процесса. Клиент проходит путь от заявителя и заявки к статусу и договорному обмену. Сотрудник проходит путь от списка заявок к карточке заявки, рассмотрению, решению и отправке версии договорного предложения.

Доступные действия могут отображаться на основе данных read API, например через `availableActions`. Однако эти действия являются только подсказкой для интерфейса: окончательная проверка выполняется backend-ом при вызове command API.
