# Тема: Контракт валидации и ошибок API

**Статус:** быстрый topic-драфт v1 / блок 2.5.3 / продолжение 2.5.1–2.5.2 / нужен repo-check по ProblemDetails, validation errors, errorCode, 401/403/404, business-state errors, file errors.

---

## 1. Зачем тема нужна

Эта тема объясняет, как backend сообщает frontend об ошибках: ошибках формы, доступа, отсутствия объекта, недопустимого состояния заявки, конфликтов действий и проблем с файлами.

Главная мысль:

> Ошибка API не должна быть просто строкой текста. Frontend должен получать структурированный ответ: тип ошибки, код, сообщение и, при необходимости, ошибки по полям формы. Это позволяет одинаково обрабатывать validation errors, access errors, business-state errors и file errors.

---

## 2. Основные типы ошибок

```text
1. Validation error
   Ошибка входных данных.

2. Unauthorized / 401
   Пользователь не вошёл в систему.

3. Forbidden / 403
   Пользователь вошёл, но не имеет права выполнить действие.

4. Not found / 404
   Объект не найден или не должен быть раскрыт текущему пользователю.

5. Business-state error
   Действие технически корректно, но недопустимо в текущем состоянии.

6. Conflict / stale data
   Данные на экране устарели, действие уже недоступно.

7. File error
   Ошибка загрузки, отсутствия файла, доступа к файлу или metadata/file consistency.

8. Unexpected error
   Непредвиденная серверная ошибка.
```

---

## 3. Validation errors

Validation errors возникают до выполнения бизнес-сценария.

Примеры:

```text
не заполнено обязательное поле;
неверный формат;
слишком длинное значение;
не передан файл;
не указана причина отказа, если она обязательна.
```

Frontend должен получить ошибки по полям:

```json
{
  "errorCode": "ValidationFailed",
  "message": "Ошибка валидации.",
  "fieldErrors": {
    "objectAddress": ["Адрес объекта обязателен."],
    "reason": ["Причина отказа обязательна."]
  }
}
```

Тезис для текста:

> Ошибки валидации должны быть связаны с конкретными полями формы, чтобы frontend мог подсветить проблемные поля и показать пользователю понятное сообщение.

---

## 4. Business-state errors

Business-state error возникает, когда запрос корректен, но действие нельзя выполнить из-за состояния объекта.

Примеры:

```text
заявка уже находится на рассмотрении;
заявка уже одобрена или отклонена;
нельзя одобрить заявку без начатого рассмотрения;
нельзя начать договорный обмен до одобрения;
версия предложения больше не актуальна;
действие из availableActions устарело.
```

Пример:

```json
{
  "errorCode": "RequestAlreadyDecided",
  "message": "По заявке уже принято решение."
}
```

Тезис:

> Business-state error отличается от validation error: входные данные могут быть корректны, но текущее состояние предметного объекта не позволяет выполнить действие.

---

## 5. 401 / 403 / 404

Нужно различать:

```text
401 Unauthorized:
пользователь не аутентифицирован.

403 Forbidden:
пользователь аутентифицирован, но не имеет права на действие.

404 Not Found:
объект не найден или не должен быть раскрыт пользователю.
```

Для чужих заявок и файлов иногда безопаснее возвращать `404`, чтобы не раскрывать факт существования объекта.

Тезис:

> Для защищённых данных API должен не только запрещать доступ, но и не раскрывать лишнюю информацию о чужих заявках, договорных обменах и файлах.

---

## 6. Ошибки файлов

Файловые ошибки отдельные, потому что file API связан с metadata, storage и access check.

Примеры:

```text
файл не передан;
файл слишком большой;
тип файла недопустим;
metadata не найдена;
physical file отсутствует;
нет доступа к файлу;
storage path/key не должен раскрываться frontend;
upload частично завершился неуспешно.
```

Безопасный ответ:

```json
{
  "errorCode": "FileUnavailable",
  "message": "Файл недоступен."
}
```

Не возвращать:

```text
internal storage path;
storage key;
stack trace;
имя директории;
детали чужого документа.
```

Тезис:

> Ошибки файлового доступа должны быть безопасными: frontend получает понятное сообщение, но не получает internal path, storage key или сведения о чужих документах.

---

## 7. Stable code и message

Нужно разделять:

```text
errorCode — стабильный код для frontend-логики;
message — текст для пользователя.
```

Пример:

```json
{
  "errorCode": "ActionNoLongerAvailable",
  "message": "Действие больше недоступно. Обновите данные заявки."
}
```

Тезис:

> Frontend не должен строить логику на тексте ошибки. Для этого нужен стабильный machine-readable code, а текст может использоваться только для отображения пользователю.

## 8. Возможная структура error response

Осторожно, до repo-check:

```json
{
  "status": 400,
  "type": "validation_error",
  "errorCode": "ValidationFailed",
  "message": "Ошибка валидации.",
  "fieldErrors": {
    "fieldName": ["Описание ошибки"]
  },
  "traceId": "..."
}
```

Если в repo есть `ProblemDetails`, можно писать:

> В качестве основы единого формата ошибок может использоваться ProblemDetails, расширенный служебным кодом ошибки и списком fieldErrors.

## 11. Черновой текст

API-контракт должен определять не только успешные ответы, но и единый способ возврата ошибок. Для frontend важно понимать, является ли ошибка результатом неверного ввода, отсутствия прав, недоступности объекта или недопустимого состояния заявки.

Ошибки валидации связаны с входными данными и могут быть отображены рядом с полями формы. Ошибки бизнес-состояния возникают в тех случаях, когда запрос технически корректен, но действие невозможно выполнить из-за текущего состояния предметного объекта. Например, заявка уже может быть рассмотрена другим сотрудником, поэтому команда одобрения должна завершиться не технической ошибкой, а структурированной business-state error.

Для защищённых данных важно различать ответы `401`, `403` и `404`. Пользователь, не прошедший аутентификацию, получает `401`. Пользователь без прав может получить `403`, а в некоторых случаях — безопасный `404`, чтобы не раскрывать факт существования чужого объекта.

Файловые ошибки также должны возвращаться через единый контракт. Backend может знать внутреннюю причину ошибки, например отсутствие physical file при наличии metadata, но frontend не должен получать storage path, storage key или внутренние детали файловой системы.
