# Topic: Формат сценарной спецификации

Status: material-harvest-needed

## 1. Зачем эта тема нужна

Эта тема объясняет, как из предметной области и пользовательских сценариев получаются требования, бизнес-правила, проверяемые состояния и будущие вертикальные срезы реализации.

## 2. Куда входит

ПЗ:
- 2.1 Роли пользователей и сценарии работы
- 2.4 Функциональная спецификация сценариев

Отчёт по ПП:
- подготовка требований и проектных материалов

Презентация:
- слайд “Сценарии и требования”

Доклад:
- тезис: требования выводились из сценариев, а не записывались произвольно.

## 3. Что нужно добиться

Преподаватель должен понять:
- сценарная спецификация связывает роль, действие, условия, результат и правила;
- сценарии помогают проектировать UI, API, домен и тесты;
- полные рабочие спецификации можно вынести в приложение.

Нужно обязательно раскрыть:
- актор;
- цель;
- предусловие;
- основной сценарий;
- альтернативный сценарий;
- постусловие;
- инвариант;
- наблюдаемый результат.

Нужно показать:
- пример SC-04;
- таблицу “сценарий → требование → реализация → тест”.

## 4. План раскрытия темы

Flow:
1. Объяснить, что сценарии фиксируют поведение системы с точки зрения пользователя и домена.
2. Русифицировать ключевые термины.
3. Показать пример на создании заявки.
4. Связать сценарий с требованиями.
5. Показать, что из сценария выделяется вертикальный срез реализации.

## 5. Запланированная реализация раскрытия

Берём:
- functional-specification;
- scenario docs;
- SC-04 diagram;
- slice docs.

Подаём так:
- не перегружать техническими деталями в начале;
- основной текст — краткая спецификация;
- приложение — полные сценарные материалы.

Обосновываем так:
- сценарии позволяют сделать требования проверяемыми.

Вставляем визуалы:
- Use Case diagram;
- фрагмент SC-04;
- mapping table.

Ссылки/источники:
- источник по Use Case / сценариям требований, если нужен.

Repo-check:
- финальные названия сценариев сверить с текущими docs.

## 8. Вопросы и решения

| Вопрос | Текущий ответ | Статус |
|---|---|---|
| Нужно ли русифицировать terms? | Да: precondition → предусловие, postcondition → постусловие, invariant → инвариант, main flow → основной сценарий. | accepted |
| Где хранить большие спецификации? | В приложении или supporting docs; в основном тексте — сжатое объяснение. | accepted |

## 9. Assumptions

- Scenario specs are design evidence, not final user manual.

## 12. Заготовки удачных формулировок

- Сценарная спецификация используется как промежуточный слой между предметной областью и реализацией: она фиксирует не только действие пользователя, но и условия, правила и ожидаемый результат.
