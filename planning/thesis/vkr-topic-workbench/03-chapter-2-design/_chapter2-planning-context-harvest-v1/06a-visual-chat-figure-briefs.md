# Visual Chat Figure Briefs — Chapter 2

**Status:** visual brief v1 / for visual-chat generation / tied to chapter-2-skeleton-v1  
**Purpose:** дать визуальному чату понятные задания на рисунки главы 2.

---

## Общие требования к рисункам

```text
- стиль: чистые схемы для ВКР, без декоративности;
- язык: русский;
- не использовать внутренние L1/L2 labels;
- использовать thesis-facing термины:
  клиент, сотрудник, заявитель, заявка, рассмотрение, решение,
  договорный обмен, версия договорного предложения, ссылка на документ;
- показывать проектную логику, а не абстрактную теорию;
- на каждом рисунке должно быть понятно, какую проблему проекта он раскрывает.
```

Каждый рисунок желательно сделать в 3 вариантах:

```text
1. строгая блок-схема;
2. swimlane / role-based схема, если есть роли;
3. компактная схема для вставки в Word.
```

## Рисунок 2.1 — Общая логика проектирования системы

Что показать:

```text
Проблемы процесса главы 1
→ Роли и сценарии
→ Предметная модель и жизненные циклы
→ Архитектура приложения
→ Хранение данных и файлов
→ API frontend/backend
→ Пользовательский интерфейс
```

Зачем:

```text
Показать, что глава 2 строится не от теории,
а от проблем процесса и проектных решений.
```

Не показывать:

```text
классы кода;
endpoint paths;
тесты;
подробности реализации.
```

## Рисунок 2.2 — Основные сценарии по ролям

Что показать:

```text
Клиент:
создать заявителя;
подать заявку;
посмотреть статус;
участвовать в договорном обмене.

Сотрудник:
открыть список заявок;
начать рассмотрение;
выполнить проверку данных;
одобрить/отклонить;
сопровождать договорный обмен.
```

Лучший формат:

```text
две колонки или swimlane:
Клиент | Сотрудник
```

Зачем:

```text
Показать, что роли выделены по участию в процессе обработки заявки.
```

## Рисунок 2.3 — Предметная модель процесса

Что показать:

```text
Клиент
→ Заявитель
→ Заявка
→ Рассмотрение заявки
→ Результат: одобрено / отклонено
→ Договорный обмен
→ Версии договорного предложения
→ Ссылка на документ
```

Важно:

```text
- клиент ≠ заявитель;
- заявка ≠ рассмотрение;
- договорный обмен ≠ один файл;
- документ показан как ссылка/metadata, а не physical path.
```

## Рисунок 2.4 — Жизненный цикл клиентской заявки

Что показать:

```text
Создание заявки
→ Доступна для рассмотрения
→ Начало работы сотрудника
→ Проверка и рассмотрение
→ Результат рассмотрения
   ├─ Одобрение → Договорный обмен
   └─ Отклонение → Результат для клиента
```

Важно:

```text
не писать Submitted/Pending;
не показывать StartReview как свободную смену статуса;
показать, что StartReview фиксирует работу сотрудника.
```

---

## Рисунок 2.5 — Жизненный цикл договорного обмена

Что показать:

```text
Заявка одобрена
→ Начат договорный обмен
→ Отправлена версия договорного предложения
→ Просмотр версии другой стороной
→ варианты:
   принять;
   отправить новую версию;
   завершить отказом.
```

Важно:

```text
- использовать “версия договорного предложения”;
- не писать “подписание договора”;
- не показывать ЭП/ЭДО;
- показать историю версий как часть обмена.
```

## Рисунок 2.6 — Общая архитектура приложения

Что показать:

```text
Frontend
→ Backend API
→ Application layer
→ Domain layer
→ Persistence + File storage
```

Внутри блоков коротко:

```text
Frontend: страницы, формы, списки, карточки, UI states
Backend API: read/command endpoints, validation, errors, auth
Application: scenarios
Domain: request, review, agreement exchange, proposal versions
Persistence/File storage: БД, metadata, physical files
```

Зачем:

```text
Показать разделение ответственности,
а не справочник по слоям.
```

## Рисунок 2.7 — Разделение БД, метаданных и физического файла

Что показать:

```text
Версия договорного предложения
→ Ссылка на документ / metadata
   - originalFileName
   - contentType
   - sizeBytes
   - storageKey
→ Файловое хранилище / physical file
```

Отдельная пометка:

```text
storageKey ≠ public URL
download через backend API
```

Зачем:

```text
Показать границу между бизнес-процессом, metadata и physical file.
```

## Рисунок 2.8 — Read/command API

Что показать:

```text
Frontend
├─ Read API:
│  получить список заявок;
│  получить карточку заявки;
│  получить договорный обмен;
│  получить историю версий.
└─ Command API:
   создать заявку;
   начать review;
   approve/reject;
   start exchange;
   send proposal version.
```

Дополнительный вариант:

```text
bad: frontend sends status = Approved
good: frontend sends approve command → backend checks → status changes
```

Зачем:

```text
Показать, что API проектируется вокруг сценариев,
а не вокруг прямого update status.
```
