# Глава 2. Проектирование web-приложения для обработки клиентских заявок

Во второй главе выполняется проектирование web-приложения, предназначенного для поддержки процесса обработки клиентских заявок в сетевой компании. В первой главе были выявлены проблемы ручного ведения заявок, недостаточной прозрачности статусов и разрозненного договорно-документного этапа. Поэтому в данной главе необходимо определить, какие роли, сценарии, предметные объекты, архитектурные решения, механизмы хранения, API и элементы пользовательского интерфейса должны быть предусмотрены в системе.

Проектирование выполняется от основного процесса: клиент подаёт заявку, сотрудник рассматривает её, принимает решение, а при положительном результате стороны переходят к договорному обмену. Следовательно, система должна поддерживать не отдельную форму обращения, а управляемую цепочку:

```text
клиент
→ заявитель
→ заявка
→ рассмотрение сотрудником
→ результат рассмотрения
→ договорный обмен
→ версия договорного предложения
→ документ
```

**Рисунок 2.1 — Общая логика проектирования системы**

```text
Проблемы процесса главы 1
        ↓
Роли и сценарии
        ↓
Предметная модель и жизненные циклы
        ↓
Архитектура приложения
        ↓
Хранение данных и файлов
        ↓
API frontend/backend
        ↓
Пользовательский интерфейс
```

## 2.1 Роли, границы доступа и основные сценарии системы

В исходном процессе клиенту важно не только подать обращение, но и видеть его дальнейшее состояние. Сотруднику, в свою очередь, нужен рабочий инструмент для просмотра заявок, начала рассмотрения, проверки данных, принятия решения и перехода к договорному этапу. Поэтому роли в системе выделяются не формально, а по участию в процессе обработки заявки.

В проектируемой системе основными ролями являются **клиент** и **сотрудник**. Клиент инициирует процесс: работает с данными заявителя, создаёт заявку, отслеживает её состояние и участвует в договорном обмене после положительного решения. Сотрудник работает с заявками со стороны организации: просматривает список обращений, открывает карточку заявки, фиксирует начало рассмотрения, выполняет проверку данных, принимает решение и при необходимости сопровождает договорный обмен.

Неавторизованный пользователь не рассматривается как отдельная предметная роль процесса. Это состояние доступа до регистрации или входа. Основные бизнес-сценарии начинаются после авторизации, потому что действия должны быть связаны либо с клиентским аккаунтом, либо с сотрудником.

**Таблица 2.1 — Роли и основные сценарии системы**

| Роль                                             | Основная цель                                        | Сценарии                                                                                                              |
| ------------------------------------------------ | ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Клиент                                           | Подать заявку и отслеживать её результат             | создание заявителя, создание заявки, просмотр статуса, просмотр результата, участие в договорном обмене               |
| Сотрудник                                        | Рассмотреть заявку и сопровождать дальнейший процесс | список заявок, карточка заявки, начало рассмотрения, проверка данных, одобрение/отклонение, запуск договорного обмена |
| Состояние доступа: неавторизованный пользователь | Получить доступ к системе                            | регистрация, вход                                                                                                     |

**Рисунок 2.2 — Основные сценарии по ролям**

```text
Клиент
 ├─ создать заявителя
 ├─ подать заявку
 ├─ посмотреть статус заявки
 └─ участвовать в договорном обмене

Сотрудник
 ├─ открыть список заявок
 ├─ начать рассмотрение
 ├─ выполнить проверку данных
 ├─ одобрить / отклонить заявку
 └─ сопровождать договорный обмен
```

В текущий объём проектирования не включаются сложная маршрутизация по подразделениям, SLA, автоматическое назначение заявок конкретным сотрудникам и юридически значимый электронный документооборот. Эти возможности могут рассматриваться как развитие системы.

## 2.2 Проектирование предметной модели и жизненных циклов

Заявка является центральным объектом процесса, но сама по себе она недостаточна для описания всей логики. Необходимо отделить клиента от заявителя, заявку от рассмотрения, результат рассмотрения от договорного обмена, а документ договорного предложения — от физического файла.

Клиент — это пользователь системы, который работает через личный кабинет. Заявитель — лицо или организация, от имени которых подаётся заявка. Такое разделение необходимо, потому что заявка должна быть связана не только с учётной записью пользователя, но и с данными стороны, по которой оформляется обращение.

Заявка отражает обращение клиента в сетевую компанию. Она связывает заявителя, данные обращения, состояние обработки и дальнейшие действия сотрудника. При этом рассмотрение заявки выделяется отдельно, поскольку работа сотрудника имеет собственные признаки: начало работы, исполнитель, завершение рассмотрения и возможное пояснение для клиента при отклонении.

После положительного результата рассмотрения возникает договорный этап. Его нельзя свести к одному прикреплённому файлу, потому что договорное взаимодействие может включать обмен версиями предложения. Поэтому в модели выделяются договорный обмен, версия договорного предложения и ссылка на документ.

**Таблица 2.2 — Основные предметные объекты**

| Объект                         | Зачем нужен в проекте                                                |
| ------------------------------ | -------------------------------------------------------------------- |
| Клиент                         | связывает действия пользователя с личным кабинетом                   |
| Заявитель                      | хранит данные лица или организации, от имени которых подаётся заявка |
| Заявка                         | является центральным объектом процесса                               |
| Рассмотрение заявки            | фиксирует работу сотрудника с заявкой                                |
| Результат рассмотрения         | отражает одобрение или отклонение                                    |
| Договорный обмен               | описывает этап согласования после одобрения                          |
| Версия договорного предложения | хранит очередной вариант предложения от клиента или сотрудника       |
| Ссылка на документ             | связывает версию предложения с файлом и его метаданными              |

**Рисунок 2.3 — Предметная модель процесса**

```text
Клиент
  │
  └── Заявитель
          │
          └── Заявка
                 │
                 ├── Рассмотрение заявки
                 │       └── Результат: одобрено / отклонено
                 │
                 └── Договорный обмен
                         └── Версии договорного предложения
                                  └── Ссылка на документ
```

### Жизненный цикл заявки

После создания заявка становится доступной для рассмотрения сотрудником. Отдельное действие начала рассмотрения фиксирует, что сотрудник принял заявку в работу, но не должно трактоваться как произвольное изменение статуса со стороны интерфейса. Такой подход позволяет отделить общее состояние заявки от факта работы сотрудника с ней.

Процесс рассмотрения включает анализ данных заявки и вспомогательную проверку данных. Такая проверка не заменяет решение сотрудника: она помогает обработке, но одобрение или отклонение остаётся отдельным действием.

При отклонении сотрудник может указать пояснение для клиента. Это пояснение хранится как часть результата рассмотрения, если оно было введено. При одобрении заявка получает возможность перейти к договорному этапу.

**Рисунок 2.4 — Жизненный цикл клиентской заявки**

```text
Создание заявки
      ↓
Доступна для рассмотрения
      ↓
Начало работы сотрудника
      ↓
Проверка и рассмотрение
      ↓
Результат рассмотрения
 ┌───────────────┴───────────────┐
Одобрение                    Отклонение
   ↓                              ↓
Договорный обмен             Результат для клиента
```

### Жизненный цикл договорного обмена

Договорный этап проектируется как обмен версиями договорного предложения, а не как одиночное прикрепление файла после одобрения заявки. После одобрения сотрудник может начать договорный обмен. В рамках обмена стороны могут работать с версиями предложения, каждая из которых имеет отправителя, состояние и связанную ссылку на документ.

Главная задача модели договорного обмена — сохранить историю согласования и показать пользователю, какая версия предложения является актуальной. Действия принятия предложения или отказа могут завершать обмен, однако в тексте не следует описывать этот процесс как юридическое подписание договора или полноценный ЭДО.

**Рисунок 2.5 — Жизненный цикл договорного обмена**

```text
Заявка одобрена
      ↓
Начат договорный обмен
      ↓
Отправлена версия договорного предложения
      ↓
Просмотр версии другой стороной
      ↓
 ┌───────────────┬────────────────────┐
Принять       Отправить новую версию  Завершить отказом
   ↓                 ↓                      ↓
Обмен завершён   История пополняется   Обмен завершён
```

## 2.3 Проектирование архитектуры web-приложения

Один пользовательский сценарий в системе проходит несколько уровней: пользователь нажимает кнопку в интерфейсе, frontend отправляет запрос, backend проверяет роль и состояние объекта, предметная модель применяет правила, а результат сохраняется в хранилище. Поэтому архитектура приложения должна разделять отображение, API, сценарную логику, предметные правила и хранение.

Frontend отвечает за отображение состояния процесса: формы, списки, карточки, кнопки действий, сообщения об ошибках и загрузку данных. Он не должен самостоятельно изменять жизненный цикл заявки. Например, сотрудник не передаёт из интерфейса новый статус заявки как свободное значение. Он выполняет действие, а backend проверяет возможность его выполнения.

Backend API является точкой входа для read- и command-сценариев. Application layer координирует выполнение сценария: определяет пользователя, проверяет доступ, загружает нужные данные и вызывает предметную логику. Domain layer содержит правила процесса: когда можно рассматривать заявку, когда можно принять решение, когда возможен договорный обмен и как связана версия предложения с документом.

Infrastructure layer отвечает за технические детали: сохранение данных в БД, работу с файловым хранилищем и вспомогательные сервисы. Такое разделение позволяет не смешивать правила обработки заявки с кодом интерфейса, HTTP-запросами, SQL-запросами и файловой системой. В главе 2 это описывается как проектное разделение ответственности, а не как подробный обзор папок репозитория. 

**Рисунок 2.6 — Общая архитектура приложения**

```text
[Frontend]
страницы клиента и сотрудника,
формы, списки, карточки, состояния UI
        │
        ▼
[Backend API]
read endpoints / command endpoints,
валидация, ошибки, авторизация
        │
        ▼
[Application layer]
сценарии: create request, approve, reject, start exchange
        │
        ▼
[Domain layer]
заявка, рассмотрение, договорный обмен, версии предложения
        │
        ▼
[Persistence + File storage]
БД, метаданные, физические файлы
```

**Проектный пример: одобрение заявки**

```text
Сотрудник нажимает “Одобрить”
        ↓
Frontend отправляет command-запрос
        ↓
Backend определяет пользователя и проверяет доступ
        ↓
Application layer загружает заявку и рассмотрение
        ↓
Domain logic проверяет допустимость решения
        ↓
Persistence сохраняет результат
        ↓
Frontend обновляет карточку заявки
```

**Таблица 2.3 — Ответственность компонентов архитектуры**

| Компонент         | Ответственность в проекте                                        |
| ----------------- | ---------------------------------------------------------------- |
| Frontend          | отображает состояние процесса и отправляет действия пользователя |
| Backend API       | принимает запросы и возвращает DTO или ошибки                    |
| Application layer | координирует сценарии и проверяет контекст выполнения            |
| Domain layer      | содержит правила заявки, рассмотрения и договорного обмена       |
| Persistence       | сохраняет структурированные данные                               |
| File storage      | хранит физические файлы договорных предложений                   |

## 2.4 Проектирование хранения данных и файлов

В процессе обработки заявки нужно хранить не только поля формы, но и состояние рассмотрения, результат решения, договорный обмен, версии предложений и связанные документы. При этом файлы договорных предложений имеют другую природу, чем структурированные данные: их содержимое хранится как physical file, а связь с процессом задаётся через метаданные.

Структурированные данные хранятся в БД: клиентские аккаунты, сотрудники, заявители, заявки, рассмотрения, результаты, договорные обмены и версии предложений. Это необходимо, чтобы состояние процесса можно было восстановить после завершения пользовательской сессии, показать в интерфейсе и использовать при проверке команд.

Файлы договорных предложений хранятся отдельно. В БД фиксируется ссылка на документ: исходное имя файла, тип содержимого, размер и служебный ключ хранения. Такая ссылка связывает файл с версией договорного предложения, но не превращает физический путь к файлу в часть пользовательского интерфейса.

`StorageKey` рассматривается как служебный ключ хранения. Он не является публичным URL и не должен использоваться пользователем как путь к файлу. Получение документа выполняется через backend API, где система может проверить связь файла с договорным обменом и права пользователя. Это особенно важно, потому что текущая модель допускает наличие служебного ключа в DTO, но сам файл не должен раздаваться как прямой public static file. 

На уровне пользовательского сценария отправка версии договорного предложения включает загрузку документа и связывание ссылки на документ с версией предложения. На уровне API это может быть реализовано несколькими шагами: сначала загружается файл и создаётся ссылка на документ, затем эта ссылка используется при создании или отправке версии договорного предложения.

**Рисунок 2.7 — Разделение БД, метаданных и физического файла**

```text
Версия договорного предложения
          │
          ▼
Ссылка на документ / metadata
- originalFileName
- contentType
- sizeBytes
- storageKey
          │
          ▼
Файловое хранилище
physical file
```

**Upload/download flow**

```text
Upload:
frontend отправляет файл
→ backend проверяет доступ
→ backend сохраняет physical file
→ backend возвращает document reference
→ document reference связывается с версией предложения

Download:
frontend запрашивает документ в контексте exchange/proposal
→ backend находит metadata
→ backend проверяет доступ
→ backend читает physical file
→ backend возвращает файл или безопасную ошибку
```

**Таблица 2.4 — Хранение данных и файлов**

| Данные                       | Где хранятся       | Почему                                                       |
| ---------------------------- | ------------------ | ------------------------------------------------------------ |
| Клиент, сотрудник, заявитель | БД                 | нужны для доступа и связи с заявками                         |
| Заявка и её состояние        | БД                 | состояние процесса должно быть восстановимо                  |
| Рассмотрение и результат     | БД                 | нужно фиксировать работу сотрудника                          |
| Договорный обмен             | БД                 | нужен статус и история согласования                          |
| Версия предложения           | БД                 | нужна история договорного обмена                             |
| Метаданные документа         | БД                 | связывают файл с версией предложения                         |
| Содержимое файла             | файловое хранилище | binary content не должен храниться как обычные поля процесса |

Проектируемая модель не претендует на полноценный электронный документооборот. В ней не рассматриваются электронная подпись, юридически значимое хранение, антивирусная проверка файлов и долговременный архив. Эти функции могут быть добавлены как развитие системы.

## 2.5 Проектирование API и взаимодействия frontend/backend

Поскольку жизненный цикл заявки и договорного обмена должен проверяться централизованно, взаимодействие frontend и backend проектируется как сценарный API-контракт. Frontend получает данные для экранов через read-запросы и выполняет действия через command-запросы.

Read API используется для получения данных, необходимых интерфейсу: списка заявок клиента, списка заявок сотрудника, карточки заявки, состояния рассмотрения, договорного обмена, истории версий предложения и метаданных документов. Такие запросы не изменяют состояние процесса. Их задача — вернуть данные в форме, удобной для конкретного экрана.

Command API используется для действий: создать заявителя, создать заявку, начать рассмотрение, выполнить демонстрационную проверку данных, одобрить заявку, отклонить заявку, начать договорный обмен, отправить версию предложения, принять предложение или завершить обмен отказом.

Command API выражает намерение пользователя, а не прямое изменение поля. Например, сотрудник не передаёт `status = Approved`; он выполняет команду одобрения, после чего backend проверяет доступ, состояние заявки и допустимость перехода. Такой подход делает API сценарным контрактом, а не CRUD-обёрткой над таблицами.

Доступность действий в интерфейсе может определяться на основе полученных данных о состоянии процесса, но backend повторно проверяет возможность выполнения команды. Это важно, потому что состояние заявки или договорного обмена могло измениться после загрузки экрана.

Файловые операции также проходят через API. Загрузка документа подготавливает ссылку на файл, а получение документа выполняется через backend в контексте договорного обмена и версии предложения. Это позволяет не использовать прямые public-ссылки на файлы и проверять доступ перед выдачей документа.

**Рисунок 2.8 — Read/command API**

```text
Frontend
 ├─ Read API
 │    ├─ получить список заявок
 │    ├─ получить карточку заявки
 │    └─ получить договорный обмен
 │
 └─ Command API
      ├─ создать заявку
      ├─ начать review
      ├─ approve / reject
      └─ send proposal version
```

**Таблица 2.5 — Примеры API-сценариев**

| Сценарий                     | Тип API      | Проектный смысл                                 |
| ---------------------------- | ------------ | ----------------------------------------------- |
| Получить список заявок       | read         | показать состояние обращений                    |
| Открыть карточку заявки      | read         | показать детали и доступные действия            |
| Создать заявку               | command      | начать процесс обращения                        |
| Начать рассмотрение          | command      | зафиксировать работу сотрудника                 |
| Выполнить проверку данных    | command-like | получить результат вспомогательной проверки     |
| Одобрить заявку              | command      | изменить состояние через backend rules          |
| Отклонить заявку             | command      | зафиксировать отрицательный результат           |
| Начать договорный обмен      | command      | перейти к договорному этапу                     |
| Отправить версию предложения | command      | добавить новую версию в обмен                   |
| Скачать документ             | file read    | получить файл через backend с проверкой доступа |

Ошибки API должны различать ошибки формы, ошибки доступа, отсутствие объекта, недопустимое бизнес-состояние и проблемы файлового доступа. Это нужно не для теоретического описания обработки ошибок, а для корректного поведения UI: подсветить поле, показать сообщение о недоступном действии или обновить карточку, если состояние устарело.

Формализованное API-описание и общие константы могут использоваться как средство уменьшения рассинхронизации между frontend и backend. В главе проектирования это рассматривается как способ удерживать единый контракт, а технические детали генерации относятся к главе реализации.

## 2.6 Проектирование пользовательского интерфейса

Пользовательский интерфейс проектируется вокруг двух рабочих потоков: клиентского и сотруднического. Клиент должен видеть свои заявки, их состояние и договорный обмен. Сотрудник должен видеть рабочий список заявок, карточку рассмотрения, действия по проверке и решению, а также договорный этап после одобрения.

Клиентская зона включает работу с заявителями, создание заявки, просмотр списка заявок, открытие карточки заявки и переход к договорному обмену. Сотрудническая зона включает список заявок, карточку заявки, блок рассмотрения, действия проверки, одобрения или отклонения, а также сопровождение договорного обмена.

Для клиента карточка заявки является экраном отслеживания состояния. Для сотрудника эта же карточка является рабочим экраном обработки. Поэтому карточка заявки должна показывать данные заявки, данные заявителя, текущее состояние, результат рассмотрения и действия, доступные текущему пользователю.

Интерфейс договорного обмена проектируется как экран процесса, а не как файловый список. Пользователь должен видеть статус обмена, связанную заявку, активную версию предложения, историю версий и доступные действия. Файл отображается через имя и метаданные, а получение файла выполняется через backend.

Так как состояние заявки может измениться после загрузки экрана, интерфейс не должен считать доступность действия окончательной. Он может отключать кнопки или показывать доступные действия на основе полученных данных, но backend повторно проверяет возможность выполнения команды. Если состояние устарело, пользователь должен получить понятное сообщение и обновить данные.

**Рисунок 2.9 — Навигационная структура UI**

```text
Клиент
 ├─ Мои заявители
 ├─ Мои заявки
 │    ├─ Создание заявки
 │    └─ Карточка заявки
 └─ Договорные обмены
      └─ Карточка обмена

Сотрудник
 ├─ Заявки клиентов
 │    └─ Карточка заявки / review
 └─ Договорные обмены
      └─ Карточка обмена
```

**Рисунок 2.10 — UI-flow заявки**

```text
Клиент:
создать заявителя
→ создать заявку
→ открыть карточку заявки
→ видеть статус/результат

Сотрудник:
открыть список заявок
→ открыть карточку
→ начать review
→ выполнить проверку
→ approve/reject
```

**Рисунок 2.11 — Экран договорного обмена**

```text
Статус обмена
      ↓
Краткая информация по заявке
      ↓
Активная версия предложения
      ↓
История версий
      ↓
Доступные действия
```

**Таблица 2.6 — UI-состояния и реакция интерфейса**

| Состояние            | Пример                   | Реакция UI                              |
| -------------------- | ------------------------ | --------------------------------------- |
| Loading              | загрузка карточки заявки | индикатор ожидания                      |
| Empty                | нет заявок               | пустое состояние с пояснением           |
| Validation error     | не заполнено поле        | подсветка поля                          |
| Forbidden            | нет доступа              | сообщение о недоступности               |
| Business-state error | заявка уже обработана    | сообщение и обновление данных           |
| File error           | документ недоступен      | безопасное сообщение без раскрытия пути |
| Success              | заявка одобрена          | обновление карточки и статуса           |

## Выводы по главе 2

В результате проектирования определены роли пользователей, основные сценарии, предметная модель, жизненные циклы заявки и договорного обмена, архитектура web-приложения, модель хранения данных и файлов, API-контракт и структура пользовательского интерфейса.

Заявка рассматривается как центральный объект процесса, связанный с клиентом, заявителем, рассмотрением, результатом и договорным этапом. Договорный обмен проектируется как обмен версиями договорного предложения, а не как одиночный файл. Для связи версий с документами используется ссылка на документ и метаданные, а физический файл хранится отдельно.

Архитектура приложения разделяет frontend, backend API, application layer, domain layer, persistence и file storage. Такое разделение необходимо, чтобы frontend отображал состояние и отправлял действия, но не менял жизненный цикл заявки напрямую. Изменение состояния выполняется через command API после проверки роли, доступа, текущего состояния и предметных правил.

Полученные проектные решения являются основой для реализации web-приложения, которая рассматривается в третьей главе.
