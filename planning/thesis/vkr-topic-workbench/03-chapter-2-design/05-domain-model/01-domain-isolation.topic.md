# Topic: Изоляция домена

Status: material-harvest-needed

## 1. Зачем эта тема нужна

Эта тема объясняет, почему бизнес-правила заявки, заявителя, рассмотрения и договорного обмена не должны растворяться в UI, контроллерах или инфраструктуре. Она помогает показать инженерную основу проекта.

## 2. Куда входит

ПЗ:
- 2.5 Доменная модель
- 2.7 Архитектура frontend и backend
- 3.7 Тестирование доменной логики и API

Отчёт по ПП:
- доменная модель и структура данных

Презентация:
- слайд “Доменная модель” или “Архитектура”

Доклад:
- тезис об отделении правил предметной области от технических деталей.

## 3. Что нужно добиться

Преподаватель должен понять:
- доменная модель хранит правила и инварианты;
- UI и API не должны быть местом основных бизнес-правил;
- домен можно тестировать отдельно;
- применяются отдельные принципы предметно-ориентированного проектирования, без превращения ВКР в теоретическую работу по DDD.

Нужно обязательно раскрыть:
- доменные сущности;
- инварианты;
- доменные методы;
- независимое тестирование домена.

Нужно показать:
- общую доменную диаграмму;
- схему зависимостей, где домен отделён от UI/API/persistence.

## 4. План раскрытия темы

Flow:
1. Показать, что предметные правила повторяются в разных сценариях.
2. Объяснить, почему их нужно держать в доменной модели.
3. Назвать ключевые сущности.
4. Показать, какие инварианты относятся к заявке и договорному обмену.
5. Объяснить, что домен проверяется отдельными тестами.

## 5. Запланированная реализация раскрытия

Берём:
- clean-domain-model;
- domain tests;
- docs/questions about invariants;
- scenario specs.

Подаём так:
- использовать осторожную формулировку “отдельные принципы предметно-ориентированного проектирования”;
- не писать большую теорию DDD;
- объяснить на конкретных примерах проекта.

Обосновываем так:
- правила заявки и договорного обмена должны быть единообразными независимо от UI/API.

Вставляем визуалы:
- domain model diagram;
- domain isolation diagram.

Ссылки/источники:
- можно использовать источник по DDD/чистой архитектуре точечно, если требуется.

Repo-check:
- сверить актуальные доменные сущности и названия.

## 12. Заготовки удачных формулировок

- В проекте применяются отдельные принципы предметно-ориентированного проектирования: ключевые правила заявки, заявителя и договорного обмена выносятся в доменную модель и проверяются отдельно от пользовательского интерфейса.
