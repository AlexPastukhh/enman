## 2. Что это за тема

Эта тема раскрывает, **какую ответственность несёт frontend, какую — backend, и почему бизнес-правила не должны находиться только в пользовательском интерфейсе**.

Предыдущая тема 2.3.1 отвечала на вопрос:

```text id="zukon8"
из каких крупных компонентов состоит архитектура web-приложения
```

Текущая тема отвечает на вопрос:

```text id="582dde"
как между frontend и backend распределяются:
отображение,
запуск действий,
валидация,
проверка доступа,
чтение данных,
изменение состояния,
ошибки,
работа с файлами
и бизнес-правила.
```

Главная мысль:

> Frontend отвечает за пользовательское взаимодействие: экраны, формы, кнопки, локальные состояния и отображение результата. Backend отвечает за серверную проверку доступа, применение бизнес-правил, изменение состояния заявки и договорного обмена, сохранение данных и файлов. Frontend может скрыть недоступную кнопку или показать подсказку, но окончательное решение о допустимости действия должно приниматься на backend через application layer и domain layer.

## 3. Важное уточнение: frontend не является source of truth

Frontend нужен для удобного взаимодействия пользователя с системой, но он не должен быть единственным местом, где существуют правила.

### Frontend может

```text id="a1zdf5"
показать кнопку;
скрыть кнопку;
заблокировать кнопку;
показать подсказку;
проверить заполненность поля;
показать ошибку;
показать статус;
отобразить доступные действия;
передать файл;
показать результат backend-операции.
```

### Frontend не должен окончательно решать

```text id="m1dciu"
может ли пользователь видеть чужую заявку;
может ли сотрудник рассматривать заявку;
может ли сотрудник одобрить заявку;
может ли клиент изменить статус;
можно ли начать договорный обмен;
можно ли принять договорное предложение;
является ли переход состояния допустимым;
можно ли связать файл с версией предложения;
выполнена ли бизнес-проверка.
```

Безопасная формулировка:

> Frontend может улучшать пользовательский опыт и предотвращать очевидные ошибки ввода, однако он не является источником истины для бизнес-правил. Окончательная проверка доступа, принадлежности данных и допустимости изменения состояния выполняется на backend.

## 4. Принятые уточнения

1. Тема относится к архитектуре, а не к реализации конкретных компонентов.
2. Frontend отвечает за UI, запуск действий и отображение результата.
3. Backend отвечает за доступ, бизнес-правила, состояние и сохранение данных.
4. API-контракт является границей взаимодействия frontend/backend.
5. Frontend не обращается напрямую к БД и файловому хранилищу.
6. Frontend не должен быть единственным источником бизнес-правил.
7. Backend API принимает запрос и возвращает результат или ошибку.
8. Application layer координирует пользовательский сценарий.
9. Domain layer содержит основную бизнес-логику, состояния и инварианты.
10. Валидация делится на frontend validation, request validation и application/domain validation.
11. Frontend validation — это подсказка пользователю, а не гарантия корректности системы.
12. Похожая проверка на frontend, backend/application и domain layer не всегда является плохим дублированием, потому что уровни решают разные задачи.
13. Read API и command API имеют разную ответственность.
14. Read API готовит данные для отображения.
15. Command API запускает сценарий изменения состояния.
16. DTO ответа не должен быть прямым отражением domain model.
17. Frontend может получать action availability в read DTO, но это не заменяет backend/domain проверку при выполнении команды.
18. Ошибки должны быть структурированными: не только текст, но и code/type/fieldErrors, если такая модель подтверждена.
19. 401, 403 и 404 нужно различать по смыслу, особенно при доступе к чужим данным.
20. ProblemDetails можно упоминать как возможный механизм единого формата ошибок, но подробно раскрывать в 2.5.
21. OpenAPI и generated constants/types можно упоминать как способ согласования frontend/backend, но подробно раскрывать в 2.5.
22. Mock-кнопка проверки данных должна описываться как frontend-точка запуска backend-сценария, а не как реальная внешняя интеграция.
23. Mock-проверка не принимает решение за сотрудника.
24. Бизнес-логика проверки заявки не должна жить в кнопке.
25. Работа с файлами делится на upload и download сценарии.
26. Frontend выбирает/передаёт файл или запрашивает файл.
27. Backend сохраняет physical file, metadata и проверяет доступ при выдаче.
28. Domain layer не хранит байты файла и не знает storage path.
29. Email/push, ЭП, ЭДО, полноценная СЭД и промышленный storage не заявлять как реализованные функции.
30. Не писать, что “что-то не доделано”; писать через архитектурную расширяемость и возможность локальной замены поведения.
31. Сценарии из `planning/use-cases.md` использовать как карту, но нормализовать старые элементы: L1/L2/L3, ContractDraft, email, PDF generation, старые статусы.
32. Детальные endpoints, DTO, React-компоненты, controllers, handlers и тесты раскрываются в главе 3 или в 2.5, если речь про API-flow.

## 5. Сценарная основа темы

Разделение ответственности frontend/backend должно объясняться через пользовательские сценарии.

Основные сценарии:

```text id="bi3m5d"
клиент входит в систему;
клиент создаёт заявителя;
клиент создаёт заявку;
клиент просматривает свои заявки;
сотрудник открывает список заявок;
сотрудник открывает карточку заявки;
сотрудник начинает рассмотрение;
сотрудник запускает проверку данных;
сотрудник одобряет или отклоняет заявку;
сотрудник начинает договорный обмен;
сотрудник отправляет версию договорного предложения;
клиент просматривает версию;
клиент принимает предложение или отправляет встречную версию, если подтверждено моделью;
клиент или сотрудник загружает/получает файл версии предложения.
```

Для каждого сценария есть общий принцип:

```text id="2fsjx9"
frontend отображает и запускает действие;
read API готовит данные для экрана;
command API запускает изменение состояния;
backend проверяет и выполняет действие;
application layer координирует сценарий;
domain layer определяет, допустимо ли изменение состояния;
storage сохраняет результат.
```

Рабочая формулировка:

> Разделение frontend и backend проектируется исходя из сценариев системы. Пользователь выполняет действие в интерфейсе, но изменение состояния заявки, рассмотрения или договорного обмена происходит только после серверной проверки и применения предметных правил.

## 6. Зачем эта тема нужна

### На уровне темы

Тема нужна, чтобы не смешивать UI-логику и бизнес-логику.

Без этого разделения возникнут проблемы:

```text id="vjfjoo"
одно и то же правило появится в разных UI-компонентах;
пользователь сможет обойти frontend-ограничение прямым API-запросом;
изменение статуса будет зависеть от UI-кнопки;
read DTO начнёт протекать во внутреннюю domain model;
валидация станет непредсказуемой;
ошибки будут по-разному отображаться в разных местах;
расширение сценариев станет дороже.
```

## 7. Содержание темы

### 7.1 Frontend как слой пользовательского взаимодействия

Frontend отвечает за то, что пользователь видит и какие действия может запустить.

Frontend включает:

```text id="xq95ar"
страницы;
формы;
таблицы;
карточки заявок;
кнопки действий;
локальные состояния загрузки;
локальные состояния ошибок;
подсказки валидации;
отображение статусов;
отображение доступных действий;
отображение результата backend-операции.
```

Рабочая формулировка:

> Frontend обеспечивает взаимодействие пользователя с системой. Он отображает формы, списки, карточки, статусы и доступные действия, а также отправляет действия пользователя на backend через API.

---

### 7.2 Frontend-зоны: клиент и сотрудник

Frontend должен поддерживать разные пользовательские сценарии.

Клиентская зона:

```text id="08fvm6"
личный кабинет;
заявители;
создание заявки;
список своих заявок;
статус и результат;
договорный обмен по своей заявке;
просмотр версий договорного предложения;
действия клиента по версии, если подтверждены моделью.
```

Зона сотрудника:

```text id="5mge3i"
список заявок;
карточка заявки;
рассмотрение;
проверка данных;
одобрение;
отклонение;
причина отказа;
начало договорного обмена;
отправка версии договорного предложения;
просмотр версий клиента.
```

Рабочая формулировка:

> Frontend должен учитывать разные сценарии клиента и сотрудника. Клиентская зона ориентирована на подачу и отслеживание заявки, а зона сотрудника — на рассмотрение, принятие решения и сопровождение договорного обмена.

---

### 7.3 Backend API как серверная граница

Backend API принимает запросы от frontend и возвращает результат.

Backend API отвечает за:

```text id="s68ob9"
приём запросов;
маршрутизацию к нужному сценарию;
первичную проверку авторизации;
проверку формы запроса;
возврат успешного результата;
возврат ошибки в едином формате;
изоляцию frontend от внутренней структуры backend.
```

Рабочая формулировка:

> Backend API является серверной границей системы. Frontend не обращается напрямую к базе данных или файловому хранилищу, а выполняет действия через API, который передаёт запрос в соответствующий сценарий application layer.

---

### 7.4 Application layer как координатор сценария

Application layer выполняет сценарий, который был запущен через API.

Он координирует:

```text id="19cbv8"
проверку доступа;
загрузку данных;
проверку принадлежности данных пользователю;
вызов domain layer;
сохранение результата;
работу с metadata;
подготовку ответа frontend.
```

Примеры:

```text id="zo796j"
создать заявителя;
создать заявку;
начать рассмотрение;
выполнить проверку данных;
одобрить заявку;
отклонить заявку;
начать договорный обмен;
отправить версию договорного предложения.
```

Рабочая формулировка:

> Application layer связывает пользовательское действие с серверной логикой: проверяет доступ, получает нужные данные, вызывает предметные правила, сохраняет результат и формирует ответ для frontend.

---

### 7.5 Domain layer как источник бизнес-правил

Domain layer содержит основную бизнес-логику.

Он отвечает за:

```text id="48rzxt"
состояния заявки;
допустимые переходы;
правила начала рассмотрения;
правила одобрения и отклонения;
правила перехода к договорному обмену;
правила создания версии договорного предложения;
инварианты отправителя версии;
защиту от некорректных состояний.
```

Domain layer не должен зависеть от:

```text id="a7tg3g"
React-компонентов;
HTTP-запросов;
DTO;
controllers;
БД;
ORM;
файлового хранилища;
внешних интеграций.
```

Рабочая формулировка:

> Domain layer является источником бизнес-правил системы. Он определяет, какие состояния и переходы допустимы для заявки и договорного обмена, и не зависит от деталей пользовательского интерфейса, HTTP-слоя, базы данных и файлового хранения.

---

### 7.6 Разделение frontend validation, request validation и domain validation

Валидация не должна быть одной большой проверкой в одном месте.

Frontend validation:

```text id="sp5xx5"
помогает пользователю заполнить форму;
показывает обязательные поля;
показывает форматные подсказки;
уменьшает количество очевидно ошибочных запросов.
```

Request validation на backend:

```text id="bifkkl"
проверяет структуру запроса;
проверяет обязательные поля;
проверяет формат входных данных;
возвращает ошибки валидации frontend.
```

Application/domain validation:

```text id="54sstx"
проверяет права доступа;
проверяет принадлежность данных пользователю;
проверяет существование объектов;
проверяет допустимость действия в текущем состоянии;
проверяет бизнес-инварианты.
```

Рабочая формулировка:

> Frontend validation улучшает удобство пользователя, но не заменяет серверную проверку. Backend должен проверить форму запроса, права доступа, принадлежность данных и допустимость изменения состояния предметного объекта.

---

### 7.7 Frontend validation как подсказка, а не гарантия

Frontend validation не должна рассматриваться как гарантия корректности системы.

Frontend может проверить:

```text id="x0sqoj"
заполнено ли обязательное поле;
похож ли email на email;
выбран ли файл;
не пустой ли комментарий;
не превышен ли визуальный лимит длины поля.
```

Но frontend не может окончательно решить:

```text id="tns6kl"
принадлежит ли заявка текущему клиенту;
может ли сотрудник рассматривать заявку;
можно ли одобрить заявку в текущем состоянии;
можно ли начать договорный обмен;
можно ли принять конкретную версию предложения.
```

Рабочая формулировка:

> Проверки на стороне frontend следует рассматривать как механизм удобства пользователя, а не как источник бизнес-гарантий. Даже если интерфейс скрывает недоступное действие или показывает ошибку до отправки формы, backend должен повторно проверить доступ, состояние объекта и бизнес-инварианты.

---

### 7.8 Повторение проверки на разных уровнях

Похожая проверка на разных уровнях не всегда является плохим дублированием.

Пример:

```text id="gfddcm"
Frontend:
скрывает кнопку “Одобрить”, если в DTO указано,
что действие недоступно.

Backend/application:
проверяет, действительно ли заявка может быть одобрена
текущим сотрудником.

Domain layer:
проверяет, допустим ли переход заявки в состояние одобрения.
```

Разный смысл проверки:

```text id="yytgnb"
frontend — удобство и предотвращение лишнего действия;
backend/application — безопасность и доступ;
domain — бизнес-корректность состояния.
```

Рабочая формулировка:

> Повторение похожей проверки на разных уровнях не всегда означает размазывание логики. Frontend использует проверку для отображения доступных действий, application layer — для защиты сценария и доступа, а domain layer — для сохранения корректности предметного состояния.

---

### 7.9 Доступность действий в UI и read DTO

Frontend может отображать доступные действия на основе данных, полученных от backend.

Read DTO может содержать:

```text id="uosoi7"
requestStatus;
reviewState;
startedByCurrentEmployee;
canStartReview;
canApprove;
canReject;
canStartAgreementExchange;
canUploadProposal;
canAcceptProposal.
```

Frontend использует эти значения для:

```text id="v0pk9k"
отображения кнопок;
скрытия недоступных действий;
показа подсказок;
объяснения текущего состояния;
упрощения UI-flow.
```

Но это не заменяет command validation.

Рабочая формулировка:

> Доступность действий может передаваться frontend как часть модели чтения. Это упрощает отображение интерфейса, но не переносит бизнес-правила во frontend: при выполнении команды backend повторно проверяет состояние объекта и права пользователя.

---

### 7.10 Разделение read API и command API

API системы можно условно разделить на два типа операций.

Read operations:

```text id="qp2yxw"
получить список заявок;
открыть карточку заявки;
получить историю договорного обмена;
получить доступные действия;
получить список версий предложения.
```

Command operations:

```text id="rq85go"
создать заявителя;
создать заявку;
начать рассмотрение;
одобрить заявку;
отклонить заявку;
начать договорный обмен;
отправить версию предложения;
принять предложение, если подтверждено моделью.
```

Разница:

```text id="x5d8l3"
read API готовит данные для отображения;
command API меняет состояние;
read DTO может быть удобным для конкретного экрана;
command должен проходить через application layer и domain layer.
```

Рабочая формулировка:

> Операции чтения и изменения состояния имеют разную архитектурную роль. Read API подготавливает данные для отображения, а command API запускает сценарий изменения состояния. Поэтому список заявок может использовать модель чтения, удобную для интерфейса, тогда как одобрение заявки должно проходить через application layer и domain layer.

---

### 7.11 DTO не равен domain model

Frontend не должен напрямую зависеть от внутренней структуры domain layer.

API возвращает данные:

```text id="1fb03x"
нужные конкретному экрану;
нужные конкретному сценарию;
достаточные для отображения статуса;
достаточные для показа доступных действий;
не раскрывающие лишнюю внутреннюю структуру backend.
```

Например, если внутри domain layer заявка содержит внутренний объект рассмотрения, frontend не обязан знать все его поля. Для dashboard может быть достаточно:

```text id="pkhk20"
reviewState;
startedByEmployeeName;
startedByCurrentEmployee;
availableActions;
statusLabel;
lastUpdatedAt.
```

Рабочая формулировка:

> DTO ответа не должен быть прямым отражением доменной модели. API возвращает данные, необходимые для конкретного пользовательского сценария, а внутренняя структура domain layer остаётся серверной деталью. Это снижает связанность frontend с внутренней моделью backend.

---

### 7.12 Проверка доступа

Проверка доступа должна быть серверной ответственностью.

Frontend может:

```text id="85n828"
не показывать недоступную кнопку;
скрыть раздел;
показать сообщение “действие недоступно”;
перенаправить пользователя.
```

Backend должен:

```text id="mv6a20"
проверить авторизацию;
проверить роль пользователя;
проверить принадлежность данных;
проверить доступность действия;
запретить действие при нарушении правил.
```

Рабочая формулировка:

> Даже если frontend скрывает недоступные действия, backend обязан проверять доступ повторно. Это защищает систему от прямых API-запросов и обеспечивает единый источник правил доступа.

---

### 7.13 Изменение состояния заявки

Изменение состояния заявки не должно выполняться во frontend.

Правильный flow:

```text id="60g8m3"
сотрудник нажимает кнопку во frontend;
frontend отправляет запрос;
backend API принимает запрос;
application layer проверяет доступ и загружает заявку;
domain layer проверяет допустимость перехода;
изменение сохраняется в БД;
frontend получает результат и обновляет отображение.
```

Примеры:

```text id="b20zc9"
одобрить заявку;
отклонить заявку;
начать рассмотрение;
начать договорный обмен.
```

Рабочая формулировка:

> Frontend запускает действие, но не изменяет состояние заявки самостоятельно. Изменение состояния выполняется на backend после проверки доступа и применения правил domain layer.

---

### 7.14 Mock-проверка как вспомогательный результат, а не решение

Проверка данных может вернуть результат, который помогает сотруднику принять решение.

Разделение:

```text id="qo0zvq"
проверка данных:
даёт результат проверки;

решение сотрудника:
меняет состояние заявки.
```

Frontend:

```text id="v9z4uq"
показывает кнопку проверки;
показывает загрузку;
показывает результат проверки;
показывает ошибку, если backend вернул ошибку.
```

Backend/application:

```text id="z5e06x"
принимает запрос проверки;
проверяет доступ сотрудника;
выполняет mock-проверку или вызывает service boundary;
возвращает результат;
не одобряет и не отклоняет заявку автоматически.
```

Рабочая формулировка:

> Результат проверки данных является входной информацией для сотрудника, но не заменяет само решение по заявке. Одобрение или отклонение остаётся отдельным действием сотрудника и проходит через domain layer как изменение состояния заявки.

---

### 7.15 Работа с файлами: upload и download

Работа с файлами включает два разных сценария.

Upload:

```text id="fpmc5w"
frontend выбирает файл;
backend проверяет доступ;
backend сохраняет physical file;
backend сохраняет metadata;
domain layer проверяет допустимость document ref / proposal version.
```

Download:

```text id="zwj6wh"
frontend запрашивает файл;
backend проверяет доступ;
backend находит metadata;
backend получает physical file;
backend отдаёт файл или ошибку.
```

Рабочая формулировка:

> Файловый сценарий состоит не только из загрузки, но и из последующего получения файла. В обоих случаях frontend не должен обращаться к файловому хранилищу напрямую: backend проверяет доступ и связывает физический файл с предметными метаданными.

---

### 7.16 Ошибки: code/type/message/fieldErrors

Frontend должен получать от backend понятную и структурированную ошибку.

Ошибка может включать:

```text id="vmbqib"
errorCode;
type;
message;
fieldErrors;
traceId, если используется;
status.
```

Пример бизнес-ошибки:

```text id="e6y5hz"
errorCode: RequestAlreadyInReview
message: Заявка уже находится на рассмотрении.
fieldErrors: null
```

Пример ошибки валидации:

```text id="stuxp1"
errorCode: ValidationFailed
fieldErrors:
  objectAddress: Адрес объекта обязателен.
```

Рабочая формулировка:

> Для frontend важно получать не только текст ошибки, но и структурированный код или тип ошибки. Это позволяет одинаково обрабатывать ошибки доступа, ошибки валидации и ошибки бизнес-состояния, не завязывая интерфейс на конкретный текст сообщения.

---

### 7.17 401 / 403 / 404 и сокрытие чужих данных

При проектировании API важно различать ситуации:

```text id="3in1cr"
401 Unauthorized:
пользователь не вошёл в систему;

403 Forbidden:
пользователь вошёл, но не имеет роли или права;

404 Not Found:
объект не существует или не должен быть раскрыт текущему пользователю.
```

Для клиентских данных иногда безопаснее возвращать `404`, если пользователь пытается открыть чужую заявку, чтобы не раскрывать факт существования объекта.

Рабочая формулировка:

> Backend должен не только проверять доступ, но и корректно выбирать тип ответа. Для защищённых клиентских данных отсутствие доступа может обрабатываться как отсутствие ресурса для текущего пользователя, чтобы не раскрывать сведения о чужих заявках.

### 7.18 API-контракт как договорённость frontend/backend

API-контракт нужен, чтобы frontend и backend одинаково понимали:

```text id="rsffol"
какие запросы существуют;
какие данные нужно отправлять;
какие ответы можно получить;
какие ошибки возможны;
как называются поля;
какие коды используются;
какие действия доступны для сценария.
```

Возможные механизмы:

```text id="2vuggh"
OpenAPI;
generated types;
generated constants;
ProblemDetails;
единые error codes;
единая структура validation errors.
```

Рабочая формулировка:

> API-контракт является технической и смысловой границей между frontend и backend. Он описывает не только структуру запросов и ответов, но и единый способ обработки ошибок, служебных кодов и результатов валидации.

---

### 7.19 Изменение поведения без переписывания всей системы

Разделение ответственности делает изменение поведения локальным.

Примеры:

```text id="h3xk7d"
изменить правило одобрения заявки в domain layer;
добавить новое условие проверки в application layer;
заменить mock-проверку внешней интеграцией;
изменить формат ошибки через API-контракт;
добавить новый UI-state без изменения business rule;
заменить файловое хранилище за backend boundary;
расширить договорный обмен новой операцией.
```

Рабочая формулировка:

> Такое разделение позволяет изменять поведение системы локально. Например, если правило одобрения заявки меняется, изменение должно затронуть domain/application слой, а не набор разрозненных UI-компонентов. Если mock-проверка заменяется внешним сервисом, frontend продолжает запускать тот же сценарий через API, а меняется серверная реализация точки расширения.

## 14. Что требует обоснования

### 14.1 Почему frontend не является источником бизнес-правил

Будущая формулировка:

> Frontend может отображать доступные действия и выполнять предварительные проверки, однако он не должен быть источником бизнес-правил. Пользователь может обойти интерфейс и обратиться к API напрямую, поэтому окончательная проверка должна выполняться на backend.

---

### 14.2 Почему frontend validation не является гарантией

Будущая формулировка:

> Frontend validation помогает пользователю быстрее исправить ввод, но не гарантирует корректность действия. Серверная часть должна повторно проверить запрос, доступ и состояние предметного объекта.

---

### 14.3 Почему похожая проверка на разных уровнях не всегда дублирование

Будущая формулировка:

> Проверка доступности действия на frontend, application layer и domain layer имеет разный смысл: frontend отвечает за удобство интерфейса, application layer — за защиту сценария, а domain layer — за корректность предметного состояния.

---

### 14.4 Почему read API и command API разделяются

Будущая формулировка:

> Read API ориентирован на отображение данных, а command API — на изменение состояния. Поэтому операции изменения должны проходить через application layer и domain layer, даже если read DTO уже содержит информацию о доступных действиях.

---

### 14.5 Почему DTO не должен повторять domain model

Будущая формулировка:

> DTO ответа должен быть удобен для конкретного пользовательского сценария, но не обязан раскрывать внутреннюю структуру domain layer. Это снижает связанность frontend и backend.

---

### 14.6 Почему backend проверяет доступ повторно

Будущая формулировка:

> Серверная проверка доступа необходима даже в тех случаях, когда frontend уже скрыл недоступные действия. Это обеспечивает защиту данных и единообразное применение правил доступа.

---

### 14.7 Почему изменение состояния выполняется через application/domain

Будущая формулировка:

> Изменение состояния заявки или договорного обмена должно выполняться через application layer и domain layer. Application layer координирует сценарий, а domain layer проверяет допустимость перехода и бизнес-инварианты.

---

### 14.8 Почему mock-проверка не должна принимать решение

Будущая формулировка:

> Результат проверки данных является вспомогательной информацией для сотрудника. Одобрение или отклонение заявки остаётся отдельным действием, потому что именно оно изменяет состояние заявки.

---

### 14.9 Почему работа с файлами делится на upload/download

Будущая формулировка:

> Загрузка и получение файла являются разными API-сценариями. В обоих случаях backend должен проверять доступ, потому что файл связан с договорным обменом и заявкой.

---

### 14.10 Почему API-контракт важен

Будущая формулировка:

> API-контракт фиксирует границу между frontend и backend. Он снижает риск рассинхронизации, задаёт структуру запросов и ответов и обеспечивает единый способ обработки ошибок.

---

### 14.11 Почему 401/403/404 нужно различать

Будущая формулировка:

> Разные ошибки доступа требуют разного поведения frontend. Кроме того, для защищённых клиентских данных backend может не раскрывать факт существования чужого ресурса и возвращать результат как отсутствие доступного объекта.

---

### 14.12 Почему разделение ответственности помогает расширять систему

Будущая формулировка:

> Разделение ответственности позволяет изменять поведение системы локально. Бизнес-правила изменяются в domain/application слоях, интерфейс отвечает за отображение, а инфраструктура может развиваться за отдельной границей.

## 17. Черновые фрагменты будущего текста

### Фрагмент 1 — ввод

После описания общей архитектуры web-приложения необходимо уточнить разделение ответственности между frontend и backend. Это разделение важно, потому что пользовательские действия в системе связаны не только с отображением данных, но и с изменением состояния предметных объектов: заявителя, заявки, рассмотрения и договорного обмена.

### Фрагмент 2 — общий принцип

Frontend отвечает за отображение страниц, форм, кнопок, состояний загрузки и результатов действий. Backend отвечает за серверную проверку запроса, выполнение сценария, применение бизнес-правил и сохранение результата.

### Фрагмент 3 — frontend

Frontend запускает пользовательские действия, но не является источником истины для бизнес-правил. Он может скрывать недоступные действия и показывать подсказки, однако окончательная проверка выполняется на backend.

### Фрагмент 4 — backend API

Backend API является границей между пользовательским интерфейсом и серверной частью. Через него frontend передаёт действия пользователя, а сервер возвращает результат выполнения сценария или описание ошибки.

### Фрагмент 5 — application layer

Application layer координирует выполнение сценария: проверяет доступ, загружает нужные данные, обращается к domain layer, сохраняет результат и формирует ответ.

### Фрагмент 6 — domain layer

Domain layer содержит основные бизнес-правила: допустимые состояния заявки, условия рассмотрения, одобрения, отклонения и перехода к договорному обмену. Эти правила не должны зависеть от UI, HTTP-запросов или базы данных.

### Фрагмент 7 — frontend validation

Валидация на стороне frontend нужна для удобства пользователя, но не является гарантией корректности действия. Backend повторно проверяет структуру запроса, доступ, принадлежность данных и состояние предметного объекта.

### Фрагмент 8 — action availability

Доступность действий может передаваться frontend в модели чтения, чтобы интерфейс мог показать нужные кнопки и подсказки. Однако при выполнении команды backend обязан повторно проверить доступность действия через application layer и domain layer.

### Фрагмент 9 — read/command

Операции чтения и изменения состояния имеют разную архитектурную роль. Read API подготавливает данные для экрана, а command API запускает сценарий изменения состояния и должен проходить через application layer и domain layer.

### Фрагмент 10 — DTO не равен domain model

DTO ответа не должен быть прямым отражением доменной модели. API возвращает данные, необходимые для конкретного пользовательского сценария, а внутренняя структура domain layer остаётся серверной деталью.

### Фрагмент 11 — ошибки

Для frontend важно получать не только текст ошибки, но и структурированный код или тип ошибки. Это позволяет единообразно обрабатывать ошибки доступа, валидации и бизнес-состояния.

### Фрагмент 12 — mock-проверка

Кнопка проверки данных во frontend является только способом запуска сценария. Результат проверки помогает сотруднику принять решение, но не заменяет само действие одобрения или отклонения заявки.

### Фрагмент 13 — файлы

Работа с файлами делится на загрузку и получение. Frontend выбирает или запрашивает файл, backend проверяет доступ, сохраняет или читает physical file и metadata, а domain layer проверяет предметную допустимость связи файла с версией договорного предложения.

### Фрагмент 14 — расширяемость

Разделение ответственности позволяет изменять поведение системы локально. Бизнес-правила изменяются в domain/application слоях, пользовательский интерфейс отвечает за отображение, а инфраструктура может развиваться за отдельной границей.

## 21. Итоговая формула темы

```text id="l3wo1y"
разделение frontend и backend нужно,
чтобы пользовательский интерфейс не становился источником бизнес-правил;

frontend отвечает за отображение,
ввод данных,
локальные состояния,
кнопки,
подсказки,
action availability
и показ результата;

backend API принимает запросы,
проверяет авторизацию,
проверяет форму запроса,
возвращает результат или ошибку
и передаёт действие в application layer;

application layer координирует пользовательский сценарий:
проверяет доступ,
загружает данные,
проверяет принадлежность,
вызывает domain layer,
сохраняет результат
и формирует ответ;

domain layer содержит основную бизнес-логику:
состояния заявки,
допустимые переходы,
инварианты,
правила рассмотрения,
решения и договорного обмена;

frontend validation является подсказкой,
а не бизнес-гарантией;

похожая проверка на разных уровнях
не всегда является плохим дублированием:
frontend отвечает за удобство,
application layer — за безопасность сценария,
domain layer — за корректность предметного состояния;

read API готовит данные для экранов,
включая compact DTO и available actions;

command API меняет состояние
и должен проходить через application layer и domain layer;

DTO ответа не равен domain model:
frontend получает только данные,
нужные конкретному экрану или сценарию;

ошибки должны быть структурированы:
errorCode,
message,
fieldErrors,
status/type,
чтобы frontend не зависел от текста сообщения;

mock-проверка данных является вспомогательной информацией,
но не принимает решение за сотрудника;

работа с файлами делится на upload и download:
frontend выбирает или запрашивает файл,
backend сохраняет или выдаёт файл после проверки доступа,
domain layer знает только предметную связь document ref с proposal;

такое разделение делает бизнес-логику более ясной,
локализованной,
тестируемой
и расширяемой без переписывания кода во множестве мест.
```

Главные изменения v2: добавлены `read API / command API`, `DTO ≠ domain model`, `action availability`, structured errors, различение `401/403/404`, frontend validation как подсказка, усиление mock-проверки и отдельное разделение upload/download file flows.
