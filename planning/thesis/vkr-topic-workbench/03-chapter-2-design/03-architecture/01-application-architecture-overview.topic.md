## 2. Что это за тема

Эта тема открывает пункт **2.3 “Проектирование архитектуры web-приложения”** и объясняет, из каких крупных частей состоит проектируемая система.

Предыдущие темы 2.1–2.2 отвечали на вопросы:

```text
кто участвует в системе;
какие сценарии выполняются;
какие предметные понятия нужны;
как меняется состояние заявки;
как устроен договорный обмен.
```

Текущая тема отвечает на вопрос:

```text
как web-приложение должно быть архитектурно устроено,
чтобы поддержать роли, сценарии, предметную модель и жизненные циклы.
```

Главная мысль:

> Архитектура web-приложения выводится из пользовательских сценариев. Клиент создаёт заявителя и заявку, сотрудник рассматривает заявку, заявка меняет состояние, после одобрения возможен договорный обмен, а frontend, backend API, application layer, domain layer, база данных и файловое хранилище обеспечивают выполнение этой цепочки. При этом основная бизнес-логика концентрируется в независимом domain layer, не загрязняется деталями UI, HTTP, БД и файлового хранения, что упрощает тестирование, понимание и дальнейшее изменение поведения системы.

## 3. Важное уточнение: архитектура ≠ реализационный отчёт

В этой теме нужно описывать **проектную архитектуру**, а не конкретную реализацию файлов, классов, endpoints и тестов.

### Как писать безопасно

```text
архитектура предусматривает;
система проектируется как web-приложение;
frontend отвечает за пользовательские сценарии;
backend API задаёт серверную границу;
application layer координирует пользовательские сценарии;
domain layer содержит основную бизнес-логику;
предметная модель задаёт правила и допустимые состояния;
БД хранит структурированные данные и метаданные;
файловое хранилище хранит прикреплённые файлы;
подробные API-flow раскрываются в 2.5;
реализация и тестирование раскрываются в главе 3.
```

### Как не писать в 2.3.1

```text
конкретный endpoint возвращает;
класс X вызывает класс Y;
миграция создаёт таблицу;
тест проверяет сценарий;
компонент React называется так-то;
controller реализует такой-то метод;
конкретный путь в файловой системе такой-то;
система построена строго по Clean Architecture;
полностью реализован DDD;
реализованы все сценарии договорного обмена.
```

### Отдельная правка по тону

Не писать:

```text
часть архитектуры не доделана;
часть находится в планируемой зоне;
старый код мешает текущей реализации;
реализовано не полностью;
legacy ломает архитектуру.
```

Писать так:

```text
архитектура допускает поэтапное развитие;
отдельные сценарии могут уточняться без изменения всей системы;
поведение можно изменять на уровне application layer и domain layer;
внешние интеграции подключаются как точки расширения;
текущая архитектурная линия отделяется от исторических решений;
реализация конкретных элементов рассматривается в главе 3.
```

## 4. Принятые уточнения

1. Глава 2 является проектной главой.
2. Тема 2.3 должна объяснять архитектуру, а не код.
3. Архитектура выводится из сценариев и предметной модели.
4. Основная форма системы — клиент-серверное web-приложение.
5. В архитектуре выделяются frontend, backend API, application layer, domain layer, база данных и файловое хранилище.
6. Термин `application layer` использовать можно, но его нужно объяснять как слой координации пользовательских сценариев.
7. Термин `domain layer` использовать можно, но его нужно объяснять как независимый слой предметной бизнес-логики.
8. Не заменять `application layer` и `domain layer` полностью громоздкими русскими терминами.
9. Frontend отвечает за пользовательский интерфейс и запуск действий пользователем.
10. Backend API отвечает за серверную границу взаимодействия frontend/backend.
11. Application layer отвечает за координацию сценариев: проверку доступа, загрузку данных, вызов domain layer, сохранение результата и подготовку ответа.
12. Domain layer отвечает за основную бизнес-логику, инварианты, состояния и допустимые переходы.
13. Domain layer должен быть независим от UI, HTTP, БД, файлового хранения и внешних интеграций.
14. Независимость domain layer нужна не только для unit-тестов, но и для ясности, локализации и расширяемости бизнес-логики.
15. База данных хранит структурированные данные и метаданные.
16. Файловое хранилище хранит физические файлы договорных предложений.
17. Физическое содержимое файла не является частью domain layer; в предметной модели хранится ссылка/метаданные.
18. API между frontend и backend подробнее раскрывается в 2.5.
19. UI-flow подробнее раскрывается в 2.6.
20. Детальная реализация, код и тесты раскрываются в главе 3.
21. OpenAPI, generated constants и ProblemDetails можно упоминать как архитектурные механизмы согласования frontend/backend, но подробно раскрывать в 2.5.
22. Валидация должна быть разделена по уровням: frontend validation, server request validation, application/domain validation.
23. Архитектура должна показывать не только компоненты, но и возможность локально менять поведение сценариев.
24. Элементы DDD можно раскрывать мягко: предметные объекты, жизненные циклы, инварианты и независимость domain layer.
25. Не писать “система полностью построена по DDD” или “Clean Architecture”, если это не нужно защищать отдельно.
26. Сценарные архитектурные срезы можно упоминать как способ проектирования и проверки поведения, но не строить на L1/L2/L3 структуру ВКР.
27. Email/push, ЭП, ЭДО, полноценная СЭД, промышленный object storage и внешние интеграции не заявляются как реализованные функции.
28. `planning/use-cases.md` использовать как сценарную карту, но нормализовать старые элементы.
29. Исторические решения и текущую архитектурную линию описывать нейтрально: через архитектурную эволюцию и устойчивые границы, а не через “недоделанность”.

## 5. Сценарная основа архитектуры

Архитектура должна поддерживать не абстрактный сайт, а конкретные пользовательские сценарии.

Из сценариев берём смысловую основу:

```text
регистрация и авторизация;
работа клиента в личном кабинете;
создание заявителя;
подача заявки;
просмотр своих заявок;
просмотр заявок сотрудником;
рассмотрение заявки;
одобрение или отклонение;
переход к договорному этапу;
обмен версиями договорного предложения.
```

Из старого `planning/use-cases.md` не переносим буквально:

```text
L1/L2/L3 как структуру ВКР;
Submitted / InReview / ContractDraftSent без repo-check;
ContractDraft как текущую модель договора;
email как обязательную реализованную функцию;
автоматическое создание проекта договора;
PDF-генерацию договора без repo-check.
```

Нормализация сценариев для архитектуры:

| Старый сценарный элемент  | Архитектурная интерпретация сейчас                              |
| ------------------------- | --------------------------------------------------------------- |
| Регистрация / авторизация | frontend forms + backend access control                         |
| Создание заявителя        | сценарий клиента, данные в БД                                   |
| Подача заявки             | frontend form + backend scenario + domain rule + БД             |
| Просмотр заявок           | UI list + API read model + БД                                   |
| Взять / начать обработку  | сценарий сотрудника + application layer rule                    |
| Одобрить / отклонить      | сценарий сотрудника + изменение состояния заявки в domain layer |
| Mock-проверка             | демонстрационная проверка данных / точка расширения backend     |
| Создать проект договора   | нормализовать в договорный обмен                                |
| Версионирование договора  | обмен версиями договорного предложения                          |
| Email                     | future work / не заявлять без repo-check                        |

Рабочая формулировка:

> Архитектура проектируется с учётом пользовательских сценариев: клиентские сценарии требуют личного кабинета и форм ввода, сценарии сотрудника требуют рабочей зоны обработки заявок, а договорный обмен требует связи между заявкой, версиями предложений, метаданными документа и файловым хранилищем. Поэтому архитектура должна поддерживать не отдельные экраны, а целостные сценарии изменения состояния предметных объектов.

## 7. Содержание темы

### 7.1 Общий архитектурный подход

Система проектируется как web-приложение с клиент-серверной архитектурой.

Основные части:

```text
frontend;
backend API;
application layer;
domain layer;
база данных;
файловое хранилище.
```

Рабочая формулировка:

> Проектируемая система имеет клиент-серверную архитектуру. Пользователь взаимодействует с web-интерфейсом, frontend отправляет запросы к backend API, серверная часть выполняет сценарии через application layer, обращается к domain layer для применения бизнес-правил и сохраняет данные в базе данных или файловом хранилище.

---

### 7.2 Frontend

Frontend обеспечивает взаимодействие пользователя с системой.

Он нужен для:

```text
отображения страниц и форм;
регистрации и входа;
личного кабинета клиента;
рабочей зоны сотрудника;
создания заявителя;
подачи заявки;
просмотра статуса и результата;
отображения договорного обмена;
загрузки или выбора файла, если это предусмотрено UI;
отображения ошибок и доступных действий.
```

Что frontend не должен делать как единственный источник истины:

```text
окончательно проверять права доступа;
самостоятельно менять состояние заявки без backend;
хранить бизнес-данные как source of truth;
считать договор юридически подписанным;
решать за сотрудника;
содержать основные бизнес-инварианты предметной области.
```

Рабочая формулировка:

> Frontend отвечает за пользовательское взаимодействие: отображение экранов, ввод данных, запуск действий и показ результата. При этом окончательная проверка прав и изменение состояния предметных объектов выполняются на серверной стороне.

---

### 7.3 Backend API

Backend API является серверной границей для frontend.

Он нужен для:

```text
приёма запросов от frontend;
проверки авторизации;
маршрутизации запроса к нужному сценарию;
возврата результата frontend;
возврата ошибок в едином формате;
отделения UI от серверной логики.
```

Рабочая формулировка:

> Backend API принимает запросы от frontend и является серверной границей выполнения пользовательских сценариев. Он не должен подменять всю предметную модель, но отвечает за вход в серверную часть, проверку доступа и передачу действия в application layer.

---

### 7.4 Application layer

Application layer координирует выполнение пользовательских сценариев.

Он нужен для:

```text
создания заявителя;
создания заявки;
начала рассмотрения;
проверки данных заявки;
одобрения заявки;
отклонения заявки;
начала договорного обмена;
отправки версии договорного предложения;
принятия предложения или отправки встречной версии, если подтверждено моделью.
```

Application layer связывает:

```text
API-запрос;
проверку доступа;
загрузку нужных данных;
проверку допустимости действия;
вызов domain layer;
сохранение результата;
ответ frontend.
```

Рабочая формулировка:

> Application layer выполняет координацию пользовательских сценариев. Например, при одобрении заявки серверная часть должна проверить право сотрудника, получить заявку, убедиться, что действие допустимо для текущего состояния, зафиксировать решение и сохранить изменения. Такая координация относится к application layer, а не к frontend, базе данных или файловому хранилищу.

Осторожность:

```text
не перечислять конкретные классы;
не писать названия handlers без repo-check;
не превращать это в главу 3;
не использовать DDD-термины, если они перегружают текст.
```

---

### 7.4.1 Application layer и транзакционная граница сценария

Application layer удобен для описания сценария как единой операции.

Сценарий может включать:

```text
проверку доступа;
загрузку нескольких объектов;
проверку принадлежности данных пользователю;
вызов методов domain layer;
сохранение изменений;
возврат результата или ошибки;
обеспечение отсутствия частичной записи при ошибке.
```

Рабочая формулировка:

> Application layer связывает пользовательское действие с несколькими архитектурными элементами: проверкой доступа, загрузкой нужных данных, применением предметных правил, сохранением результата и возвратом ответа frontend. Благодаря этому HTTP-детали не смешиваются с предметными правилами, а бизнес-логика не размазывается по контроллерам и UI-компонентам.

---

### 7.5 Независимый domain layer

Domain layer содержит основную бизнес-логику приложения.

Он должен быть независим от:

```text
frontend;
HTTP-запросов;
DTO;
контроллеров;
БД;
ORM;
файлового хранилища;
внешних интеграций;
конкретных UI-состояний.
```

Domain layer нужен для:

```text
правил изменения состояния заявки;
условий начала рассмотрения;
условий одобрения или отклонения;
связи решения с заявкой;
условий перехода к договорному обмену;
правил работы с версиями договорного предложения;
инвариантов, предотвращающих некорректные состояния.
```

Рабочая формулировка:

> В серверной части выделяется domain layer, независимый от пользовательского интерфейса, HTTP-слоя, базы данных и файлового хранения. Такая модель содержит основную бизнес-логику приложения: правила изменения состояния заявки, условия принятия решения и ограничения договорного обмена. Благодаря этому бизнес-логика не загрязняется деталями отображения, передачи данных и хранения.

---

### 7.6 Элементы DDD без перегруза

В тексте ВКР не нужно доказывать, что проект “использует DDD” как отдельную самоцель.

Корректнее писать:

```text
при проектировании предметной части используются элементы DDD;
выделяются предметные объекты;
у объектов есть жизненные циклы;
бизнес-правила размещаются рядом с объектом, который владеет состоянием;
некорректные состояния предотвращаются инвариантами;
изменение состояния выполняется через контролируемые сценарии.
```

Не нужно глубоко раскрывать:

```text
bounded context;
aggregate theory;
eventual consistency;
domain events;
outbox;
ORM purity;
сложные DDD-паттерны;
теоретические детали Khorikov/Vernon.
```

Рабочая формулировка:

> Для проектирования предметной части используются элементы Domain-Driven Design: выделение предметных объектов, жизненных циклов и инвариантов. DDD здесь не является самостоятельной темой главы, а используется как способ объяснить, почему заявка, заявитель, рассмотрение и договорный обмен выделяются в модели и почему бизнес-правила изменения состояния размещаются на серверной стороне в domain layer.

---

### 7.7 Domain layer и unit-тестируемость

Независимость domain layer позволяет проверять бизнес-правила быстрыми unit-тестами.

Что можно тестировать быстро:

```text
создание заявки;
переход заявки к рассмотрению;
запрет некорректного перехода;
одобрение после начала рассмотрения;
отклонение после начала рассмотрения;
запрет повторного решения;
невозможность договорного обмена до одобрения;
правила отправки версии договорного предложения;
инварианты отправителя версии.
```

Рабочая формулировка:

> Независимость domain layer позволяет проверять бизнес-правила быстрыми unit-тестами без запуска frontend, HTTP-сервера, базы данных и файлового хранилища. Такие тесты дешевле в поддержке, потому что проверяют не весь технический стек, а конкретные правила предметной области.

Но важно: тестируемость — не единственный плюс.

Рабочая формулировка:

> Преимущество независимого domain layer не ограничивается возможностью написать большое количество unit-тестов. Более важным является то, что бизнес-логика становится явной, локализованной и защищённой от внешних технических факторов. Изменение правил заявки или договорного обмена не требует поиска условий по контроллерам, UI-компонентам, SQL-запросам и инфраструктурному коду.

### 7.8 База данных / persistence

База данных используется для структурированных данных.

В ней должны храниться:

```text
учётные записи и роли, если подтверждено repo;
заявители;
заявки;
текущее состояние предметных объектов;
рассмотрения;
решения;
договорные обмены;
версии договорного предложения;
метаданные документов;
связи между объектами.
```

Рабочая формулировка:

> База данных хранит текущее состояние предметных объектов и данные, необходимые для восстановления процесса: сведения о заявителях, заявках, рассмотрении, решениях, договорном обмене и метаданных документов.

Осторожность:

```text
точные таблицы не раскрывать здесь;
поля не перечислять без repo-check;
подробную модель данных оставить для 2.4;
миграции и ORM оставить для главы 3.
```

---

### 7.9 Файловое хранилище

Файловое хранилище используется для физических файлов договорных предложений.

Важно разделять:

```text
метаданные документа — в БД;
физический файл — в файловом хранилище;
ссылка/ключ файла связывает эти уровни.
```

Рабочая формулировка:

> Физическое содержимое файла не является частью предметной сущности. В предметной модели хранится ссылка и метаданные документа, а сам файл размещается отдельно в файловом хранилище.

Осторожность:

```text
не заявлять промышленный object storage;
не заявлять полноценную СЭД;
не описывать полный аудит файловых операций;
не писать конкретные пути хранения в 2.3.
```

### 7.10 API-контракт как архитектурная граница

API-контракт отделяет frontend от backend и делает взаимодействие между ними явным.

В 2.3 достаточно раскрыть архитектурную роль API-контракта:

```text
frontend не обращается напрямую к БД;
frontend взаимодействует с backend через API;
API задаёт границу между UI и серверной логикой;
структурная часть контракта описывает запросы, ответы и DTO;
семантическая часть помогает единообразно обрабатывать ошибки, поля и служебные коды;
подробные API-группы раскрываются в 2.5.
```

Можно осторожно упомянуть:

```text
OpenAPI;
generated constants;
ProblemDetails.
```

Рабочая формулировка:

> API-контракт нужен не только для передачи данных, но и для согласования frontend и backend. Структурная часть контракта описывает запросы и ответы, а семантическая часть помогает frontend одинаково понимать коды ошибок, имена полей валидации и служебные расширения ответа.

### 7.11 Обработка ошибок и обратная связь

На архитектурном уровне нужно показать, что система должна возвращать понятный результат действий.

Примеры:

```text
ошибка авторизации;
ошибка доступа;
ошибка валидации;
заявка не найдена;
действие недоступно для текущего состояния;
файл не найден;
ошибка загрузки файла.
```

Рабочая формулировка:

> Архитектура должна предусматривать единый подход к ошибкам и обратной связи, чтобы frontend мог корректно показывать пользователю результат выполнения действия или причину невозможности его выполнить.

Подробно:

```text
формат ошибок → 2.5;
UI-состояния ошибок → 2.6;
реализация обработки ошибок → глава 3.
```

---

### 7.12 Граница валидации

Валидация на архитектурном уровне разделяется на несколько уровней:

```text
frontend validation;
server request validation;
application/domain validation.
```

Смысл разделения:

```text
frontend помогает пользователю исправить ввод;
backend API проверяет форму запроса и обязательные поля;
application layer проверяет существование объектов, права доступа и принадлежность данных;
domain layer проверяет допустимость изменения состояния и бизнес-инварианты.
```

Рабочая формулировка:

> Валидация не должна быть сосредоточена только во frontend. Интерфейс может подсказать пользователю ошибку ввода, но серверная часть должна проверить форму запроса, права доступа, принадлежность данных и допустимость изменения состояния предметного объекта.

Дополнительная формулировка:

> Такое разделение позволяет не делать frontend единственным источником правил и не смешивать форму HTTP-запроса с предметными ограничениями. Ошибки ввода, ошибки доступа и ошибки бизнес-состояния имеют разную природу и должны обрабатываться на соответствующих уровнях архитектуры.

### 7.13 Архитектура как поддержка вертикальных пользовательских сценариев

Система проектируется не только по техническим слоям, но и по пользовательским сценариям.

Пользовательский сценарий проходит через несколько архитектурных компонентов:

```text
UI-действие
→ API-запрос
→ проверка доступа и входных данных
→ application layer
→ domain layer
→ сохранение данных / файлов
→ ответ frontend
→ отображение результата пользователю
```

Пример:

```text
Сотрудник нажимает “Одобрить заявку”
→ frontend отправляет запрос
→ backend API проверяет доступ
→ application layer загружает заявку
→ domain layer проверяет допустимость одобрения
→ результат сохраняется в БД
→ frontend показывает новый статус
```

Рабочая формулировка:

> Такой подход позволяет рассматривать систему не только как набор слоёв, но и как набор завершённых пользовательских сценариев. Каждый сценарий проходит через UI, API, application layer, domain layer и хранение, но ответственность каждого уровня остаётся разделённой.

### 7.14 Сценарные архитектурные срезы

Сценарный срез — ограниченная часть поведения, которую можно спроектировать, реализовать и проверить независимо.

Примеры сценарных срезов:

```text
регистрация клиента;
создание заявителя;
создание заявки;
начало рассмотрения;
одобрение заявки;
отклонение заявки;
начало договорного обмена;
отправка версии договорного предложения;
принятие договорного предложения.
```

Важно:

```text
сценарный срез не равен одному техническому слою;
один срез может затрагивать frontend, API, application layer, domain layer, БД и тесты;
некоторые срезы могут быть только серверными;
некоторые срезы могут быть client/server;
срезы не являются структурой ВКР;
L1/L2/L3 не использовать как названия разделов диплома.
```

Рабочая формулировка:

> Для проектирования поведения системы удобно использовать сценарные архитектурные срезы. Каждый срез связан с конкретным результатом для пользователя: например, созданием заявителя, созданием заявки или принятием решения по заявке. Срез может включать изменения в UI, API, application layer, domain layer, модели данных и тестах, но в тексте ВКР он используется не как отдельный раздел, а как способ объяснить поэтапное проектирование системы.

### 7.15 Архитектурная эволюция и заменяемость поведения

Эту мысль нужно раскрывать аккуратно: не как “в проекте есть недоделанные части”, а как архитектурное преимущество.

Архитектура должна позволять менять поведение локально:

```text
изменить сценарий рассмотрения заявки без переписывания UI целиком;
заменить демонстрационную проверку данных на внешнюю интеграцию;
расширить договорный обмен новыми действиями;
заменить простое файловое хранение на более развитое;
добавить email/push-уведомления как внешний канал;
уточнить API-контракт без смешивания UI и БД.
```

Смысл:

```text
frontend знает сценарий через API;
backend API задаёт стабильную границу;
application layer координирует поведение;
domain layer содержит правила;
storage можно развивать за отдельной границей;
внешние интеграции подключаются через отдельные точки расширения.
```

Рабочая формулировка:

> Разделение frontend, backend API, application layer, domain layer и хранения позволяет развивать систему поэтапно. Например, демонстрационную проверку данных можно заменить внешней интеграцией, а простое файловое хранение — более развитым хранилищем, не переписывая пользовательский интерфейс и предметную модель во множестве мест.

### 7.16 Текущая архитектурная линия и исторические решения

Этот блок нужен только для рабочего драфта. В финальный текст его можно сильно очистить.

Не писать как проблему:

```text
legacy-код не доделан;
часть реализации старая;
часть реализации новая;
архитектура ещё не закончена.
```

Писать как архитектурную границу:

```text
в проектном описании фиксируется целевая архитектурная линия;
исторические решения не должны подменять текущую проектную модель;
архитектура допускает поэтапное развитие сценариев;
новое поведение должно добавляться через устойчивые границы:
API, application layer, domain layer и storage boundary.
```

Рабочая формулировка:

> Для ВКР важна не история изменения кода, а итоговая проектная логика. Поэтому архитектура описывается через устойчивые границы системы: frontend, backend API, application layer, domain layer, базу данных и файловое хранилище. Такое разделение позволяет развивать отдельные сценарии без изменения всей системы.

### 7.17 Внешние интеграции и точки расширения

В текущем scope внешние интеграции не заявляются как реализованные.

Но архитектура может иметь точки расширения:

```text
внешняя проверка данных;
email/push-уведомления;
внешний ЭДО;
электронная подпись;
промышленное файловое хранилище.
```

Рабочая формулировка:

> Некоторые функции целесообразно рассматривать как направления дальнейшего развития. Например, демонстрационная проверка данных может быть заменена реальной внешней интеграцией, а системная обратная связь может быть дополнена email- или push-уведомлениями.

## 11. Независимый domain layer и тестируемость бизнес-логики

### 11.1 Что означает независимый domain layer

Независимый domain layer означает, что ключевые бизнес-правила не зависят от внешних технических факторов.

Domain layer не должен знать:

```text
как выглядит форма во frontend;
какой HTTP endpoint был вызван;
как называется DTO;
какая таблица хранит данные;
где физически лежит файл;
какой внешний сервис будет подключён позже.
```

Domain layer должен знать:

```text
какие состояния заявки допустимы;
можно ли начать рассмотрение;
можно ли одобрить заявку;
можно ли отклонить заявку;
можно ли начать договорный обмен;
кто может быть отправителем версии предложения;
какие переходы состояния запрещены.
```

Рабочая формулировка:

> Независимый domain layer позволяет сосредоточить основную бизнес-логику в предметной модели. Это уменьшает связанность между бизнес-правилами и техническими деталями, упрощает unit-тестирование и делает изменение логики менее затратным.

---

### 11.2 Почему unit-тесты важны, но не являются единственным плюсом

Unit-тесты дают возможность быстро проверить правила:

```text
без запуска frontend;
без запуска HTTP-сервера;
без подключения к БД;
без файлового хранилища;
без внешних интеграций.
```

Но главное преимущество шире:

```text
бизнес-логика становится явной;
правила не размазываются по слоям;
условия переходов легче читать;
ошибки в правилах легче локализовать;
изменения проще вносить;
расширение сценариев меньше затрагивает внешние слои.
```

Рабочая формулировка:

> Быстрые unit-тесты являются важным следствием независимости доменной модели, но не единственным преимуществом. Более значимым является то, что бизнес-логика становится явной, локализованной и защищённой от загрязнения деталями UI, HTTP, БД и файлового хранения.

---

### 11.3 Как это влияет на расширение приложения

Изоляция domain layer помогает менять поведение приложения без значительных потерь времени и усилий.

Примеры:

```text
изменить правила перехода заявки между состояниями;
добавить новое ограничение для одобрения;
уточнить правила отказа;
расширить договорный обмен новыми действиями;
заменить демонстрационную проверку внешней интеграцией;
перейти от простой директории к более развитому file storage;
добавить уведомления как внешний канал.
```

Рабочая формулировка:

> Изоляция domain layer повышает расширяемость приложения. Например, демонстрационную проверку данных можно заменить внешней интеграцией, изменить правила перехода заявки между состояниями или расширить договорный обмен новыми действиями без переписывания всей системы. Внешние факторы — интерфейс, API, база данных, файловое хранилище — подключаются к предметной модели через устойчивые границы, но не определяют её бизнес-смысл.

## 12. Архитектура как поддержка сценарных срезов

Сценарный срез связывает требования, архитектуру и проверку результата.

Пример цепочки:

```text
Требование:
сотрудник должен принять решение по заявке

Сценарий:
сотрудник открывает заявку и одобряет её

Сценарный срез:
UI-действие / API / application layer / domain rule / сохранение / тест

Результат:
заявка получает новое состояние, клиент видит результат
```

Рабочая формулировка:

> Проектирование приложения выполняется не только по техническим слоям, но и по пользовательским сценариям. Для этого используется понятие сценарного среза — ограниченной части поведения, которую можно спроектировать, реализовать и проверить независимо. Такой подход позволяет связывать требования, предметную модель, API, хранение данных, пользовательский интерфейс и тестирование вокруг конкретного результата для пользователя.

## 15. Что требует обоснования

### 15.1 Почему выбрана клиент-серверная архитектура

Она соответствует web-приложению.

Будущая формулировка:

> Клиент-серверная архитектура подходит для web-приложения, так как позволяет отделить пользовательский интерфейс от серверной логики, централизованно проверять права доступа и хранить данные в единой базе.

---

### 15.2 Почему frontend не должен содержать бизнес-логику как source of truth

Frontend может скрыть кнопку, но не должен окончательно решать доступ.

Будущая формулировка:

> Frontend отвечает за отображение доступных действий, однако окончательная проверка прав и состояния объекта должна выполняться на серверной стороне.

---

### 15.3 Почему application layer нужен отдельно от API и domain layer

API принимает запрос, а domain layer содержит бизнес-правила. Между ними нужна координация сценария.

Будущая формулировка:

> Application layer связывает пользовательское действие с проверкой доступа, загрузкой данных, применением предметных правил и сохранением результата. Это позволяет не смешивать HTTP-границу, бизнес-правила и хранение данных.

---

### 15.4 Почему domain layer должен быть независимым

Независимость нужна для ясности, тестируемости и расширяемости.

Будущая формулировка:

> Независимый domain layer позволяет сосредоточить основную бизнес-логику в предметной модели. Это уменьшает связанность между бизнес-правилами и техническими деталями, упрощает unit-тестирование и делает изменение логики менее затратным.

---

### 15.5 Почему тестируемость не единственный плюс независимого домена

Главный плюс не только в количестве тестов.

Будущая формулировка:

> Быстрые unit-тесты являются важным следствием независимости доменной модели, но не единственным преимуществом. Более значимым является то, что бизнес-логика становится явной, локализованной и защищённой от загрязнения деталями UI, HTTP, БД и файлового хранения.

---

### 15.6 Почему backend является точкой применения бизнес-правил

Серверная часть работает с данными и состояниями.

Будущая формулировка:

> Серверная часть является точкой применения бизнес-правил. Сами предметные ограничения концентрируются в domain layer, а application layer координирует их применение в рамках пользовательского сценария.

---

### 15.7 Почему данные и файлы разделяются

Структурированные данные и физические файлы имеют разную природу.

Будущая формулировка:

> Метаданные договорного документа хранятся вместе со структурированными данными, а физический файл размещается отдельно. Такое разделение упрощает связь файла с предметной моделью и не превращает базу данных в файловое хранилище.

---

### 15.8 Почему API-контракт важен архитектурно

Он отделяет UI от backend и делает взаимодействие стабильным.

Будущая формулировка:

> API-контракт задаёт устойчивую границу между frontend и backend. Благодаря этому пользовательский интерфейс может развиваться отдельно от внутренней серверной логики при сохранении согласованного формата запросов, ответов и ошибок.

---

### 15.9 Почему валидация разделяется по уровням

Разные проверки имеют разную ответственность.

Будущая формулировка:

> Разделение валидации позволяет отделить подсказки пользовательского интерфейса от серверной проверки запроса и предметных ограничений. Это снижает риск ситуации, когда бизнес-правило существует только во frontend.

---

### 15.10 Почему архитектура поддерживает изменение поведения

Сценарии могут уточняться, но не должны ломать всю систему.

Будущая формулировка:

> Разделение архитектуры на frontend, API, application layer, domain layer и хранение позволяет изменять отдельные сценарии локально. Например, замена демонстрационной проверки данных на внешнюю интеграцию требует изменения точки расширения в серверной части, но не должна приводить к переписыванию всей системы.

---

### 15.11 Почему сценарные срезы полезны

Они связывают требования и реализацию через поведение.

Будущая формулировка:

> Сценарный срез позволяет проектировать систему вокруг конкретного результата для пользователя. Это помогает связать требования, API, предметную модель, хранение данных, UI и тестирование в рамках одной проверяемой части поведения.

---

### 15.12 Почему внешние интеграции вынесены за scope

Они усложняют проект и не обязательны для демонстрации основной цепочки.

Будущая формулировка:

> Внешние интеграции рассматриваются как направления дальнейшего развития. В текущем scope достаточно показать архитектурные точки, в которых такие интеграции могут быть добавлены.

## 18. Черновые фрагменты будущего текста

### Фрагмент 1 — ввод

После определения ролей, сценариев и предметной модели необходимо описать общую архитектуру web-приложения. Архитектура показывает, какие части системы участвуют в выполнении пользовательских сценариев и как они взаимодействуют между собой.

### Фрагмент 2 — общий подход

Проектируемая система имеет клиент-серверную архитектуру. Пользователь взаимодействует с frontend-частью, которая отправляет запросы к backend API. Серверная часть выполняет проверку прав, координирует сценарии через application layer, применяет правила domain layer и сохраняет данные в базе данных или файловом хранилище.

### Фрагмент 3 — frontend

Frontend отвечает за отображение интерфейса клиента и сотрудника: формы, списки заявок, карточки заявок, статусы, результаты рассмотрения и элементы договорного обмена.

### Фрагмент 4 — backend API

Backend API образует серверную границу системы. Через него frontend передаёт действия пользователя, а серверная часть возвращает результат выполнения сценария или описание ошибки.

### Фрагмент 5 — application layer

Application layer координирует выполнение пользовательских сценариев. Он связывает входящий запрос с проверкой доступа, загрузкой данных, применением предметных правил, сохранением результата и формированием ответа.

### Фрагмент 6 — domain layer

Domain layer содержит основную бизнес-логику приложения: правила изменения состояния заявки, условия рассмотрения, ограничения одобрения и отклонения, а также правила договорного обмена. Он не зависит от пользовательского интерфейса, HTTP-слоя, базы данных и файлового хранения.

### Фрагмент 7 — DDD без перегруза

При проектировании предметной части используются элементы DDD: выделение предметных объектов, жизненных циклов и инвариантов. Это нужно не для демонстрации использования методологии, а для объяснения того, почему бизнес-правила располагаются в серверной предметной модели и не смешиваются с интерфейсом или хранением данных.

### Фрагмент 8 — данные и файлы

Структурированные данные и метаданные документов хранятся в базе данных, а физические файлы договорных предложений размещаются отдельно в файловом хранилище. Это позволяет связать файл с предметной моделью, не смешивая данные процесса и байты файла.

### Фрагмент 9 — API-контракт

API-контракт задаёт границу между frontend и backend. Он позволяет согласовать структуру запросов и ответов, а также обработку ошибок и результатов валидации.

### Фрагмент 10 — независимость домена и unit-тесты

Независимость domain layer позволяет проверять бизнес-правила быстрыми unit-тестами без запуска frontend, HTTP-сервера, базы данных и файлового хранилища. Такие тесты проверяют не техническую инфраструктуру, а правила предметной области.

### Фрагмент 11 — тестируемость не единственный плюс

Преимущество такого подхода не ограничивается тестированием. Когда бизнес-логика сосредоточена в domain layer, она становится более явной, лучше читается и проще изменяется. Изменение правил заявки или договорного обмена не требует поиска условий в UI-компонентах, контроллерах и инфраструктурном коде.

### Фрагмент 12 — архитектурная эволюция

Разделение системы на frontend, backend API, application layer, domain layer и хранилища позволяет развивать поведение системы поэтапно. Например, демонстрационная проверка данных может быть заменена внешней интеграцией без переписывания пользовательского интерфейса и хранения данных во множестве мест.

### Фрагмент 13 — границы

Проектируемая архитектура не является архитектурой полноценной СЭД или юридически значимого ЭДО. Электронная подпись, внешние уведомления, промышленное файловое хранилище и внешние интеграции рассматриваются как возможные направления развития.

### Фрагмент 14 — переход

Общая архитектура задаёт крупные компоненты системы. Далее необходимо подробнее раскрыть разделение ответственности между frontend и backend.

клиент → заявитель → заявка → рассмотрение → решение
→ договорный обмен → версия предложения → документная ссылка → файл;

при проектировании предметной части используются элементы DDD:
выделение предметных объектов, жизненных циклов и инвариантов;

domain layer проектируется независимым от UI, HTTP,
БД, файлового хранения и внешних интеграций;

это позволяет проверять бизнес-правила быстрыми unit-тестами,
но главное преимущество шире:
бизнес-логика становится явной, локализованной
и не загрязняется внешними техническими факторами;

за счёт такого разделения изменение правил заявки,
рассмотрения или договорного обмена можно выполнять локально,
без переписывания кода во множестве несвязанных мест;

API-контракт обеспечивает согласование frontend/backend,
а разделение валидации не позволяет переносить бизнес-правила только во frontend;

архитектурное разделение позволяет развивать поведение системы поэтапно:
например, заменить демонстрационную проверку внешней интеграцией
или изменить файловое хранение без переписывания пользовательского интерфейса
и предметной модели во множестве мест;

старые сценарии из planning/use-cases.md используются только как сценарная карта
и нормализуются под текущую модель;

детальные API-flow раскрываются в 2.5,
UI-flow — в 2.6,
а реализация и тестирование — в главе 3.
