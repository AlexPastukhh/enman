## 2. Что это за тема

Эта тема открывает блок **2.4 “Проектирование хранения данных и файлов”** и объясняет, как в системе должны храниться структурированные данные, метаданные документов и физические файлы договорных предложений.

Предыдущий блок 2.3 отвечал на вопрос:

```text id="ss067n"
как архитектура разделяет frontend,
backend API,
application layer,
domain layer,
БД
и файловое хранилище
```

Текущая тема отвечает на вопрос:

```text id="j2zxy2"
какие данные нужно сохранять;
что хранится в базе данных;
что хранится в файловом хранилище;
как связать файл с договорным обменом;
как storage model поддерживает сценарии,
но не управляет бизнес-поведением.
```

Главная мысль:

> Хранение данных в системе разделяется на два уровня: структурированные данные и метаданные хранятся в базе данных, а физические файлы договорных предложений размещаются отдельно в файловом хранилище. База данных фиксирует состояние процесса, document metadata связывает процесс с файлом, файловое хранилище хранит только физическое содержимое, а domain layer остаётся независимым от SQL, путей файловой системы и инфраструктурных деталей.

## 3. Важное уточнение: storage model ≠ domain layer

В предыдущем блоке был выделен независимый `domain layer`. В этой теме важно не смешать его с хранением.

### Domain layer отвечает за смысл

```text id="xyliup"
заявка;
рассмотрение;
решение;
договорный обмен;
версия договорного предложения;
отправитель версии;
допустимые переходы;
бизнес-инварианты.
```

### Storage отвечает за сохранение состояния

```text id="gczava"
таблицы;
ключи;
связи;
метаданные;
физические файлы;
путь/ключ файла;
технические поля хранения.
```

Безопасная формулировка:

> Domain layer определяет бизнес-смысл объектов и допустимые изменения состояния, а storage layer сохраняет текущее состояние этих объектов и связанные с ними метаданные. Поэтому модель хранения должна поддерживать предметную модель, но не подменять её.

## 4. Принятые уточнения

1. В системе есть структурированные данные, метаданные документов и физические файлы.
2. Структурированные данные хранятся в БД.
3. Метаданные файла хранятся в БД.
4. Физический файл хранится отдельно в файловом хранилище.
5. По текущему scope физическое хранение можно описывать как простое хранение в директории.
6. SQL Server можно использовать как рабочее предположение, но точные настройки нужно проверить по repo.
7. Storage model поддерживает сценарии, но не управляет ими.
8. БД хранит результат бизнес-переходов, но не объясняет смысл этих переходов.
9. Бизнес-правила переходов относятся к `domain layer`.
10. Storage должен поддерживать как команды изменения состояния, так и чтение данных для UI.
11. Для чтения могут использоваться read DTO, projections или модели чтения.
12. Read DTO не должен подменять domain model.
13. Связи `ClientAccount → ApplicantParty → ConnectionRequest` нужны не только для навигации, но и для access scope.
14. Backend должен иметь возможность определить, относится ли заявка, договорный обмен, версия предложения или файл к текущему пользователю.
15. Файл не является source of truth для состояния договорного обмена.
16. Файл является приложением к версии договорного предложения.
17. Версия договорного предложения и physical file — разные понятия.
18. Новая версия предложения должна создаваться через domain/application сценарий, а не простой перезаписью файла.
19. После отправки версии связанный файл целесообразно рассматривать как неизменяемое приложение к этой версии.
20. `AgreementDocumentRef` или аналогичная metadata-модель нужна как boundary между domain и file system.
21. Domain layer может знать о документной ссылке, но не должен знать storage path или file bytes.
22. Backend контролирует согласованность metadata и physical file.
23. Файл без metadata не является документом процесса.
24. Metadata без physical file должна обрабатываться как ошибка согласованности или отсутствующий файл.
25. Не заявлять полноценную СЭД.
26. Не заявлять юридически значимый ЭДО.
27. Не заявлять электронную подпись.
28. Не заявлять промышленный object storage как часть текущего scope.
29. Не заявлять полный аудит файловых операций.
30. Не писать, что файл “является договором, подписанным в системе”.
31. Лучше писать “файл договорного предложения” или “прикреплённый документ”.
32. Точные таблицы, поля, индексы и миграции раскрывать осторожно и после repo-check.
33. Глава 2 описывает проектирование, а не конкретные migration files.
34. Реализация ORM, миграций и физической файловой директории подробнее относится к главе 3.

## 5. Сценарная основа хранения

Хранение данных должно поддерживать не абстрактную БД, а конкретные сценарии приложения.

Основные сценарии, которые требуют хранения:

```text id="vbicq6"
клиент создаёт учётную запись;
клиент создаёт заявителя;
клиент создаёт заявку;
клиент просматривает свои заявки;
сотрудник просматривает заявки;
сотрудник начинает рассмотрение;
сотрудник выполняет проверку данных;
сотрудник одобряет или отклоняет заявку;
сохраняется причина отказа при наличии;
после одобрения сотрудник начинает договорный обмен;
сторона отправляет версию договорного предложения;
к версии прикрепляется файл;
клиент и сотрудник видят версии договорного предложения.
```

Для хранения это означает:

```text id="ieh0ie"
нужно хранить заявителей;
нужно хранить заявки;
нужно хранить состояние заявки;
нужно хранить связь заявки с рассмотрением;
нужно хранить результат решения;
нужно хранить причину отказа, если она указана;
нужно хранить договорный обмен;
нужно хранить версии договорного предложения;
нужно хранить отправителя версии;
нужно хранить метаданные документа;
нужно хранить связь metadata с физическим файлом;
нужно хранить связи, позволяющие проверять доступ.
```

Нормализация старых use-cases:

| Старый сценарный элемент         | Как трактовать в модели хранения                                                                          |
| -------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `ContractDraft`                  | не использовать как актуальную сущность без repo-check; заменить на договорный обмен / версию предложения |
| `ContractDraftSent`              | не использовать как статус без repo-check                                                                 |
| Email                            | не включать в обязательную модель хранения                                                                |
| PDF generation                   | не включать без repo-check                                                                                |
| L1/L2/L3                         | не использовать как структуру хранения                                                                    |
| Автоматическое создание договора | заменить на связь одобренной заявки с договорным обменом, который начинает сотрудник                      |

Рабочая формулировка:

> Модель хранения проектируется от сценариев: каждый пользовательский сценарий должен оставлять в системе необходимые данные для отображения состояния, проверки доступа и продолжения процесса. Поэтому в БД сохраняются структурированные данные процесса, а файлы договорных предложений выносятся в отдельное файловое хранилище.

## 7. Содержание темы

### 7.1 Общий подход к хранению

В системе нужно разделить:

```text id="vl56vx"
структурированные данные;
метаданные документов;
физические файлы.
```

Структурированные данные:

```text id="19xjpf"
учётные записи;
роли;
заявители;
заявки;
состояния;
рассмотрения;
решения;
договорные обмены;
версии предложений;
связи между объектами.
```

Метаданные документов:

```text id="p45bf7"
имя файла;
тип файла, если сохраняется;
размер файла, если сохраняется;
ключ или путь хранения;
дата загрузки;
отправитель или загрузивший пользователь, если сохраняется;
связь с версией предложения;
служебные сведения для доступа.
```

Физические файлы:

```text id="bfdbn2"
прикреплённые файлы договорных предложений;
файлы встречных версий;
файлы, связанные с конкретной версией предложения.
```

Рабочая формулировка:

> В проектируемой системе структурированные данные и метаданные документов сохраняются в базе данных, а физические файлы размещаются отдельно в файловом хранилище. Это позволяет хранить состояние процесса в БД, не смешивая его с байтами файлов.

---

### 7.2 Хранение как поддержка сценариев, а не источник поведения

Модель хранения должна обеспечивать возможность восстановить состояние процесса, но не должна сама определять бизнес-поведение системы.

Пример:

```text id="6jco8w"
В БД может быть сохранено:
RequestStatus = Approved

Но смысл перехода в Approved определяется не БД,
а domain layer:
- заявка может быть одобрена только из допустимого состояния;
- рассмотрение должно быть начато;
- решение фиксируется сотрудником;
- после решения заявка становится финальной.
```

Рабочая формулировка:

> Модель хранения фиксирует состояние объектов после выполнения сценариев, но не должна подменять предметную модель. Правила переходов заявки, рассмотрения и договорного обмена относятся к domain layer, а БД сохраняет результат применения этих правил.

---

### 7.3 Хранение для команд и для чтения

Одна и та же БД используется для двух разных задач:

```text id="vzdujq"
1. Сохранение состояния после команд.
2. Получение данных для экранов и списков.
```

Команды требуют восстановления предметных объектов:

```text id="a32xgm"
создать заявку;
начать рассмотрение;
одобрить заявку;
отклонить заявку;
начать договорный обмен;
отправить версию предложения.
```

Чтение требует удобных представлений:

```text id="foyg1f"
мои заявки;
дашборд сотрудника;
детали заявки;
история версий договорного предложения;
доступные действия;
сведения о файлах версии.
```

Рабочая формулировка:

> Модель хранения должна поддерживать как изменение состояния, так и получение данных для интерфейса. Для команд backend восстанавливает нужные предметные объекты и применяет правила domain layer. Для списков и карточек могут использоваться модели чтения, которые объединяют данные в форме, удобной для frontend.

---

### 7.4 База данных как хранилище структурированного состояния

База данных нужна для хранения состояния процесса.

В БД должны храниться:

```text id="d5w6pp"
кто является клиентом;
какой заявитель создан клиентом;
какая заявка создана;
в каком состоянии находится заявка;
начато ли рассмотрение;
какое решение принято;
есть ли причина отказа;
начат ли договорный обмен;
какие версии предложения отправлены;
кто отправил версию;
какой документ связан с версией.
```

Рабочая формулировка:

> База данных хранит структурированное состояние системы: сведения о пользователях, заявителях, заявках, рассмотрении, решениях, договорном обмене и метаданных документов. Это состояние используется backend для проверки доступа, выполнения сценариев и отображения актуальной информации во frontend.

---

### 7.5 Данные доступа и принадлежности

Модель хранения должна позволять backend проверять, какие данные доступны текущему пользователю.

Для клиентских сценариев важны связи:

```text id="2tm70m"
ClientAccount → ApplicantParty
ApplicantParty → ConnectionRequest
ConnectionRequest → AgreementProposalExchange
AgreementProposalExchange → AgreementProposal
AgreementProposal → AgreementDocumentRef
```

Эти связи нужны для проверки:

```text id="q844my"
клиент видит только свои заявки;
клиент видит только договорные обмены по своим заявкам;
клиент получает только файлы, относящиеся к его заявкам;
сотрудник выполняет действия только в рамках сотруднической зоны;
файл можно получить только через доступный договорный обмен или заявку.
```

Рабочая формулировка:

> Связи между учётной записью, заявителем, заявкой и договорным обменом нужны не только для навигации по данным, но и для проверки доступа. Backend должен иметь возможность определить, относится ли заявка, версия предложения или файл к текущему пользователю.

---

### 7.6 Основные группы данных

Логически данные можно разделить на несколько групп.

```text id="m3yuq9"
1. Пользователи и роли.
2. Заявители.
3. Клиентские заявки.
4. Рассмотрение и решение.
5. Договорный обмен.
6. Версии договорного предложения.
7. Метаданные документов.
8. Физические файлы.
```

Рабочая формулировка:

> Для проектирования хранения данные системы целесообразно разделить на группы: пользовательские данные, сведения о заявителях, заявки, данные рассмотрения, договорный обмен, версии предложений и документные метаданные.

---

### 7.7 Пользователи и роли

Эта группа нужна для разграничения сценариев клиента и сотрудника.

Хранить нужно:

```text id="9hedad"
учётную запись пользователя;
роль или тип пользователя;
связь клиента с заявителями и заявками;
связь сотрудника с действиями рассмотрения, если это подтверждено моделью.
```

Осторожность:

```text id="2kx7pe"
не раскрывать конкретную схему Identity без repo-check;
не утверждать сложную матрицу ролей;
не утверждать, что сотрудник видит все заявки;
не утверждать точную модель назначения сотрудника.
```

Рабочая формулировка:

> Пользовательские данные и роли используются для разграничения клиентских и сотруднических сценариев. На уровне хранения важно обеспечить возможность связать действия пользователя с его ролью и доступными объектами.

---

### 7.8 Заявитель

Заявитель хранит предметные данные, используемые при подаче заявки.

Возможный repo-term:

```text id="u03tqi"
ApplicantParty
```

Хранить нужно:

```text id="pr9elp"
идентификатор заявителя;
связь с клиентом;
основные данные заявителя;
служебные даты создания/обновления, если есть;
признак актуальности, если есть.
```

Что проверить:

```text id="8gbyj0"
один клиент может иметь одного или нескольких заявителей;
создаётся ли заявитель отдельно от заявки;
какие поля заявителя реально есть;
как заявитель связан с заявкой.
```

Рабочая формулировка:

> Заявитель хранится отдельно от учётной записи клиента, поскольку заявитель отражает предметные данные, используемые в заявке, а учётная запись отвечает за доступ к системе.

---

### 7.9 Клиентская заявка

Заявка — центральный объект хранения.

Возможный repo-term:

```text id="ig6ayh"
ConnectionRequest
```

Хранить нужно:

```text id="gsd7ze"
идентификатор заявки;
связь с клиентом или заявителем;
данные заявки;
текущее состояние;
дату создания;
результат рассмотрения, если хранится в заявке;
связь с рассмотрением;
связь с договорным обменом после одобрения.
```

Рабочая формулировка:

> Клиентская заявка является центральным объектом хранения. Именно через неё связываются заявитель, рассмотрение, решение и дальнейший договорный обмен.

Осторожность:

```text id="yuqd76"
точные статусы не перечислять без repo-check;
не утверждать наличие черновика заявки;
не утверждать возможность редактирования после подачи;
не утверждать автоматическое создание договорного обмена.
```

---

### 7.10 Рассмотрение и решение

Рассмотрение фиксирует обработку заявки сотрудником.

Возможный repo-term:

```text id="p5pr7i"
RequestReview
```

Хранить нужно:

```text id="irwhnp"
связь рассмотрения с заявкой;
сотрудника, если модель это фиксирует;
факт начала рассмотрения;
результат решения;
причину отказа при наличии;
время решения, если хранится;
текущее состояние рассмотрения, если оно есть.
```

Особенность по причине отказа:

```text id="vkyvjr"
причина отказа может быть пустой;
но сам результат отказа должен быть понятен клиенту;
точную обязательность поля проверить по repo.
```

Рабочая формулировка:

> Данные рассмотрения нужны для фиксации обработки заявки сотрудником. Результатом рассмотрения является решение: одобрение или отклонение, при этом причина отказа может быть сохранена при наличии.

---

### 7.11 Договорный обмен

Договорный обмен возникает после одобрения заявки и связывается с ней.

Возможный repo-term:

```text id="32zah2"
AgreementProposalExchange
```

Хранить нужно:

```text id="p6be4v"
идентификатор обмена;
связь с одобренной заявкой;
текущее состояние обмена, если оно есть;
дату начала;
участников обмена;
связь с версиями договорного предложения.
```

Рабочая формулировка:

> Договорный обмен хранится как отдельный блок данных, связанный с одобренной заявкой. Это позволяет отделить жизненный цикл заявки от обмена версиями договорного предложения.

Осторожность:

```text id="5gwi5p"
не писать “договор подписан”;
не писать “юридически значимый обмен”;
не писать “ЭДО”;
не утверждать точные статусы без repo-check.
```

---

### 7.12 Версия договорного предложения и файл — разные понятия

Версия договорного предложения — это предметный объект обмена.

Возможный repo-term:

```text id="xyn6zc"
AgreementProposal
```

Версия может иметь:

```text id="f1fuqj"
идентификатор;
связь с договорным обменом;
отправителя;
дату отправки;
статус версии, если он есть;
комментарий, если он есть;
связь с документной ссылкой.
```

Файл — это физическое содержимое документа, приложенное к версии.

Нельзя считать, что:

```text id="98qkic"
новый файл автоматически равен новой версии;
новое имя файла определяет статус версии;
замена файла равна изменению версии;
файл сам определяет, активна версия или нет.
```

Рабочая формулировка:

> Версия договорного предложения и физический файл не являются одним и тем же объектом. Версия имеет предметный смысл в договорном обмене, а файл является документным приложением к этой версии.

---

### 7.13 Файл как приложение к процессу, а не источник состояния

Физический файл договорного предложения не должен быть источником состояния договорного обмена.

Состояние обмена хранится в структурированных данных:

```text id="og8ec7"
какая версия активна;
кто отправил версию;
когда версия отправлена;
принята ли версия;
заменена ли встречным предложением;
с каким document metadata связана версия.
```

Файл содержит содержимое предложения, но не должен сам определять:

```text id="wrtwz0"
активна ли версия;
принята ли версия;
кто имеет доступ;
можно ли отправить встречное предложение;
какой статус у договорного обмена.
```

Рабочая формулировка:

> Файл договорного предложения является приложением к версии предложения, но не источником состояния процесса. Состояние договорного обмена должно храниться в структурированной форме, чтобы backend мог проверять доступ, отображать текущую версию и применять правила domain layer.

---

### 7.14 Документная ссылка и метаданные файла

Документная ссылка связывает версию договорного предложения с физическим файлом.

Возможный repo-term:

```text id="8giplg"
AgreementDocumentRef
```

Хранить нужно:

```text id="wfeqw7"
идентификатор metadata-записи;
связь с версией предложения;
исходное имя файла;
внутреннее имя или ключ хранения;
тип содержимого, если сохраняется;
размер файла, если сохраняется;
дату загрузки;
загрузившего пользователя, если сохраняется;
путь/ключ физического файла;
служебные данные доступа.
```

Рабочая формулировка:

> В базе данных хранится не сам файл, а ссылка на него и метаданные. Такая запись позволяет связать физический файл с конкретной версией договорного предложения и сохранить контекст его появления в системе.

---

### 7.15 Metadata как граница между domain и file system

Document metadata выполняет роль границы между предметной моделью и физическим хранением.

Domain layer работает с понятием:

```text id="a5rcko"
DocumentRef;
документная ссылка;
наличие документа у версии;
связь версии с документом.
```

Storage layer знает технические детали:

```text id="9rs47s"
storage key;
path;
content type;
file size;
original file name;
physical location.
```

Рабочая формулировка:

> Document metadata отделяет предметный смысл документа от технического способа его хранения. Благодаря этому версия договорного предложения может ссылаться на документ, не зная, находится ли физический файл в директории, объектном хранилище или другой инфраструктуре.

---

### 7.16 Физическое файловое хранилище

Физическое файловое хранилище хранит байты файлов.

По текущему scope:

```text id="nm1p3v"
допустимо простое хранение файлов в директории;
БД хранит путь или ключ;
backend отвечает за сохранение и чтение файла;
frontend не обращается к файловой системе напрямую.
```

Рабочая формулировка:

> В рамках текущего scope физические файлы могут храниться в простой файловой директории. При этом доступ к файлам должен осуществляться через backend, а не напрямую из frontend.

Осторожность:

```text id="6c1f48"
не заявлять object storage как текущую реализацию;
не заявлять версионирование уровня промышленной СЭД;
не заявлять юридическое архивное хранение;
не заявлять полный аудит файла.
```

---

### 7.17 Связь metadata и physical file

Связь выглядит так:

```text id="z2aafo"
AgreementProposal
→ AgreementDocumentRef
→ physical file
```

В русской терминологии:

```text id="cun1xe"
версия договорного предложения
→ ссылка/метаданные документа
→ физический файл
```

Смысл:

```text id="0nidx8"
версия имеет бизнес-контекст;
metadata связывает бизнес-контекст с файлом;
файл хранится отдельно;
при изменении политики хранения важно не потерять связь.
```

Рабочая формулировка:

> Связь между версией предложения и физическим файлом выполняется через метаданные документа. Это позволяет отделить бизнес-сущность от способа хранения файла и в дальнейшем заменить механизм хранения без изменения предметной модели.

---

### 7.18 Последовательность появления данных

Данные в системе появляются не одновременно, а по мере выполнения сценариев.

```text id="b0fsx8"
1. Клиент создаёт учётную запись.
2. Клиент создаёт заявителя.
3. Клиент создаёт заявку.
4. Сотрудник начинает рассмотрение.
5. Сотрудник принимает решение.
6. При одобрении может начаться договорный обмен.
7. В договорном обмене появляются версии предложения.
8. К версии прикрепляется document metadata.
9. Физический файл сохраняется в файловом хранилище.
```

Не все связи обязательны с самого начала:

```text id="rrgpvu"
новая заявка ещё не имеет решения;
отклонённая заявка не имеет договорного обмена;
договорный обмен не существует до одобрения заявки;
версия предложения не имеет смысла без договорного обмена;
файл не имеет бизнес-смысла без metadata и версии предложения.
```

Рабочая формулировка:

> Модель хранения должна учитывать последовательность выполнения процесса. Не все данные существуют с момента создания заявки: рассмотрение, решение, договорный обмен, версии предложений и файлы появляются на разных этапах жизненного цикла.

---

### 7.19 Целостность данных

Модель хранения должна предотвращать потерю связей между объектами процесса.

Примеры проектных ограничений:

```text id="h0kdbn"
заявка должна ссылаться на существующего заявителя;
договорный обмен должен быть связан с одобренной заявкой;
версия предложения должна быть связана с договорным обменом;
document metadata должна быть связана с версией предложения;
metadata должна содержать ключ или путь к физическому файлу;
файл не должен быть доступен без проверки связи с заявкой или обменом.
```

Рабочая формулировка:

> При проектировании хранения важно обеспечить целостность связей: заявка должна быть связана с заявителем, договорный обмен — с заявкой, версия предложения — с обменом, а metadata документа — с физическим файлом. Это позволяет backend восстановить полный контекст действия и проверить доступ пользователя.

---

### 7.20 Согласованность metadata и physical file

Поскольку metadata и physical file хранятся в разных местах, возникает риск рассогласования.

Возможные проблемы:

```text id="lyms3g"
metadata есть, но файл отсутствует;
файл есть, но metadata отсутствует;
metadata указывает на старый storage key;
файл сохранён, но операция создания версии не завершилась;
metadata создана, но physical file не был сохранён.
```

Для текущего scope достаточно принципа:

```text id="e4xj1z"
backend должен сохранять metadata и файл в рамках одного сценария;
ошибка сохранения файла не должна приводить к созданию некорректной версии предложения;
получение файла должно начинаться с проверки metadata и доступа;
файл без metadata не должен считаться документом процесса.
```

Рабочая формулировка:

> Так как metadata и физический файл находятся в разных хранилищах, backend должен контролировать их согласованность. Файл не должен рассматриваться как самостоятельный документ системы без metadata-записи, связывающей его с версией договорного предложения.

---

### 7.21 Изменение и удаление файлов

В текущем scope не нужно раскрывать сложную политику удаления файлов.

Но на уровне проектирования стоит зафиксировать принцип:

```text id="8qfdb9"
файл договорного предложения не должен произвольно изменяться после отправки версии;
новый вариант должен сохраняться как новая версия предложения;
новая версия должна иметь новую metadata-запись;
перезапись старого файла может разрушить историю обмена.
```

Рабочая формулировка:

> После отправки версии договорного предложения связанный с ней файл целесообразно рассматривать как неизменяемое приложение к этой версии. Если сторона отправляет новый вариант, он должен сохраняться как новая версия предложения с новой metadata-записью, а не как перезапись старого файла.

---

### 7.22 Хранение и independent domain layer

Storage должен поддерживать domain layer, но не загрязнять его.

Domain layer не должен содержать:

```text id="499otk"
SQL-запросы;
имена таблиц;
пути к файлам;
работу с директориями;
DTO upload-запросов;
HTTP details.
```

Storage layer должен обеспечивать:

```text id="wb7tqp"
сохранение состояния;
загрузку нужных объектов;
сохранение metadata;
сохранение physical file;
восстановление связей;
поддержку application scenarios.
```

Рабочая формулировка:

> Независимость domain layer означает, что бизнес-правила заявки и договорного обмена не должны зависеть от того, как именно данные сохранены в БД или где физически расположен файл. Storage layer отвечает за сохранение состояния, но не определяет бизнес-смысл объектов.

---

### 7.23 Хранение и расширяемость

Разделение БД, metadata и physical file помогает развивать систему.

Примеры развития:

```text id="k8aidi"
заменить директорию на object storage;
добавить проверку типа файла;
добавить ограничение размера;
добавить антивирусную проверку;
добавить аудит загрузок;
добавить срок хранения;
добавить внешнее ЭДО как отдельный блок;
добавить электронную подпись как отдельный сценарий.
```

Рабочая формулировка:

> Разделение структурированных данных, метаданных и физических файлов делает систему расширяемой. Например, простое файловое хранение может быть заменено более развитым хранилищем, при этом связь версии договорного предложения с документом сохраняется через metadata-запись.

## 8. Логическая модель хранения

Общая логическая цепочка:

```text id="jsp8ge"

   ↓
ApplicantParty
   ↓
ConnectionRequest
   ↓
RequestReview / Decision
   ↓
AgreementProposalExchange
   ↓
AgreementProposal
   ↓
AgreementDocumentRef
   ↓

```

```text id="f6460u"

   ↓

   ↓

   ↓
рассмотрение / решение
   ↓

   ↓
версия договорного предложения
   ↓
ссылка и метаданные документа
   ↓

```

Важно:

```text id="58zkjm"
это логическая схема хранения;
точные таблицы и связи проверить по repo;
кардинальности не утверждать без repo-check;
названия repo-терминов использовать осторожно.
```

| Физический файл      | файловое хранилище | хранить содержимое документа          |
| Путь/ключ файла      | БД                 | найти физический файл через backend   |

## 11. Метаданные документа

### 11.1 Зачем нужны метаданные

Метаданные нужны, чтобы физический файл не был “потерянным приложением”.

Они связывают файл с:

```text id="rmh6oo"
договорным обменом;
версией предложения;
отправителем;
датой загрузки;
именем файла;
путём/ключом хранения;
правами доступа.
```

Рабочая формулировка:

> Метаданные документа позволяют связать физический файл с предметным процессом. Без metadata-записи файл существовал бы как отдельный объект файловой системы и не имел бы связи с договорным обменом и версией предложения.

---

### 11.2 Минимальный набор metadata

Минимальный набор для ВКР можно описывать так:

```text id="c3aatw"
идентификатор;
связь с версией предложения;
имя файла;
ключ/путь хранения;
дата загрузки;
размер файла, если сохраняется;
тип файла, если сохраняется;
загрузившая сторона, если сохраняется.
```

Осторожность:

```text id="hq2auk"
точные поля проверить по repo;
не перечислять как точно реализованные до проверки;
не писать MIME/content type, если его нет;
не писать checksum/hash, если его нет.
```

---

### 11.3 Почему metadata в БД, а file отдельно

Причины:

```text id="z1z3tg"
БД удобна для связей и поиска;
файл может быть большим бинарным объектом;
file storage лучше подходит для физического содержимого;
metadata позволяет менять storage без изменения предметной модели;
backend контролирует доступ к файлам.
```

Рабочая формулировка:

> Хранение метаданных в БД позволяет связывать документ с заявкой и договорным обменом, а вынесение физического файла в файловое хранилище упрощает работу с бинарными данными и не перегружает предметную модель.

## 12. Source of truth и границы хранения

### 12.1 Что является source of truth

Для процесса source of truth — это структурированное состояние и предметные правила.

```text id="e5iqyi"
domain layer:
определяет допустимые переходы и бизнес-инварианты;

БД:
хранит состояние после применения правил;

metadata:
связывает состояние процесса с physical file;

backend:
контролирует доступ и согласованность операций.
```

### 12.2 Что не является source of truth

| Элемент                | Почему не source of truth                                    |
| ---------------------- | ------------------------------------------------------------ |
| Frontend state         | может устареть, обновляется через API                        |
| Физический файл        | содержит документ, но не состояние процесса                  |
| Имя файла              | не определяет статус версии или договора                     |
| Путь к файлу           | техническая деталь хранения                                  |
| Read DTO               | отражает данные для экрана, но не управляет бизнес-правилами |
| Старые use-case labels | не должны подменять текущую проектную модель                 |

Подпись:

```text id="gr3woe"
Таблица 2.x — Элементы, не являющиеся источником истины для состояния процесса
```

Рабочая формулировка:

> Источником состояния процесса являются структурированные данные и предметная модель, а не UI-состояние, имя файла или физическое расположение документа.

## 13. Целостность и согласованность хранения

### 13.1 Целостность связей

Хранение должно поддерживать цепочку:

```text id="lye8ia"
клиент
→ заявитель
→ заявка
→ рассмотрение / решение
→ договорный обмен
→ версия предложения
→ document metadata
→ physical file
```

Если связь потеряна:

```text id="uepblv"
невозможно проверить доступ;
невозможно показать историю;
невозможно понять, кто отправил версию;
невозможно безопасно выдать файл;
невозможно восстановить контекст процесса.
```

Рабочая формулировка:

> Целостность связей нужна для восстановления контекста процесса. Backend должен иметь возможность пройти от файла к версии предложения, от версии — к договорному обмену, от обмена — к заявке и пользователю.

---

### 13.2 Согласованность metadata и physical file

Согласованность metadata и physical file нужна, потому что они находятся в разных местах.

Принцип:

```text id="o2xobh"
metadata создаётся только для файла, который сохранён;
файл выдаётся только при наличии metadata;
metadata должна указывать на актуальный storage key/path;
ошибка файлового хранения не должна создавать некорректное состояние версии.
```

Рабочая формулировка:

> Backend должен контролировать согласованность metadata и physical file. Это особенно важно при загрузке версии договорного предложения: если файл не был сохранён, версия не должна ссылаться на несуществующий документ.

---

### 13.3 Неизменяемость файла версии

Для истории договорного обмена важно не перезаписывать старые версии.

Принцип:

```text id="8m1alq"
отправленная версия сохраняется как факт обмена;
её файл не должен подменяться незаметно;
новый вариант должен создаваться как новая версия;
новая версия получает новую metadata-запись.
```

Рабочая формулировка:

> Для сохранения истории договорного обмена файл, связанный с отправленной версией предложения, целесообразно рассматривать как неизменяемое приложение. Новый вариант предложения должен создаваться как новая версия, а не как перезапись старого файла.

---

## 15. Что требует обоснования

### 15.1 Почему нужно разделять структурированные данные и файлы

Будущая формулировка:

> Структурированные данные и физические файлы имеют разную природу. Заявки, состояния, решения и связи удобно хранить в БД, а бинарное содержимое документов — в файловом хранилище.

---

### 15.2 Почему storage model не управляет поведением

Будущая формулировка:

> Модель хранения фиксирует результат выполнения сценариев, но не определяет бизнес-правила. Смысл переходов заявки, рассмотрения и договорного обмена должен находиться в domain layer.

---

### 15.3 Почему нужно разделять command data и read data

Будущая формулировка:

> Команды требуют восстановления предметных объектов и применения бизнес-правил, а чтение требует удобных представлений для интерфейса. Поэтому модель хранения должна поддерживать оба режима: изменение состояния и получение данных для экранов.

---

### 15.4 Почему связи нужны для access scope

Будущая формулировка:

> Связи между пользователем, заявителем, заявкой, договорным обменом и файлом нужны не только для навигации, но и для проверки доступа. Backend должен определять, относится ли запрашиваемый объект к текущему пользователю.

---

### 15.5 Почему metadata хранится в БД

Будущая формулировка:

> Метаданные документа хранятся в БД, потому что они связывают файл с предметным процессом: заявкой, договорным обменом, версией предложения и отправителем.

---

### 15.6 Почему файл не является source of truth

Будущая формулировка:

> Физический файл содержит документное содержимое, но не определяет состояние договорного обмена. Статусы, отправитель, активность версии и права доступа должны храниться в структурированных данных.

---

### 15.7 Почему версия предложения и файл — разные понятия

Будущая формулировка:

> Версия договорного предложения является предметным объектом обмена, а файл — приложением к этой версии. Поэтому новая версия должна создаваться через сценарий договорного обмена, а не через простую замену файла.

---

### 15.8 Почему файл не является частью domain layer

Будущая формулировка:

> Domain layer должен содержать бизнес-правила и предметные связи, но не физическое содержимое файла. Байты файла относятся к инфраструктурному хранению и не должны загрязнять предметную модель.

---

### 15.9 Почему простая директория допустима для scope ВКР

Будущая формулировка:

> Для учебного проекта достаточно простой файловой модели: physical file хранится в директории, а БД содержит путь или ключ к нему. Такая модель демонстрирует принцип разделения metadata и physical file без внедрения промышленного хранилища.

---

### 15.10 Почему нужно контролировать согласованность metadata и physical file

Будущая формулировка:

> Metadata и physical file находятся в разных хранилищах, поэтому backend должен контролировать их согласованность. Файл не должен считаться документом процесса без metadata-записи, связывающей его с версией предложения.

---

### 15.11 Почему это не полноценная СЭД

Будущая формулировка:

> Система хранит файлы как документы, связанные с договорным обменом, но не реализует функции полноценной СЭД: юридически значимый ЭДО, электронную подпись, сложные маршруты согласования, архивное хранение и полный аудит файловых операций.

---

### 15.12 Почему storage boundary помогает расширяемости

Будущая формулировка:

> Выделение границы хранения позволяет заменить способ физического хранения файла без изменения предметного смысла договорного обмена. Версия предложения продолжает ссылаться на metadata, даже если механизм physical file storage будет изменён.

---

### 15.13 Почему клиент не должен обращаться к файлам напрямую

Будущая формулировка:

> Доступ к файлам должен выполняться через backend, потому что серверная часть проверяет права пользователя и связь файла с доступной заявкой или договорным обменом.

## 18. Черновые фрагменты будущего текста

### Фрагмент 1 — ввод

После описания предметной модели и архитектуры необходимо определить подход к хранению данных и файлов. Система должна сохранять состояние заявок, рассмотрений, решений и договорного обмена, а также связывать версии договорных предложений с прикреплёнными файлами.

### Фрагмент 2 — общее разделение

В проектируемой системе структурированные данные и метаданные документов хранятся в базе данных, а физические файлы размещаются отдельно в файловом хранилище. Такое разделение позволяет не смешивать состояние бизнес-процесса и бинарное содержимое файлов.

### Фрагмент 3 — storage не управляет поведением

Модель хранения фиксирует результат выполнения сценариев, но не определяет бизнес-правила. Например, БД может хранить состояние заявки, но допустимость перехода заявки в это состояние определяется в domain layer.

### Фрагмент 4 — command/read

Хранение поддерживает два режима работы. При выполнении команд backend восстанавливает предметные объекты и применяет правила domain layer. При чтении данных для интерфейса могут использоваться read-модели или DTO, удобные для списка заявок, карточки заявки или истории договорного обмена.

### Фрагмент 5 — access scope

Связи между учётной записью, заявителем, заявкой и договорным обменом нужны не только для навигации, но и для проверки доступа. Backend должен иметь возможность определить, относится ли запрашиваемая заявка, версия предложения или файл к текущему пользователю.

### Фрагмент 6 — заявка как центр хранения

Клиентская заявка является центральным объектом хранения. Через неё связываются заявитель, рассмотрение, решение и договорный обмен, который может быть начат после одобрения заявки.

### Фрагмент 7 — договорный обмен и версии

Договорный обмен хранится отдельно от заявки, но связан с ней. Внутри обмена сохраняются версии договорного предложения, каждая из которых имеет отправителя и может быть связана с документом.

### Фрагмент 8 — version не file

Версия договорного предложения и физический файл не являются одним и тем же объектом. Версия имеет предметный смысл в договорном обмене, а файл является приложением к этой версии.

### Фрагмент 9 — document metadata

Для связи версии предложения с файлом используется metadata-запись. Она хранит сведения о документе и путь или ключ physical file, но не содержит сам файл как часть предметной модели.

### Фрагмент 10 — file storage

Физические файлы договорных предложений размещаются в файловом хранилище. В рамках текущего scope это может быть простая файловая директория, доступ к которой выполняется через backend.

### Фрагмент 11 — доступ через backend

Frontend не обращается к файлам напрямую. Пользователь запрашивает файл через backend, серверная часть проверяет доступ к заявке или договорному обмену, получает metadata и только после этого возвращает файл или ошибку.

### Фрагмент 12 — source of truth

Источником состояния процесса являются структурированные данные и предметная модель, а не UI-состояние, имя файла или физическое расположение документа. Файл содержит документное содержимое, но не определяет статус договорного обмена.

### Фрагмент 13 — consistency

Так как metadata и physical file находятся в разных хранилищах, backend должен контролировать их согласованность. Файл не должен рассматриваться как самостоятельный документ системы без metadata-записи, связывающей его с версией предложения.

### Фрагмент 14 — immutable version attachment

После отправки версии договорного предложения связанный файл целесообразно рассматривать как неизменяемое приложение к этой версии. Если сторона отправляет новый вариант, он должен сохраняться как новая версия предложения с новой metadata-записью.

### Фрагмент 15 — границы

Предложенная модель хранения не является полноценной СЭД. Она не включает электронную подпись, юридически значимый ЭДО, сложное архивное хранение, промышленный object storage и полный аудит файловых операций.

### Фрагмент 16 — расширяемость

Разделение metadata и physical file позволяет в дальнейшем изменить механизм хранения. Например, простая директория может быть заменена объектным хранилищем без изменения предметного смысла договорного обмена.
