## 2. Что это за тема

Эта тема завершает блок **2.4 “Проектирование хранения данных и файлов”** и фиксирует границы выбранной модели хранения.

Предыдущие темы 2.4.1 и 2.4.2 отвечали на вопросы:

```text id="o567gi"
какие данные хранятся в БД;
как связаны заявка, рассмотрение, договорный обмен и версии;
как metadata связывает версию договорного предложения с physical file;
почему frontend не обращается к файлам напрямую;
почему domain layer не должен знать storage path и file bytes;
почему proposal version, document metadata и physical file — разные элементы модели.
```

Текущая тема отвечает на вопрос:

```text id="bmpzdv"
какие возможности входят в текущую модель хранения,
какие возможности сознательно вынесены за scope,
почему эти границы являются архитектурным решением,
и как выбранные границы позволяют развивать систему дальше.
```

Главная мысль:

> Модель хранения проектируется как минимально достаточная для основной цепочки ВКР: клиент создаёт заявителя и заявку, сотрудник рассматривает заявку, после одобрения возникает договорный обмен, а версии договорного предложения связываются с прикреплёнными файлами через metadata. При этом система не проектируется как полноценная СЭД, юридически значимый ЭДО или промышленное файловое хранилище. Эти функции рассматриваются как направления развития, а текущая модель сохраняет устойчивые границы: domain layer содержит бизнес-правила, БД хранит structured state и document metadata, файловое хранилище хранит physical file, backend контролирует доступ и согласованность.

## 3. Важное уточнение: ограничения ≠ слабость проекта

В финальном тексте не нужно писать:

```text id="p7fmgc"
это не реализовано;
это пока не доделано;
это ограничение из-за нехватки времени;
это слабое место;
система не умеет нормально работать с документами.
```

Лучше писать:

```text id="5nj4bf"
в рамках текущего scope;
для целей ВКР;
выбранная модель достаточна для основной цепочки;
функция вынесена за границы проектирования;
это направление дальнейшего развития;
архитектура сохраняет точку расширения;
возможность может быть добавлена без изменения бизнес-смысла модели.
```

Рабочая формулировка:

> Ограничения модели хранения следует описывать как осознанные границы проектирования. Для текущего scope важно не реализовать все функции промышленной документной системы, а показать корректную связь structured data, document metadata, physical file и проверки доступа.

## 4. Границы как архитектурное решение

Границы модели хранения нужны не только для ограничения scope, но и для защиты архитектуры от преждевременного усложнения.

В текущем проекте важнее показать устойчивую цепочку:

```text id="6l3k7d"
business process
→ structured state
→ document metadata
→ physical file
```

чем сразу добавлять:

```text id="1ngnxv"
промышленное файловое хранилище;
ЭДО;
ЭП;
аудит;
архивную политику;
антивирусный pipeline;
document preview;
сложную document management platform.
```

Рабочая формулировка:

> Границы модели хранения являются частью архитектурного решения. Они позволяют сосредоточиться на основной цепочке обработки заявки и договорного обмена, не смешивая её с инфраструктурой полноценной СЭД, электронного документооборота и юридически значимого подписания.

## 5. Принятые уточнения

1. Текущая модель хранения поддерживает основную цепочку ВКР.
2. Основная цепочка: клиент → заявитель → заявка → рассмотрение → решение → договорный обмен → версия предложения → document metadata → physical file.
3. Границы модели хранения — это архитектурное решение, а не список отказов.
4. Модель хранения должна быть минимально достаточной для текущего scope.
5. БД хранит structured data процесса.
6. БД хранит document metadata.
7. Physical file хранится отдельно.
8. Backend является обязательной точкой доступа к файлам.
9. Frontend не имеет прямого доступа к file storage.
10. Domain layer не знает storage path, storage key, file bytes и file system.
11. Storage model поддерживает сценарии, но не управляет бизнес-поведением.
12. Бизнес-переходы относятся к domain/application layer.
13. Metadata является границей между domain/application и infrastructure/file storage.
14. Physical file не является source of truth для состояния договорного обмена.
15. Версия договорного предложения и файл — разные понятия.
16. Новый документ после отправки должен рассматриваться как новая версия, а не перезапись старой.
17. Internal storage key не должен быть частью публичного frontend-контракта.
18. Frontend должен работать через documentId / proposalVersionId / download API, а не через physical path.
19. Ошибки файлового доступа не должны раскрывать internal path, storage key и чужие документы.
20. Договорные файлы не должны раздаваться как public static files.
21. Signed URLs можно рассматривать только как future work при переходе к object storage.
22. Возможны orphan file и orphan metadata как технические риски.
23. Файл без metadata не считается документом системы.
24. Metadata без physical file должна приводить к безопасной ошибке.
25. Successful upload должен создавать и physical file, и metadata.
26. Текущий scope не включает полноценную СЭД.
27. Текущий scope не включает юридически значимый ЭДО.
28. Текущий scope не включает электронную подпись.
29. Текущий scope не требует object storage.
30. Текущий scope не требует signed temporary URLs.
31. Текущий scope не требует антивирусной проверки.
32. Текущий scope не требует полного аудита скачиваний.
33. Текущий scope не требует архивной политики и retention policy.
34. Эти функции можно описывать как направления развития.
35. Главное — показать, что архитектура не блокирует такие расширения.

## 6. Сценарная основа темы

Границы хранения определяются сценариями, которые реально нужны для ВКР.

### 6.1 Входит в основную цепочку

```text id="u1dzl6"
создание заявителя;
создание заявки;
просмотр заявок;
начало рассмотрения;
одобрение или отклонение;
сохранение причины отказа при наличии;
начало договорного обмена после одобрения;
отправка версии договорного предложения;
прикрепление файла к версии;
получение файла через backend;
отображение истории версий.
```

### 6.2 Не является обязательной частью текущей цепочки

```text id="fofq1p"
электронная подпись;
юридически значимый ЭДО;
автоматическая генерация договора;
промышленное document management;
совместное редактирование файлов;
полнотекстовый поиск;
антивирусная проверка;
долговременное архивное хранение;
полный аудит скачиваний;
object storage как обязательная инфраструктура;
signed temporary URLs;
email/push как обязательный канал уведомлений.
```

Рабочая формулировка:

> Границы модели хранения определяются основной цепочкой сценариев. Система должна сохранять состояние заявки и договорного обмена, связывать версии предложений с файлами и обеспечивать доступ к этим файлам через backend. Более сложные функции документооборота не являются обязательными для демонстрации этой цепочки.

## 8. Содержание темы

### 8.1 Минимально достаточная модель хранения

Для текущего scope модель хранения должна быть не максимальной, а минимально достаточной.

Она должна обеспечить:

```text id="0mnn4n"
заявка сохраняет состояние;
рассмотрение и решение фиксируются;
договорный обмен связан с одобренной заявкой;
версия предложения связана с обменом;
document metadata связывает версию с файлом;
backend может проверить доступ;
frontend может показать файл и историю версий.
```

Но ей не обязательно обеспечивать:

```text id="f615x6"
юридическое подписание;
полный аудит;
корпоративное архивное хранение;
сложные маршруты согласования;
объектное хранилище;
антивирусный pipeline;
document preview;
совместное редактирование;
полнотекстовый поиск.
```

Рабочая формулировка:

> Модель хранения проектируется как минимально достаточная для основной цепочки ВКР. Она должна сохранять состояние заявки, договорного обмена, версии предложения и связь с файлом, но не обязана реализовывать функции промышленной системы документооборота.

---

### 8.2 Разделение текущего scope и направлений развития

В тексте и визуалах нужно явно отделять:

```text id="fz3t6k"
Current scope:
  structured data;
  document metadata;
  physical file;
  backend access check;
  upload/download через API.

Future work:
  object storage;
  antivirus scan;
  audit trail;
  ЭДО;
  ЭП;
  notifications;
  archive/retention policy.
```

Future work не должен выглядеть как уже существующая часть архитектуры.

Рабочая формулировка:

> Направления развития следует показывать отдельно от текущей модели. Они демонстрируют расширяемость архитектуры, но не должны восприниматься как реализованные компоненты системы.

---

### 8.3 Граница между domain layer и storage

Domain layer содержит бизнес-правила:

```text id="yi50y1"
можно ли начать рассмотрение;
можно ли одобрить заявку;
можно ли отклонить заявку;
можно ли начать договорный обмен;
можно ли отправить новую версию предложения;
кто является отправителем версии.
```

Storage содержит сохранённое состояние:

```text id="fqrgpy"
текущий статус заявки;
связь заявки с заявителем;
связь review с заявкой;
связь exchange с заявкой;
связь proposal с exchange;
связь document metadata с proposal;
storage key physical file.
```

Рабочая формулировка:

> Storage layer сохраняет результат выполнения сценариев, но не определяет бизнес-смысл этих сценариев. Правила изменения состояния должны находиться в domain layer, а БД и файловое хранилище фиксируют состояние после применения этих правил.

---

### 8.4 Почему storage не управляет бизнес-поведением

База данных может хранить статус заявки или версии предложения, но она не должна быть основным местом, где определяется допустимость перехода.

Например, БД может хранить:

```text id="lfhbsr"
RequestStatus = Approved
```

Но правило:

```text id="ulnx5s"
заявку можно одобрить только после начатого рассмотрения
```

должно находиться в domain/application model, а не быть скрытым только в:

```text id="m5zrr4"
SQL-запросе;
constraint-е;
UI-условии;
frontend state;
ручной проверке в отдельном компоненте.
```

Рабочая формулировка:

> Storage layer фиксирует результат бизнес-операции, но не должен подменять правила её выполнения. Если допустимость перехода состояния хранится только в SQL-условиях или UI-логике, бизнес-смысл становится размазанным и сложным для проверки.

---

### 8.5 Граница между metadata и physical file

Metadata и physical file решают разные задачи.

Metadata:

```text id="op0g2e"
хранится в БД;
связывает файл с версией предложения;
содержит original file name;
содержит storage key/path;
используется для проверки доступа;
позволяет восстановить бизнес-контекст файла.
```

Physical file:

```text id="97150p"
хранится в file storage;
содержит байты документа;
не знает о заявке;
не знает о договорном обмене;
не определяет статус предложения;
не является source of truth.
```

Рабочая формулировка:

> Metadata связывает physical file с предметным процессом, а physical file хранит только содержимое документа. Поэтому файл без metadata не является документом процесса, а metadata без physical file должна обрабатываться как ошибка согласованности.

---

### 8.6 Physical file не определяет состояние процесса

Physical file может существовать в директории, но без metadata он не является документом системы.

И наоборот: metadata может указывать на файл, но если файла нет, это ошибка хранения, а не новое состояние договорного обмена.

Состояние процесса определяется structured data:

```text id="4d60pp"
статус заявки;
статус рассмотрения;
статус договорного обмена;
активная версия предложения;
отправитель версии;
связь версии с document metadata.
```

Рабочая формулировка:

> Physical file не является источником истины для состояния договорного обмена. Состояние процесса определяется структурированными данными, а файл является содержимым документа, связанным с этим процессом через metadata.

---

### 8.7 Граница между frontend и file storage

Frontend не должен обращаться к file storage напрямую.

Frontend отвечает за:

```text id="aat44f"
выбор файла;
отправку файла через API;
показ имени файла;
запрос скачивания через backend;
отображение ошибки.
```

Backend отвечает за:

```text id="x9z1az"
проверку авторизации;
проверку доступа к request/exchange/proposal;
сохранение physical file;
создание metadata;
чтение metadata;
получение physical file;
возврат файла или безопасной ошибки.
```

Рабочая формулировка:

> Frontend работает с файлами только через API. Это позволяет backend скрыть физическую структуру хранения и выполнить проверку доступа перед выдачей договорного документа.

---

### 8.8 Внутренний storage key и внешний API

`StorageKey` или путь к файлу являются внутренними деталями backend/storage layer.

Frontend не должен получать:

```text id="wfdmd9"
абсолютный путь к файлу;
локальный путь директории;
внутреннее имя файла;
storage key как основной публичный идентификатор;
имя директории;
серверный physical path.
```

Frontend должен работать через API-идентификатор документа или версии:

```text id="5z1rp4"
documentId;
proposalVersionId;
download endpoint;
file metadata DTO без internal path.
```

Рабочая формулировка:

> Внутренний storage key не должен становиться частью публичного frontend-контракта. Пользовательский интерфейс должен запрашивать файл через API, а backend уже по metadata определяет внутренний путь или ключ хранения.

---

### 8.9 Почему договорные файлы не являются public static files

Public static file serving подходит для открытых ресурсов, но не для договорных документов.

Для договорных документов важно:

```text id="naivj3"
проверять пользователя;
проверять роль;
проверять связь файла с заявкой;
проверять связь файла с договорным обменом;
не раскрывать внутренний путь;
не раскрывать факт существования чужого файла.
```

Неправильная модель:

```text id="lghtqk"
Frontend → /uploads/agreement-files/file.pdf
```

Правильная модель:

```text id="1kx5tv"
Frontend
→ Backend API
→ auth/access check
→ document metadata
→ file storage
→ file response или safe error
```

Рабочая формулировка:

> Договорные файлы не должны раздаваться как публичные статические файлы, потому что доступ к ним зависит от предметных связей и роли пользователя. Получение файла должно проходить через backend и проверку доступа.

---

### 8.10 Безопасная обработка ошибок файлового доступа

Файловые ошибки не должны раскрывать внутреннюю структуру хранения или факт существования чужого документа.

Примеры внутренних причин:

```text id="safina"
нет доступа к чужому файлу;
metadata существует, но пользователь не имеет права;
physical file отсутствует;
storage key некорректен;
файл был удалён вручную;
metadata указывает на несуществующий файл.
```

Backend может возвращать безопасные ошибки:

```text id="6tq8fg"
not found;
forbidden;
file unavailable;
validation error;
business-state error.
```

Но frontend не должен получать:

```text id="l57smb"
internal path;
storage key;
имя директории;
stack trace;
наличие чужого файла;
технические детали file system.
```

Рабочая формулировка:

> Ошибки файлового доступа должны быть безопасными. Backend может различать причины внутри системы, но frontend не должен получать внутренние пути, storage key или сведения о документах, к которым пользователь не имеет доступа.

---

### 8.11 Граница текущего file storage

Текущая модель может использовать простую директорию.

Это допустимо, потому что:

```text id="hh0nbm"
scope ВКР не требует промышленного object storage;
важнее показать правильную границу metadata/file;
backend всё равно контролирует доступ;
domain layer не зависит от физического хранения;
модель можно заменить позже.
```

Но не нужно утверждать:

```text id="a96lwt"
это промышленное хранилище;
это полноценное архивное хранение;
это object storage;
это защищённое долговременное хранение;
это СЭД-хранилище.
```

Рабочая формулировка:

> Для текущего scope достаточно простой файловой директории. Она демонстрирует принцип разделения document metadata и physical file без усложнения проекта промышленной инфраструктурой хранения.

---

### 8.12 Ограничение: нет полноценной СЭД

Система не является полноценной системой электронного документооборота.

Не входят функции:

```text id="ac7z9j"
сложные маршруты согласования;
регистрационные карточки документов уровня СЭД;
архивное хранение;
полный аудит операций с документами;
полнотекстовый поиск;
версионирование уровня корпоративной СЭД;
права доступа уровня document management platform.
```

Рабочая формулировка:

> Проектируемая система хранит файлы как приложения к версиям договорного предложения, но не является полноценной СЭД. Её задача — поддержать договорный обмен в рамках процесса заявки, а не заменить корпоративную платформу документооборота.

---

### 8.13 Ограничение: нет юридически значимого ЭДО и ЭП

Договорный обмен в системе не нужно описывать как юридически значимое подписание.

Не входит:

```text id="d8lzmy"
электронная подпись;
квалифицированная электронная подпись;
подписание договора в системе;
интеграция с оператором ЭДО;
юридически значимый обмен документами;
проверка сертификатов;
штампы времени.
```

Рабочая формулировка:

> Договорный этап в рамках проектируемой системы представляет собой обмен версиями договорного предложения. Электронная подпись и юридически значимый ЭДО требуют отдельной правовой и технической инфраструктуры, поэтому рассматриваются как направления дальнейшего развития.

---

### 8.14 Ограничение: нет автоматической генерации договора

В текущей модели файл прикрепляется как готовый документ.

Не утверждать:

```text id="dbi4br"
система автоматически генерирует договор;
система формирует PDF;
система подставляет реквизиты в шаблон;
система создаёт юридически готовый договор.
```

Писать:

```text id="4tg4v2"
сотрудник отправляет версию договорного предложения;
к версии прикрепляется готовый файл;
клиент может просмотреть версию и отреагировать;
новый вариант оформляется как новая версия.
```

Рабочая формулировка:

> Система не обязана автоматически формировать договорный документ. В рамках текущей модели договорный обмен строится вокруг прикрепления готовых файлов к версиям договорного предложения.

---

### 8.15 Ограничение: нет полного аудита файловых операций

В текущем scope можно фиксировать базовую информацию о загрузке файла, если это есть в модели.

Но не заявлять без repo-check:

```text id="u4sjrr"
полный аудит скачиваний;
журнал всех просмотров;
журнал всех неуспешных попыток доступа;
неизменяемый audit log;
compliance audit;
retention policy.
```

Рабочая формулировка:

> Базовая metadata-запись позволяет сохранить контекст загрузки файла, но полный аудит всех файловых операций выходит за границы текущей модели хранения и может быть рассмотрен как развитие.

---

### 8.16 Ограничение: нет антивирусной проверки и file inspection

Не заявлять без repo-check:

```text id="wmi5h8"
антивирусная проверка;
проверка содержимого файла;
проверка PDF-структуры;
извлечение текста;
preview документа;
контроль вредоносного содержимого.
```

Но можно указать future work:

```text id="kwjv2u"
проверка типа файла;
ограничение размера;
антивирусная проверка;
document preview.
```

Рабочая формулировка:

> Проверка содержимого файлов и антивирусная обработка не являются обязательной частью текущей модели. Эти функции могут быть добавлены позже на границе file storage или upload pipeline.

---

### 8.17 Ограничение: нет distributed transaction для metadata/file

Metadata хранится в БД, physical file — в file storage. Это разные хранилища.

Не нужно обещать:

```text id="xv7uds"
распределённую транзакцию;
двухфазный commit;
сложный saga/outbox механизм;
автоматический cleanup orphan files.
```

Для текущего scope достаточно:

```text id="m2u54m"
обработать upload как единый application scenario;
не показывать успешную версию, если file save failed;
не отдавать файл без metadata;
безопасно обработать file missing;
указать consistency as design concern.
```

Рабочая формулировка:

> Поскольку metadata и physical file находятся в разных хранилищах, согласованность между ними должна контролироваться backend-ом на уровне сценария. Для текущего scope достаточно описать этот принцип без внедрения сложных распределённых транзакций.

---

### 8.18 Ограничение: нет сложной политики удаления

Не нужно подробно раскрывать:

```text id="rguqus"
soft delete файлов;
hard delete файлов;
garbage collection;
retention policy;
legal hold;
архивное удаление;
cleanup orphan files.
```

Безопасный принцип:

```text id="83jro1"
отправленная версия должна сохранять историю;
новый файл создаёт новую версию;
старые файлы не должны незаметно подменяться;
удаление файлов не является центральным сценарием ВКР.
```

Рабочая формулировка:

> В текущей модели важнее сохранить историю договорного обмена, чем проектировать сложную политику удаления. Поэтому новый документ рассматривается как новая версия, а не как замена файла у уже отправленной версии.

---

### 8.19 Новая версия вместо перезаписи файла

Для договорного обмена важна история того, какие предложения отправлялись сторонами.

Правильно:

```text id="13u1za"
Version 1 → File A
Version 2 → File B
Version 3 → File C
```

Неправильно:

```text id="tcqhgk"
Version 1 → File A
Version 1 → File B after overwrite
```

Почему это важно:

```text id="h9tx6k"
сохраняется история обмена;
можно понять, кто и когда отправил конкретный документ;
старое предложение не подменяется;
состояние процесса остаётся проверяемым;
UI может показать последовательность версий.
```

Рабочая формулировка:

> Новый документ после отправки должен рассматриваться как новая версия договорного предложения, а не как перезапись файла у уже существующей версии. Это сохраняет историю обмена и делает состояние процесса проверяемым.

---

### 8.20 Риски orphan file и orphan metadata

Так как metadata и physical file находятся в разных хранилищах, возможны два технических рассогласования.

```text id="v7hknp"
orphan file:
  physical file есть, но metadata нет;

orphan metadata:
  metadata есть, но physical file отсутствует.
```

Для текущего scope не нужно проектировать сложный cleanup-механизм, но нужно зафиксировать принцип:

```text id="s2vfjy"
файл без metadata не считается документом системы;
metadata без файла должна приводить к безопасной ошибке;
успешный upload должен создавать и file, и metadata;
frontend не должен видеть успешную версию, если связь file/metadata не создана.
```

Рабочая формулировка:

> Потенциальное рассогласование metadata и physical file является техническим риском выбранной модели. В рамках текущего scope достаточно обрабатывать upload как единый сценарий и не считать файл документом системы без metadata-записи.

---

### 8.21 Ограничение: нет object storage как обязательного элемента

Object storage можно указать как направление развития, но не как текущую необходимость.

Почему не обязательно:

```text id="51v2y2"
scope ВКР ограничен;
файловая модель простая;
важна архитектурная граница, а не конкретный провайдер;
backend скрывает физическое хранение;
domain layer не зависит от storage implementation.
```

Рабочая формулировка:

> Object storage не является обязательной частью текущего проекта. За счёт выделения storage boundary простая директория может быть заменена объектным хранилищем без изменения бизнес-смысла договорного обмена.

---

### 8.22 Signed URLs как возможное развитие

Если файловое хранилище будет заменено object storage, возможным развитием может стать выдача временных подписанных ссылок.

Но для текущего scope безопаснее описывать получение файла через backend:

```text id="yyxn5k"
frontend
→ backend
→ access check
→ file response
```

Signed URL требует дополнительных решений:

```text id="7e8l1l"
срок действия ссылки;
права доступа;
отзыв ссылки;
логирование скачивания;
безопасность передачи ссылки;
поведение при пересылке ссылки другому пользователю.
```

Рабочая формулировка:

> Временные подписанные ссылки можно рассматривать как развитие при переходе к object storage. В текущей модели проще и безопаснее описывать получение файла через backend, который выполняет проверку доступа перед выдачей документа.

## 16. Направления развития

### 16.1 Object storage

Возможное развитие:

```text id="xs2srx"
замена директории на object storage;
хранение файлов по storage key;
масштабирование объёма хранения;
разделение bucket/container;
управление lifecycle policies.
```

Как писать осторожно:

> При росте требований к хранению physical file может быть вынесен в object storage. При этом metadata в БД продолжит связывать версию договорного предложения с конкретным storage key.

---

### 16.2 Расширенная file validation

Можно развивать upload pipeline:

```text id="zkfxe5"
ограничение размера файла;
ограничение типов;
проверка расширения;
проверка MIME-type;
антивирусная проверка;
анализ структуры документа.
```

Рабочая формулировка:

> Upload pipeline может быть расширен проверкой размера, типа и содержимого файла. Такие проверки добавляются на backend-границе и не должны переносить файловую инфраструктуру в domain layer.

---

### 16.3 Audit trail

Можно добавить аудит:

```text id="vpix4g"
кто загрузил файл;
кто скачал файл;
когда скачал;
какая версия была открыта;
какая ошибка доступа возникла;
какой пользователь пытался получить файл.
```

Но это не текущий scope.

Рабочая формулировка:

> Расширенный аудит файловых операций может быть добавлен как отдельный инфраструктурный механизм. В текущей модели достаточно сохранить metadata, необходимую для связи файла с версией предложения.

---

### 16.4 ЭДО и электронная подпись

Возможные расширения:

```text id="5fgyne"
интеграция с ЭДО;
электронная подпись;
проверка сертификатов;
статус подписания;
хранение подписанного контейнера;
юридически значимый обмен.
```

Важно:

```text id="5k74xp"
это не просто поле в БД;
это отдельный сценарий;
нужны новые правила;
нужны новые integration boundaries;
нужно правовое обоснование.
```

Рабочая формулировка:

> Электронная подпись и ЭДО могут быть добавлены только как отдельный сценарный блок. Они требуют не только хранения файла, но и проверки подписи, статусов подписания и интеграции с внешней инфраструктурой.

---

### 16.5 Уведомления

Можно добавить:

```text id="1j7qn7"
уведомление о новой версии;
уведомление о принятии версии;
уведомление об отказе;
email;
push;
внутренний notification center.
```

Но не утверждать как реализованное:

```text id="zt20dh"
система отправляет email;
система пушит уведомления;
система имеет outbox;
есть очередь событий.
```

Рабочая формулировка:

> Уведомления о новых версиях договорного предложения можно рассматривать как развитие системы. В текущей модели пользователь видит версии в интерфейсе, а внешние каналы уведомлений не являются обязательными.

## 17. Что требует обоснования

### 17.1 Почему границы модели хранения — это архитектурное решение

Будущая формулировка:

> Границы модели хранения являются частью архитектурного решения. Они позволяют сосредоточиться на основной цепочке заявки и договорного обмена, не смешивая её с инфраструктурой полноценной СЭД, ЭДО и юридически значимого подписания.

---

### 17.2 Почему модель хранения минимально достаточная

Будущая формулировка:

> Для текущего scope модель хранения должна сохранять состояние заявки, договорного обмена, версий предложения и связь с файлом. Реализация функций промышленной СЭД не является обязательной для демонстрации этой цепочки.

---

### 17.3 Почему current scope и future work нужно разделять

Будущая формулировка:

> Направления развития показывают расширяемость архитектуры, но не должны восприниматься как уже реализованные компоненты. Поэтому current scope и future work нужно показывать отдельно.

---

### 17.4 Почему storage не управляет business rules

Будущая формулировка:

> Storage layer фиксирует результат выполнения сценариев, но не должен определять бизнес-правила. Допустимость переходов заявки и договорного обмена должна находиться в domain/application layer.

---

### 17.5 Почему physical file не является source of truth

Будущая формулировка:

> Physical file содержит документное содержимое, но не определяет состояние договорного обмена. Статус, отправитель и активность версии хранятся в structured data.

---

### 17.6 Почему storage key не должен попадать во frontend

Будущая формулировка:

> Storage key является внутренней деталью backend/storage layer. Frontend должен запрашивать файл через API-идентификатор документа или версии, а backend должен самостоятельно находить physical file по metadata.

---

### 17.7 Почему договорные файлы не должны быть public static files

Будущая формулировка:

> Договорные файлы нельзя отдавать как публичные static files, потому что доступ к ним зависит от заявки, договорного обмена и роли пользователя. Прямой URL обходил бы проверку доступа через backend.

---

### 17.8 Почему нужны безопасные file errors

Будущая формулировка:

> Ошибки файлового доступа должны быть понятны пользователю, но не должны раскрывать внутренние пути хранения, storage key или сведения о чужих документах.

---

### 17.9 Почему signed URLs — future work

Будущая формулировка:

> Временные подписанные ссылки могут быть полезны при переходе к object storage, но они требуют дополнительных решений по сроку действия, отзыву, аудиту и безопасности передачи ссылки. Поэтому в текущем scope проще и безопаснее выдавать файл через backend.

---

### 17.10 Почему новый файл должен быть новой версией

Будущая формулировка:

> Новый документ после отправки должен рассматриваться как новая версия договорного предложения, а не как перезапись файла у существующей версии. Это сохраняет историю обмена и делает состояние процесса проверяемым.

---

### 17.11 Почему orphan file / orphan metadata являются техническими рисками

Будущая формулировка:

> Metadata и physical file находятся в разных хранилищах, поэтому возможны orphan file и orphan metadata. В текущем scope достаточно обрабатывать upload как единый сценарий и не считать файл документом системы без metadata-записи.

---

### 17.12 Почему это не полноценная СЭД

Будущая формулировка:

> Система хранит файлы как приложения к версиям договорного предложения, но не реализует функции полноценной СЭД: юридически значимый ЭДО, электронную подпись, сложные маршруты согласования, архивное хранение и полный аудит файловых операций.

## 20. Черновые фрагменты будущего текста

### Фрагмент 1 — ввод

После определения логической модели хранения и связи файлов с версиями договорного предложения необходимо зафиксировать границы выбранного решения. Это важно, чтобы отделить текущий scope системы от функций полноценной СЭД, ЭДО и промышленной инфраструктуры хранения.

### Фрагмент 2 — границы как архитектурное решение

Границы модели хранения являются не признаком неполноты, а осознанным архитектурным выбором. Для текущего scope важно показать устойчивую связь между заявкой, договорным обменом, версией предложения, metadata и physical file, не превращая систему в полноценную СЭД или юридически значимый ЭДО.

### Фрагмент 3 — минимально достаточная модель

Модель хранения проектируется как минимально достаточная для основной цепочки ВКР. Она должна сохранять состояние заявки, договорного обмена, версии предложения и связь с файлом, но не обязана реализовывать функции промышленной системы документооборота.

### Фрагмент 4 — storage не domain

Модель хранения фиксирует состояние процесса, но не определяет бизнес-правила. Допустимость переходов заявки и договорного обмена должна определяться в domain layer, а БД сохраняет результат выполнения сценариев.

### Фрагмент 5 — metadata/file boundary

Document metadata связывает версию договорного предложения с physical file. Physical file хранит содержимое документа, но не определяет состояние договорного обмена и не является source of truth для процесса.

### Фрагмент 6 — physical file not source of truth

Physical file содержит документное содержимое, но не определяет статус версии, отправителя, активность предложения или доступ пользователя. Эти сведения должны храниться в structured data и проверяться backend.

### Фрагмент 7 — backend boundary

Frontend не обращается к файловому хранилищу напрямую. Пользователь запрашивает файл через backend, сервер проверяет доступ к заявке и договорному обмену, получает metadata и только затем возвращает physical file.

### Фрагмент 8 — storage key

Storage key является внутренней деталью backend. Frontend не должен получать путь к файлу или внутренний ключ хранения, а должен запрашивать документ через API-идентификатор.

### Фрагмент 9 — public static files

Договорные файлы не должны раздаваться как публичные static files, потому что доступ к ним зависит от роли пользователя и предметных связей. Прямой URL обходил бы проверку доступа через backend.

### Фрагмент 10 — safe file errors

Ошибки файлового доступа должны быть безопасными. Backend может различать причины внутри системы, но frontend не должен получать внутренние пути, storage key или сведения о документах, к которым пользователь не имеет доступа.

### Фрагмент 11 — не СЭД

Проектируемая система хранит файлы как приложения к версиям договорного предложения, но не является полноценной СЭД. Она не включает сложные маршруты согласования, архивное хранение, полнотекстовый поиск и полный аудит файловых операций.

### Фрагмент 12 — не ЭДО и не ЭП

Договорный этап в системе представляет собой обмен версиями договорного предложения. Электронная подпись и юридически значимый ЭДО требуют отдельной инфраструктуры и поэтому рассматриваются как направления развития.

### Фрагмент 13 — простая директория

Для текущего scope достаточно простой файловой директории. Важнее не конкретный тип хранилища, а то, что physical file отделён от metadata, а domain layer не зависит от файловой системы.

### Фрагмент 14 — consistency

Поскольку metadata и physical file находятся в разных хранилищах, backend должен контролировать их согласованность. Если файл не сохранён или metadata не создана, версия предложения не должна считаться успешно отправленной.

### Фрагмент 15 — orphan risks

Файл без metadata не считается документом системы, а metadata без physical file должна приводить к безопасной ошибке. Для текущего scope достаточно обрабатывать upload как единый сценарий без проектирования сложного cleanup-механизма.

### Фрагмент 16 — new file = new version

Новый документ после отправки должен рассматриваться как новая версия договорного предложения, а не как перезапись файла у уже существующей версии. Это сохраняет историю обмена и делает состояние процесса проверяемым.

### Фрагмент 17 — signed URLs

Временные подписанные ссылки можно рассматривать как развитие при переходе к object storage. В текущей модели проще и безопаснее описывать получение файла через backend, который выполняет проверку доступа перед выдачей документа.

### Фрагмент 18 — future work

Выбранная модель оставляет точки расширения: простое файловое хранилище можно заменить object storage, upload-flow можно дополнить проверкой типов и антивирусной обработкой, а договорный обмен можно расширить ЭДО или электронной подписью.

## 24. Итоговая формула темы

```text id="98cl2y"
границы модели хранения нужны,
чтобы отделить текущий scope ВКР
от функций полноценной СЭД,
ЭДО,
электронной подписи
и промышленного file storage;

ограничения модели хранения — это не список того,
что “не сделано”,
а границы текущего архитектурного решения;

текущая модель поддерживает основную цепочку:
клиент → заявитель → заявка → рассмотрение → решение
→ договорный обмен → версия предложения → metadata → physical file;

модель хранения минимально достаточна:
она хранит process state,
document metadata
и physical file,
но не реализует всю инфраструктуру document management platform;

storage model сохраняет состояние процесса,
но не управляет бизнес-поведением;

domain layer определяет правила и переходы;

БД хранит structured data и document metadata;

file storage хранит physical file;

metadata связывает proposal version с physical file;

physical file не является source of truth
для статуса договорного обмена;

backend контролирует upload,
download,
access check
и consistency metadata/file;

frontend не имеет прямого доступа к file storage;

storage key является внутренней деталью backend
и не должен становиться публичным frontend-контрактом;

договорные файлы не должны раздаваться как public static files;

download идёт через backend,
metadata
и access check;

ошибки файлового доступа должны быть безопасными
и не раскрывать internal path,
storage key
или сведения о чужих документах;

новый документ после отправки должен быть новой proposal version,
а не перезаписью старого файла;

orphan file
и orphan metadata
являются техническими рисками,
которые контролируются на уровне upload/download сценариев;

простая файловая директория достаточна для текущего scope,
потому что главная архитектурная идея —
разделить metadata,
physical file,
domain rules
и access boundary;

object storage,
signed URLs,
антивирусная проверка,
audit trail,
ЭДО,
ЭП,
notifications
и архивная политика
рассматриваются как отдельные сценарные блоки развития,
а не как скрытые части текущей модели.
```
