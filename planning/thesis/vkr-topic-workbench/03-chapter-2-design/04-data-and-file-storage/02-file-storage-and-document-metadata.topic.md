## 2. Что это за тема

Эта тема уточняет файловую часть хранения: как версия договорного предложения связывается с прикреплённым файлом, какие метаданные документа нужны в базе данных и почему физический файл хранится отдельно.

Предыдущая тема 2.4.1 отвечала на вопрос:

```text
как в целом разделяются структурированные данные,
метаданные документа
и физическое файловое хранилище
```

Текущая тема отвечает на вопрос:

```text
как именно связать версию договорного предложения
с файлом так,
чтобы файл имел бизнес-контекст,
не загрязнял domain layer,
не обходил проверку доступа
и не превращал систему в полноценную СЭД
```

Главная мысль:

> Файл договорного предложения не должен существовать в системе как самостоятельный объект без бизнес-контекста. Он связан с конкретной версией договорного предложения, версия входит в договорный обмен, а обмен связан с одобренной заявкой. Поэтому для файла создаётся metadata-запись, которая хранит связь с версией, исходное имя файла, внутренний ключ хранения и служебные сведения, необходимые backend для получения physical file. Получение файла выполняется через backend и проверку доступа, а не через прямой публичный путь.

## 3. Важное уточнение: proposal version ≠ document metadata ≠ physical file

В этой теме нужно жёстко разделять три понятия:

```text
proposal version;
document metadata;
physical file.
```

### Proposal version

Это бизнес-версия договорного предложения.

Она отвечает на вопросы:

```text
кто отправил версию;
когда отправил;
к какому договорному обмену она относится;
какой статус имеет;
является ли она актуальной;
принята ли она;
заменена ли встречной версией;
с каким документом связана.
```

### Document metadata

Это запись в БД, которая связывает бизнес-версию с physical file.

Она может включать:

```text
идентификатор;
связь с версией договорного предложения;
исходное имя файла;
внутренний storage key / storage file name;
путь хранения, если используется;
тип файла, если сохраняется;
размер файла, если сохраняется;
дату загрузки;
загрузившего пользователя или сторону, если сохраняется.
```

### Physical file

Это физическое содержимое документа.

Оно хранится:

```text
в файловом хранилище;
в рамках текущего scope — в простой директории;
доступ к нему выполняется через backend.
```

Безопасная формулировка:

> Версия договорного предложения является бизнес-объектом договорного обмена, document metadata связывает эту версию с файлом, а physical file хранит только байты документа. Такое разделение позволяет сохранить историю обмена, контролировать доступ и не смешивать бизнес-логику с файловой инфраструктурой.

## 4. Принятые уточнения

1. Файл договорного предложения прикрепляется как готовый файл.
2. Система не генерирует договор автоматически.
3. Договорный обмен строится вокруг версий договорного предложения.
4. Основной бизнес-объект договорного обмена — версия предложения, а не файл.
5. Файл является приложением к версии предложения.
6. Версия предложения и physical file — разные понятия.
7. Новая версия не должна появляться через незаметную перезапись старого файла.
8. После отправки версии связанный файл целесообразно рассматривать как неизменяемое приложение к этой версии.
9. Если сторона отправляет новый документ, он должен сохраняться как новая версия предложения с новой metadata-записью.
10. Связь версии с файлом выполняется через metadata/document ref.
11. Возможный repo-term для metadata/document ref — `AgreementDocumentRef`.
12. Метаданные хранятся в БД.
13. Физический файл хранится отдельно.
14. По текущему scope physical file можно описывать как файл в директории.
15. Backend отвечает за upload, download, metadata и проверку доступа.
16. Frontend только выбирает файл, отправляет его через API, запрашивает файл и показывает результат.
17. Domain layer не хранит байты файла.
18. Domain layer не должен зависеть от пути файловой системы.
19. Domain layer может знать о факте документной ссылки, но не о physical path, storage key, MIME-type или stream.
20. `DocumentRef` в domain layer не равен полной storage metadata.
21. `OriginalFileName` и `StorageKey` нужно разделять.
22. `OriginalFileName` нужен для отображения пользователю.
23. `StorageKey` нужен backend для безопасного поиска файла.
24. Доступ к файлу должен идти через backend, потому что backend проверяет связь файла с заявкой, договорным обменом и ролью пользователя.
25. Download должен начинаться с metadata и проверки доступа, а не с прямого обращения к файловому пути.
26. Договорные файлы не должны раздаваться как публичные static files.
27. Не заявлять прямой public URL как основной способ доступа.
28. Metadata и physical file должны создаваться согласованно.
29. Если файл не удалось сохранить, версия не должна считаться успешно отправленной.
30. Если metadata не удалось сохранить, файл не должен становиться документом процесса.
31. Ошибки upload/download не должны раскрывать внутренние пути файловой системы или сведения о чужих документах.
32. Не заявлять полноценную СЭД.
33. Не заявлять ЭДО, ЭП, юридическое подписание.
34. Не заявлять промышленный object storage как текущую обязательную реализацию.
35. Не заявлять антивирусную проверку, checksum/hash, аудит скачиваний без repo-check.
36. Точные поля metadata нужно сверить по repo.
37. Точные ограничения типа/размера файла нужно сверить по repo.
38. Реализация upload/download endpoints относится к 2.5 и главе 3.

## 5. Сценарная основа темы

Файловое хранение появляется не само по себе, а из сценариев договорного обмена.

Основные сценарии:

```text
сотрудник начинает договорный обмен после одобрения заявки;
сотрудник отправляет клиенту версию договорного предложения;
клиент просматривает версию;
клиент может отправить встречную версию, если это подтверждено моделью;
клиент или сотрудник получает файл версии;
стороны видят историю версий в рамках одного договорного обмена.
```

Для хранения файлов это означает:

```text
нужно хранить physical file;
нужно хранить metadata файла;
нужно знать, к какой версии предложения относится файл;
нужно знать, в каком договорном обмене появилась версия;
нужно знать, с какой заявкой связан обмен;
нужно знать отправителя версии;
нужно проверять доступ перед выдачей файла;
нужно не ломать историю обмена при появлении нового файла.
```

Нормализация старых элементов:

| Старый элемент                    | Как писать сейчас                   |
| --------------------------------- | ----------------------------------- |
| `ContractDraft`                   | версия договорного предложения      |
| `ContractDraftSent`               | не использовать без repo-check      |
| автоматическая генерация договора | не заявлять                         |
| PDF generation                    | не заявлять без repo-check          |
| email-уведомление о файле         | future work / не обязательная часть |
| юридическое подписание            | не входит в scope                   |
| СЭД/ЭДО                           | не заявлять                         |

Рабочая формулировка:

> Файловое хранение проектируется как часть договорного обмена. Файл появляется в системе не отдельно, а как документ, связанный с конкретной версией договорного предложения, отправителем и договорным обменом.

## 6. Зачем эта тема нужна

### На уровне темы

Тема нужна, чтобы показать, что файл в системе имеет бизнес-контекст.

Без metadata файл был бы просто объектом файловой системы:

```text
непонятно, к какой заявке он относится;
непонятно, кто его отправил;
непонятно, какая это версия;
непонятно, кто может его получить;
сложно показать историю договорного обмена;
невозможно безопасно проверить доступ через бизнес-связи.
```

С metadata файл становится частью процесса:

```text
файл связан с версией предложения;
версия связана с договорным обменом;
обмен связан с одобренной заявкой;
доступ проверяется через backend;
frontend показывает файл в нужном контексте.
```

### На уровне пункта 2.4

Пункт 2.4 должен раскрыть:

```text
логическую модель хранения;
метаданные документов;
физическое файловое хранение;
связь файла с договорным обменом;
доступ к файлам через backend;
границы текущей модели хранения.
```

Текущий драфт закрывает вторую часть:

```text
файловое хранение и метаданные договорных документов
```

### На уровне всей главы 2

Тема связывает:

```text
2.2 договорный обмен и версии
→ 2.3 storage boundary
→ 2.4 metadata + file storage
→ 2.5 upload/download API
→ 2.6 UI отображения версий и файлов
→ глава 3 реализация хранения и тесты
```

## 7. Содержание темы

### 7.1 Файл как часть версии договорного предложения

Файл не должен быть самостоятельным объектом без связи с процессом.

Он должен быть связан с:

```text
договорным обменом;
версией договорного предложения;
отправителем версии;
заявкой, через договорный обмен;
metadata-записью.
```

Рабочая формулировка:

> Файл договорного предложения рассматривается как прикреплённый документ конкретной версии. Поэтому он хранится не как отдельный неструктурированный объект, а как часть цепочки “договорный обмен → версия предложения → метаданные документа → физический файл”.

---

### 7.2 Неизменяемость файла после отправки версии

После отправки версии договорного предложения связанный с ней файл лучше рассматривать как неизменяемое приложение к этой версии.

Если клиент или сотрудник хочет отправить другой файл, это должно быть не “заменой файла у старой версии”, а созданием новой версии предложения:

```text
AgreementProposalVersion v1
  → document A

AgreementProposalVersion v2
  → document B
```

Это важно для истории договорного обмена:

```text
каждая версия сохраняет документ, который был отправлен в конкретный момент;
стороны видят историю обмена;
старое предложение не подменяется незаметно;
новый документ становится новым фактом обмена.
```

Рабочая формулировка:

> После отправки версии договорного предложения связанный с ней файл целесообразно рассматривать как неизменяемое приложение. Если сторона отправляет новый вариант документа, он должен сохраняться как новая версия предложения с новой metadata-записью, а не как перезапись старого файла.

---

### 7.3 Document metadata как связующее звено

Document metadata связывает бизнес-контекст и physical file.

Metadata отвечает на вопросы:

```text
что это за файл;
к какой версии предложения он относится;
где физически расположен файл;
какое имя файла видел пользователь;
когда файл был загружен;
кто или какая сторона загрузила файл;
как backend может найти файл;
можно ли показать файл пользователю.
```

Рабочая формулировка:

> Metadata-запись является связующим звеном между предметной моделью и файловым хранилищем. Она позволяет сохранить информацию о документе в БД, а физическое содержимое оставить в файловом хранилище.

---

### 7.4 Original file name и storage key

В metadata стоит разделять имя файла, которое видел пользователь, и внутренний ключ хранения.

```text
OriginalFileName:
  имя файла, загруженное пользователем;
  используется для отображения и скачивания.

StorageKey / StorageFileName:
  внутренний безопасный идентификатор файла;
  используется backend для поиска файла в хранилище.
```

Почему это важно:

```text
пользовательское имя может содержать пробелы, кириллицу и спецсимволы;
имя может совпадать с именем другого файла;
нельзя полагаться на original file name как на уникальный путь;
storage key должен генерироваться сервером.
```

Рабочая формулировка:

> В metadata целесообразно разделять исходное имя файла и внутренний ключ хранения. Пользовательское имя нужно для отображения, а storage key — для безопасного поиска physical file на стороне backend.

---

### 7.5 Возможный состав document metadata

Минимальная metadata-модель:

```text
document id;
proposal id;
original file name;
storage file name / storage key;
storage path, если используется;
uploaded at;
uploaded by / sender side, если сохраняется;
file size, если сохраняется;
content type, если сохраняется.
```

Осторожная версия для финального текста:

> Metadata документа может включать идентификатор, связь с версией предложения, имя файла, путь или ключ хранения, дату загрузки и служебные сведения, необходимые backend для выдачи файла пользователю.

Что не утверждать без проверки:

```text
checksum/hash;
virus scan status;
file preview status;
digital signature status;
audit trail;
retention policy;
version hash;
immutable archive marker.
```

---

### 7.6 Физическое хранение файла

Physical file хранится отдельно от БД и domain layer.

По текущему scope:

```text
файл хранится в простой директории;
backend записывает файл;
backend читает файл;
metadata хранит путь или ключ;
frontend не знает physical path;
domain layer не знает physical path.
```

Рабочая формулировка:

> В рамках текущего scope достаточно простой модели файлового хранения: физический файл размещается в директории, а в БД сохраняется metadata-запись с ключом или путём к этому файлу. При этом доступ к файлу выполняется через backend.

---

### 7.7 Почему файл не хранится напрямую в БД как основной подход

В этом драфте не нужно спорить, что “нельзя хранить файлы в БД вообще”. Нужно аккуратно объяснить выбранную модель.

Причины разделения:

```text
БД нужна для структурированных связей;
файл является бинарным содержимым;
metadata достаточно для связи файла с процессом;
файловое хранилище проще для physical content;
модель легче заменить на object storage в будущем.
```

Рабочая формулировка:

> В проектируемой модели БД используется для структурированных данных и metadata, а физическое содержимое файла выносится в файловое хранилище. Это упрощает разделение ответственности: БД хранит связи и контекст, а файловое хранилище — байты документа.

---

### 7.8 Загрузка файла: общий flow

Сценарий загрузки:

```text
пользователь выбирает файл во frontend;
frontend отправляет файл и данные версии на backend;
backend API принимает upload request;
application layer проверяет доступ к договорному обмену;
domain layer проверяет допустимость добавления версии;
backend сохраняет physical file;
backend сохраняет metadata в БД;
версия предложения связывается с metadata;
frontend получает результат и показывает новую версию.
```

Рабочая формулировка:

> При загрузке файла frontend только передаёт выбранный файл через API. Серверная часть проверяет доступ, сохраняет файл, создаёт metadata-запись и связывает её с версией договорного предложения.

---

### 7.9 Согласованность metadata и physical file при загрузке

Поскольку metadata и physical file хранятся в разных местах, backend должен контролировать их согласованность.

Возможные некорректные ситуации:

```text
metadata создана, но файл не сохранён;
файл сохранён, но metadata не создана;
metadata указывает на неправильный storage key;
версия предложения создана, но связанный файл отсутствует.
```

Для текущего scope достаточно зафиксировать принцип:

```text
если файл не удалось сохранить, версия предложения не должна считаться успешно отправленной;
если metadata не удалось сохранить, файл не должен становиться доступным как документ системы;
download всегда начинается с metadata и проверки доступа;
файл без metadata не является документом процесса.
```

Рабочая формулировка:

> Загрузка файла должна рассматриваться как единый сценарий: серверная часть проверяет доступ, сохраняет physical file, создаёт metadata и связывает её с версией предложения. Если один из шагов завершился ошибкой, система не должна показывать пользователю новую версию как успешно созданную.

---

### 7.10 Получение файла через metadata

Получение файла должно начинаться не с прямого обращения к файловому хранилищу, а с поиска metadata-записи.

Правильный порядок:

```text
1. Пользователь запрашивает документ.
2. Backend проверяет авторизацию.
3. Backend находит metadata.
4. Backend через metadata определяет proposal / exchange / request.
5. Backend проверяет доступ к процессу.
6. Backend по storage key получает physical file.
7. Backend возвращает файл или ошибку.
```

Рабочая формулировка:

> Metadata является входной точкой для получения файла. Backend сначала определяет бизнес-контекст документа и проверяет доступ пользователя, и только после этого обращается к physical file storage.

---

### 7.11 Цепочка проверки доступа к файлу

Доступ к файлу определяется не самим файлом и не его именем, а связью файла с предметным процессом.

Логическая цепочка:

```text
Physical file
← AgreementDocumentRef
← AgreementProposalVersion
← AgreementProposalExchange
← ConnectionRequest
← ApplicantParty / ClientAccount
```

Для клиента это означает:

```text
файл доступен, если договорный обмен относится к заявке его заявителя.
```

Для сотрудника:

```text
файл доступен, если сотрудник имеет право работать с заявками/договорным обменом в своей зоне.
```

Рабочая формулировка:

> Проверка доступа к файлу должна идти через цепочку предметных связей: document metadata связана с версией предложения, версия — с договорным обменом, обмен — с заявкой. Поэтому physical file не должен быть доступен только по знанию пути или имени.

---

### 7.12 Почему договорные файлы не должны раздаваться как static files

Файлы договорных предложений связаны с заявками и доступом пользователей, поэтому их нельзя отдавать как обычные публичные статические файлы.

Плохо:

```text
frontend получает прямой URL на файл в директории;
/uploads/agreement-files/file.pdf доступен напрямую.
```

Лучше:

```text
frontend вызывает backend endpoint;
backend проверяет доступ;
backend возвращает файл или безопасную ошибку.
```

Рабочая формулировка:

> Договорные файлы не должны раздаваться как публичные static files, потому что доступ к ним зависит от заявки, договорного обмена и роли пользователя. Получение файла должно проходить через backend и проверку доступа.

---

### 7.13 Ошибки файлового хранения

Типовые ошибки:

```text
файл не передан;
metadata не найдена;
physical file не найден;
нет доступа к файлу;
действие недоступно для текущего состояния обмена;
файл слишком большой, если ограничение есть;
тип файла недопустим, если ограничение есть;
ошибка сохранения файла.
```

Рабочая формулировка:

> Для файловых операций необходимо предусмотреть обработку ошибок: отсутствие файла, отсутствие metadata, недоступность physical file, отказ в доступе или ошибка сохранения. Эти ошибки должны возвращаться frontend через единый API-формат.

---

### 7.14 Безопасные ошибки файлового доступа

При ошибках файлового доступа важно не раскрывать лишние сведения.

Например:

```text
если metadata существует, но пользователь не имеет доступа,
не нужно сообщать детали чужого документа;

если файл относится к чужой заявке,
ответ может быть таким же, как для отсутствующего файла;

если physical file отсутствует,
frontend должен получить понятную ошибку,
но не внутренний путь файловой системы.
```

Рабочая формулировка:

> Ошибки файлового доступа должны быть понятны пользователю, но не должны раскрывать внутренние пути хранения или сведения о чужих документах. Backend должен возвращать безопасное описание ошибки через API-контракт.

---

### 7.15 Связь file metadata с отправителем

Версия договорного предложения имеет отправителя.

Отправитель может быть:

```text
клиент;
сотрудник.
```

Metadata может хранить:

```text
uploaded by;
sender side;
created by;
связь с proposal sender;
служебную информацию о загрузке.
```

Осторожность:

```text
не утверждать точную модель sender без repo-check;
sender может храниться у proposal, а не у document ref;
metadata может не дублировать отправителя;
важно не создать противоречие между sender proposal и uploader document.
```

Рабочая формулировка:

> Отправитель версии должен быть связан с договорным предложением. Metadata документа может дополнительно хранить сведения о загрузившем пользователе, однако точное место хранения этой информации должно соответствовать реализации модели.

---

### 7.16 Один файл или несколько файлов у версии

Это важный вопрос для repo-check.

Возможные модели:

```text
одна версия → один файл;
одна версия → несколько файлов;
версия может быть без файла, но с комментарием;
файл обязателен для каждой версии.
```

Текущее безопасное предположение:

```text
версия договорного предложения может быть связана с document ref;
точную обязательность файла и кардинальность проверить по repo.
```

Рабочая формулировка:

> В проектном описании можно указать, что версия договорного предложения связывается с документной ссылкой. При этом точная обязательность файла и кардинальность связи должны быть проверены по реализации.

---

### 7.17 Версия предложения как основной бизнес-объект

В договорном обмене основным бизнес-объектом является не файл, а версия договорного предложения.

Версия хранит бизнес-контекст:

```text
кто отправил;
когда отправил;
на какую предыдущую версию отвечает, если такая связь есть;
активна ли версия;
принята ли версия;
заменена ли встречным предложением;
с каким документом связана.
```

Файл является содержимым этой версии, но сам по себе не определяет состояние обмена.

Рабочая формулировка:

> В договорном обмене файл является приложением к версии предложения. Состояние обмена определяется не именем файла и не его физическим расположением, а структурированными данными версии: отправителем, статусом, связью с предыдущей версией и решением стороны.

---

### 7.18 DocumentRef и storage metadata

В domain layer может существовать понятие документной ссылки, но оно не должно включать инфраструктурные детали хранения.

В domain layer достаточно:

```text
DocumentRef exists;
DocumentRef id;
document is attached to proposal version.
```

В infrastructure/storage layer находятся:

```text
storage path;
storage key;
content type;
file size;
physical directory;
file stream.
```

Рабочая формулировка:

> Если domain layer использует документную ссылку, она должна выражать только предметный факт наличия документа у версии предложения. Путь к файлу, ключ хранения, размер и MIME-тип относятся к metadata и infrastructure layer.

---

### 7.19 Domain layer и file metadata

Domain layer не должен зависеть от physical storage.

Domain layer может работать с понятиями:

```text
версия предложения;
документная ссылка;
наличие документа;
отправитель версии;
допустимость новой версии.
```

Domain layer не должен работать с:

```text
путями файловой системы;
байтами файла;
MIME parsing;
stream upload;
директориями;
storage provider.
```

Рабочая формулировка:

> Domain layer может учитывать факт связи версии с документом, но не должен зависеть от того, где и как физически хранится файл. Путь, ключ и файловые операции относятся к infrastructure layer.

---

### 7.20 Storage boundary и заменяемость

Текущий вариант:

```text
metadata в БД;
physical file в директории;
backend контролирует доступ.
```

Возможное развитие:

```text
object storage;
антивирусная проверка;
контроль типов;
аудит скачиваний;
подписанные временные ссылки;
долговременное хранение;
интеграция с ЭДО.
```

Главное:

```text
меняется storage implementation;
не меняется бизнес-смысл версии предложения;
не нужно переписывать domain layer;
frontend продолжает работать через API.
```

Рабочая формулировка:

> Благодаря storage boundary можно изменить способ physical file storage без изменения бизнес-смысла договорного обмена. Для frontend и domain layer файл остаётся документом, связанным с версией предложения, даже если backend меняет механизм хранения.

## 14. Границы файлового хранения

### 14.1 Входит в текущий scope

```text
прикрепление готового файла к версии договорного предложения;
хранение metadata в БД;
хранение physical file отдельно;
простая директория как файловое хранилище;
связь version → metadata → file;
разделение OriginalFileName и StorageKey;
доступ к файлу через backend;
проверка доступа перед выдачей файла;
отображение файла в контексте договорного обмена;
обработка базовых ошибок загрузки/получения;
согласованность metadata и physical file на уровне сценария;
новый документ как новая версия, а не перезапись старого файла.
```

### 14.2 Не входит в текущий scope

```text
полноценная СЭД;
юридически значимый ЭДО;
электронная подпись;
автоматическая генерация договора;
PDF generation как обязательная функция;
совместное редактирование документа;
полнотекстовый поиск по файлам;
антивирусная проверка;
checksum/hash как обязательная часть;
аудит всех скачиваний;
промышленный object storage;
архивное хранение;
retention policy;
версионирование уровня Google Docs;
прямой публичный доступ к файлам;
public static file serving для договорных документов;
email/push-уведомления о файлах как обязательная функция.
```

### 14.3 Направления развития

```text
object storage;
signed temporary links;
file type validation;
file size policies;
antivirus scan;
download audit;
document preview;
integration with EDI/ЭДО;
electronic signature;
retention/archive policies.
```

Рабочая формулировка:

> В текущем scope файловое хранение решает задачу связи договорного предложения с прикреплённым файлом. Более сложные возможности — ЭДО, ЭП, аудит скачиваний, object storage и архивные политики — рассматриваются как направления развития.

## 16. Что требует обоснования

### 16.1 Почему нужен отдельный metadata-объект

Будущая формулировка:

> Отдельная metadata-запись нужна, чтобы связать physical file с предметным процессом. Она показывает, к какой версии договорного предложения относится файл и где backend может найти его physical content.

---

### 16.2 Почему physical file хранится отдельно

Будущая формулировка:

> Физическое содержимое файла имеет другую природу, чем структурированные данные процесса. Поэтому файл хранится отдельно, а БД содержит только metadata и связи.

---

### 16.3 Почему версия предложения важнее файла

Будущая формулировка:

> В договорном обмене основным бизнес-объектом является версия предложения. Файл является приложением к версии и не должен самостоятельно определять состояние обмена.

---

### 16.4 Почему файл версии должен быть неизменяемым

Будущая формулировка:

> Неизменяемость файла после отправки версии позволяет сохранить историю договорного обмена. Новый документ должен создаваться как новая версия предложения, а не как замена файла у уже отправленной версии.

---

### 16.5 Почему OriginalFileName и StorageKey нужно разделять

Будущая формулировка:

> Исходное имя файла используется для отображения пользователю, но не является безопасным техническим идентификатором. Storage key формируется сервером и используется backend для поиска файла в хранилище.

---

### 16.6 Почему metadata и physical file должны создаваться согласованно

Будущая формулировка:

> Metadata и physical file хранятся в разных местах, поэтому backend должен контролировать их согласованность. Если файл не был сохранён или metadata не создана, версия предложения не должна считаться успешно отправленной.

---

### 16.7 Почему download начинается с metadata

Будущая формулировка:

> Получение файла должно начинаться с metadata, потому что metadata связывает physical file с версией предложения, договорным обменом и заявкой. Только после проверки этого контекста backend может получить physical file.

---

### 16.8 Почему доступ к файлу идёт через backend

Будущая формулировка:

> Доступ к файлу должен выполняться через backend, потому что серверная часть проверяет, имеет ли пользователь право видеть заявку, договорный обмен и конкретную версию предложения.

---

### 16.9 Почему нельзя раздавать договорные файлы как static files

Будущая формулировка:

> Договорные файлы нельзя отдавать как публичные static files, потому что доступ к ним зависит от предметных связей и роли пользователя. Прямой URL обходил бы проверку доступа через заявку и договорный обмен.

---

### 16.10 Почему frontend не работает напрямую с файловой системой

Будущая формулировка:

> Frontend не должен обращаться к файловому хранилищу напрямую. Он работает через API, а backend скрывает physical location файла и проверяет доступ.

---

### 16.11 Почему domain layer не хранит байты файла

Будущая формулировка:

> Domain layer содержит бизнес-правила и предметные связи, но не занимается чтением или записью байтов файла. Файловые операции относятся к infrastructure layer.

---

### 16.12 Почему простая директория допустима

Будущая формулировка:

> Для scope ВКР достаточно простой файловой директории: она позволяет показать принцип разделения metadata и physical file без усложнения проекта промышленным object storage.

---

### 16.13 Почему это не СЭД

Будущая формулировка:

> Система хранит файлы как приложения к версиям договорного предложения, но не реализует функции полноценной СЭД: ЭДО, ЭП, сложное согласование, архивное хранение и полный аудит документов.

## 19. Черновые фрагменты будущего текста

### Фрагмент 1 — ввод

После определения общей модели хранения необходимо подробнее рассмотреть хранение файлов договорных предложений. Файл в системе появляется не сам по себе, а как часть версии договорного предложения в рамках договорного обмена.

### Фрагмент 2 — metadata

Для связи файла с предметным процессом используется metadata-запись. Она хранит связь с версией предложения, имя файла, путь или ключ хранения и другие служебные сведения, необходимые backend для доступа к physical file.

### Фрагмент 3 — proposal version, metadata и file

Версия договорного предложения, metadata документа и physical file являются разными элементами модели. Версия хранит бизнес-контекст обмена, metadata связывает версию с файлом, а physical file содержит только байты документа.

### Фрагмент 4 — immutable attachment

После отправки версии договорного предложения связанный с ней файл рассматривается как неизменяемое приложение. Если сторона отправляет новый вариант документа, он сохраняется как новая версия предложения с новой metadata-записью.

### Фрагмент 5 — OriginalFileName и StorageKey

Важно разделять исходное имя файла и внутренний ключ хранения. Исходное имя используется для отображения пользователю, но оно не является безопасным идентификатором: имена могут повторяться, содержать специальные символы и не должны использоваться как путь к файлу. Внутренний storage key формируется сервером и используется для обращения к файловому хранилищу.

### Фрагмент 6 — physical file

Физическое содержимое файла хранится отдельно от структурированных данных. В рамках текущего scope достаточно простой файловой директории, тогда как в БД сохраняется metadata.

### Фрагмент 7 — upload

При загрузке файла frontend передаёт файл через API. Backend проверяет доступ, сохраняет physical file, создаёт metadata-запись и связывает её с версией договорного предложения.

### Фрагмент 8 — consistency

Загрузка файла должна рассматриваться как единый сценарий. Если physical file не был сохранён или metadata не была создана, новая версия предложения не должна показываться пользователю как успешно отправленная.

### Фрагмент 9 — download

Получение файла выполняется через backend. Сервер сначала находит metadata, определяет связанную версию, договорный обмен и заявку, проверяет доступ пользователя и только после этого получает physical file из хранилища.

### Фрагмент 10 — access chain

Доступ к файлу определяется через цепочку предметных связей: metadata связана с версией предложения, версия — с договорным обменом, обмен — с заявкой. Поэтому physical file не должен быть доступен только по знанию пути или имени.

### Фрагмент 11 — no static files

Договорные файлы не должны раздаваться как публичные static files, потому что доступ к ним зависит от заявки, договорного обмена и роли пользователя. Получение файла должно проходить через backend и проверку доступа.

### Фрагмент 12 — safe errors

Ошибки файлового доступа должны быть понятны пользователю, но не должны раскрывать внутренние пути хранения или сведения о чужих документах. Backend должен возвращать безопасное описание ошибки через API-контракт.

### Фрагмент 13 — domain boundary

Domain layer не должен зависеть от путей файловой системы и деталей хранения. Он может учитывать связь версии с документом, но чтение и запись файла относятся к infrastructure layer.

### Фрагмент 14 — не СЭД

Предложенная модель не является полноценной СЭД. Она не включает электронную подпись, юридически значимый ЭДО, промышленное архивное хранение и полный аудит файловых операций.

### Фрагмент 15 — расширяемость

Разделение metadata и physical file позволяет в дальнейшем заменить простое файловое хранение на object storage или добавить дополнительные проверки файлов без изменения бизнес-смысла договорного обмена.

## 23. Итоговая формула темы

```text
файловое хранение проектируется вокруг договорного обмена;

файл не существует отдельно от процесса:
он связан с версией договорного предложения;

proposal version — это бизнес-версия предложения;

document metadata — мост между бизнес-версией и файлом;

physical file — только байты документа;

metadata хранится в БД,
потому что она связывает файл с бизнес-контекстом:
версией, договорным обменом, отправителем и заявкой;

physical file хранится отдельно,
в рамках текущего scope — в простой файловой директории;

original file name нужен пользователю;

storage key нужен backend;

public file URL не является основным способом доступа;

frontend выбирает файл,
отправляет его через API
и показывает результат;

backend проверяет доступ,
сохраняет physical file,
создаёт metadata
и выдаёт файл пользователю только после проверки прав;

download идёт через metadata и проверку доступа,
а не через прямой путь к файлу;

application layer координирует сценарий upload/download;

domain layer проверяет предметную допустимость версии,
но не хранит байты файла,
не знает storage path
и не зависит от файловой системы;

новый документ после отправки — это новая версия,
а не перезапись старого файла;

ошибки upload/download должны быть безопасными:
без раскрытия internal path
и сведений о чужих документах;

такая модель не является полноценной СЭД,
не включает ЭДО,
ЭП,
юридическое подписание,
object storage
и полный аудит документов;

разделение proposal version,
document metadata
и physical file
делает модель понятной,
не загрязняет business logic,
защищает историю договорного обмена
и позволяет в будущем заменить способ хранения
без изменения бизнес-смысла договорного обмена.
```
