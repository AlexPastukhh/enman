## 5. Пункт 2.2 — Проектирование предметной модели и жизненных циклов

### Что раскрыть

```text
ClientAccount — учётная запись клиента;
ApplicantParty — заявитель;
ConnectionRequest — заявка / клиентская заявка;
RequestReview — рассмотрение заявки;
StartReview — начало рассмотрения;
Employee — сотрудник;
AgreementProposalExchange — договорный обмен;
AgreementProposal — версия договорного предложения;
AgreementDocumentRef — ссылка и метаданные договорного документа;
жизненный цикл заявки;
жизненный цикл договорного обмена.
```

### Обязательные смысловые акценты

```text
клиент ≠ заявитель;
заявка имеет явный жизненный цикл и рассматривается сотрудником;
рассмотрение заявки моделируется как часть заявки, если это подтверждается repo;
договорный обмен — это обмен версиями договорных предложений, а не один файл;
AgreementDocumentRef — ссылка/метаданные документа, а не байты файла;
физическое хранение файла относится к инфраструктуре.
```

### Что не делать

```text
не сводить договорный обмен к одному прикреплённому файлу;
не называть систему полноценной СЭД;
не утверждать юридически значимый ЭДО;
не утверждать электронную подпись;
не вводить старые термины без проверки.
```

### Возможные визуалы

```text
диаграмма предметной модели;
диаграмма жизненного цикла заявки;
диаграмма жизненного цикла договорного обмена;
таблица “сущность → ответственность → связи”.
```

## 6. Пункт 2.3 — Проектирование архитектуры web-приложения

### Что раскрыть

```text
клиент-серверная структура;
frontend / React;
backend / ASP.NET Core API;
application layer;
domain layer;
persistence / SQL Server;
file storage;
ответственность frontend;
ответственность backend;
вертикальные срезы как способ проектирования сценариев;
границы текущего scope и будущие интеграции.
```

### Главная мысль

Архитектура должна объяснить, как проектные сценарии распределяются между клиентской частью, серверной частью, доменной логикой, хранением данных и файловым хранилищем.

### Про вертикальные срезы

Вертикальные срезы можно упоминать в главе 2 как способ проектирования сценариев:

```text
сценарий пользователя
→ API
→ application logic
→ domain model
→ persistence
→ UI response.
```

Но подробную реализацию срезов, checklist, тесты и конкретные файлы кода нужно оставить для главы 3.

### Возможные визуалы

```text
общая архитектурная схема;
схема ответственности frontend/backend;
схема вертикального среза как проектной единицы сценария;
таблица “слой → ответственность”.
```

## 7. Пункт 2.4 — Проектирование хранения данных и файлов

### Что раскрыть

```text
структурированные данные в SQL Server;
основные таблицы и связи;
хранение учётных записей, заявителей, заявок, рассмотрения, договорного обмена, версий предложений;
хранение файлов договора отдельно от БД;
в БД хранятся метаданные и ключ/путь файла;
простое файловое хранилище — директория;
система не является полноценной СЭД.
```

### Главная мысль

SQL Server хранит структурированные данные и метаданные, а физический файл договора хранится отдельно в простом файловом хранилище. Это нужно для поддержки договорного обмена, но не превращает систему в промышленное файловое хранилище или СЭД.

### Важные границы

```text
AgreementDocumentRef — это ссылка и метаданные договорного документа;
байты файла не являются частью доменной сущности;
физическое хранение файла — инфраструктурная ответственность;
простая директория допустима для scope ВКР;
промышленный storage service — дальнейшее развитие.
```

### Возможные визуалы

```text
ERD / схема данных;
схема “SQL Server метаданные → файловое хранилище”;
таблица “данные → где хранятся → зачем нужны”.
```

## 8. Пункт 2.5 — Проектирование API и взаимодействия frontend/backend

### Что раскрыть

```text
группы API по сценариям;
flow создания заявки;
flow рассмотрения заявки;
flow договорного обмена;
OpenAPI как структурный контракт;
generated constants как семантический контракт;
ProblemDetails как единый формат ошибок;
связь API с UI и предметной моделью.
```

### Главная мысль

API должен быть показан как проектный контракт между frontend и backend, а не как длинный список endpoint-кода. Нужно объяснить, какие группы сценариев поддерживаются API и как единый формат ошибок помогает согласовать поведение интерфейса и сервера.

### Важные акценты

```text
OpenAPI задаёт структурный контракт;
generated constants уменьшают расхождение frontend/backend по статусам, типам и значениям;
ProblemDetails используется как единый формат ошибок;
API группируется по сценариям, а не просто по техническим файлам.
```

### Возможные визуалы

```text
схема взаимодействия frontend → API → application/domain/persistence;
таблица “scenario → API group → UI screen”;
схема обработки ошибок через ProblemDetails.
```

## 11. Устаревшие или опасные источники и термины

### Источники, которые нельзя брать как source of truth без проверки

```text
planning/use-cases.md;
vkr-clean/README.md.
```

### Почему осторожно

`planning/use-cases.md` может содержать старые или устаревшие элементы:

```text
L1/L2/L3 labels;
Submitted;
Email-сервис как L1;
подача заявки со статусом Submitted;
Worker;
DocumentFileRef;
старый SC-14 как Client Data Verification.
```

`vkr-clean/README.md` может overclaim document/email flow. Поэтому email notification нельзя заявлять как реализованную функцию без проверки кода.

### Актуальные замены

| Не использовать без проверки | Использовать |
|---|---|
| `Worker` | `Employee` |
| `DocumentFileRef` | `AgreementDocumentRef` |
| `SC-14 Client Data Verification` | `SC-14 Agreement Documents / AgreementDocumentRef`, если подтверждено repo |
| `Submitted` как текущий статус заявки | проверить актуальную модель |
| `Email service` как реализованный L1 scope | не заявлять без проверки |
| `L1/L2/L3` как значимые категории ВКР | не использовать как структуру главы |

## 13. Главные акценты главы 2

1. Клиент ≠ заявитель.
2. Заявка имеет явный жизненный цикл и рассматривается сотрудником.
3. Рассмотрение заявки моделируется как часть заявки, а не отдельный корневой процесс, если это подтверждается repo.
4. Договорный обмен — это обмен версиями договорных предложений.
5. `AgreementDocumentRef` — это ссылка/метаданные документа, а не байты файла.
6. Физическое хранение файла относится к инфраструктуре.
7. Frontend/backend согласуются через API-контракт, OpenAPI и генерируемые типы/константы.
8. UI проектируется вокруг пользовательских сценариев и состояний интерфейса.
9. Вертикальные срезы можно упоминать в главе 2 как способ проектирования сценариев.
10. Подробную реализацию слайсов, тесты и checklist оставить для главы 3.
