## 1.1 Состав solution

```text

EnergyManagement.Tools
```

Это подтверждает, что решение организовано как набор проектов, а не как один общий проект без разделения ответственности. 

---

## 1.2 Серверная часть

`EnergyManagement.Server` — ASP.NET Core web-проект на `.NET 8`. В нём подключены Dapper, FluentValidation, MediatR, Entity Framework Core, SQL Server provider, Serilog, Swashbuckle/OpenAPI, SpaProxy и Docker-related tools. Серверный проект ссылается на `Domain.EnergyManagement` и клиентский проект. 

Для текста ВКР из этого следует:

> Серверная часть является центром выполнения сценариев: принимает API-запросы, валидирует данные, вызывает прикладную логику, работает с доменной моделью и сохраняет результат.

---

## 1.3 Доменный проект

`Domain.EnergyManagement` — отдельный `.NET 8` проект. Он вынесен отдельно от frontend, controllers, API и persistence-каталогов серверного проекта. 

Важное уточнение:

> Доменный проект физически изолирует предметную модель от web-слоя, контроллеров, миграций БД и клиентского интерфейса.

Но нельзя писать, что домен вообще “без внешних зависимостей”, потому что в `.csproj` есть NuGet-зависимости. Правильнее:

> Домен отделён от внешних зависимостей приложения: web/API/persistence/UI, но может использовать небольшие технические библиотеки, не привязывающие его к серверной инфраструктуре.

---

## 1.4 Клиентская часть

`energymanagement.client` использует React, TypeScript, Vite, React Router, TanStack React Query, React Hook Form, Zod, Vitest, Playwright и `openapi-typescript`. 

По коду клиентского входа видно:

* `main.tsx` подключает стили и рендерит `App`; 
* `App.tsx` подключает `AppProviders` и `RouterProvider`; 
* `AppProviders` подключает `QueryClientProvider`, `PageErrorProvider` и `SessionProvider`; 
* `router.tsx` задаёт маршруты для главной страницы, входа, регистрации, аккаунта, клиентских заявок, сотруднических заявок, договорных обменов и тестового UI; 
* `clientRoutes.ts` централизует URL-маршруты приложения. 

---

## 1.5 Клиентская read/command архитектура

В planning-документе по клиентской архитектуре зафиксировано разделение:

```text
entities/* — read-side business/entity API, read hooks, read models, display UI
features/* — command/user-action API, mutation hooks, forms/actions, command feedback
shared/* — общая инфраструктура
widgets/* — крупные переиспользуемые составные UI-блоки
```

То есть на клиенте `entities` не нужно объяснять как “доменные сущности” в backend-смысле. Это именно read-side слой клиентского приложения. 

Практический пример из кода:

* сессия оформлена как entity/read-side модуль: `SessionProvider` получает состояние сессии через `useSessionQuery`, а тот вызывает API-функцию `getCurrentSession`;   
* общий API-transport находится в `shared/api/fetchJson.ts` и обрабатывает ошибки, ProblemDetails, CSRF/antiforgery и `204 No Content`; 
* создание заявки реализовано как страница + feature: page-level компонент загружает данные и управляет навигацией, UI формы вынесен в feature, а отправка формы, mutation, invalidation query и преобразование ошибок находятся в feature model.

## 3.1 Структура программного решения и организация реализации

В предыдущей главе были спроектированы основные части web-приложения: пользовательский интерфейс, API, прикладная логика, модель предметной области, хранение данных и документов, а также средства выполнения работы. В третьей главе рассматривается реализация этих проектных решений. Первый раздел главы задаёт общую карту реализации: показывает состав программного решения, назначение основных проектов и связь между проектными зонами второй главы и фактической структурой кода.

Реализованное приложение представляет собой клиент-серверное web-приложение. Клиентская часть отвечает за отображение интерфейса, ввод данных, работу с формами, списками заявок и договорными предложениями. Серверная часть предоставляет API, выполняет прикладные сценарии, проверяет входные данные и права доступа, обращается к модели предметной области и сохраняет результат в базе данных или связанном файловом хранилище.

Функционально реализация охватывает несколько основных контуров: работу пользователя с аккаунтом, работу с заявителями, создание и просмотр заявок, обработку заявок сотрудником, принятие решения по заявке, договорный обмен и работу с версиями договорных предложений. Эти контуры далее раскрываются в отдельных разделах главы.

Программное решение организовано как набор проектов. В состав решения входят серверная часть, клиентское приложение, отдельный проект предметной модели, тестовые проекты и вспомогательные инструменты. Такая структура позволяет разделить пользовательский интерфейс, API, прикладную логику, предметные правила, хранение данных, тестирование и технические задачи.

Серверный проект является центральной точкой выполнения сценариев приложения. Он принимает HTTP-запросы от клиентского интерфейса, выполняет проверку данных, вызывает прикладную логику, обращается к доменной модели и сохраняет результат. Внутри серверного проекта выделены каталоги для API, прикладной логики, инфраструктуры, миграций и доступа к данным. Такое разделение позволяет не смешивать обработку HTTP-запроса, выполнение сценария, предметные правила и технические детали хранения.

Отдельный проект `Domain.EnergyManagement` содержит предметные объекты и правила процесса. Его выделение важно не только организационно, но и технически: предметная модель физически отделена от web-слоя, контроллеров, миграций базы данных и клиентского интерфейса. Серверный проект ссылается на доменный проект, но доменный проект не зависит от серверной инфраструктуры. Благодаря этому правила жизненного цикла заявки, рассмотрения и договорного обмена остаются выраженными отдельно от способов их вызова и сохранения.

Клиентский проект отвечает за пользовательский интерфейс. На верхнем уровне клиентское приложение имеет входную точку, компонент приложения, общие провайдеры и маршрутизатор. Входная точка `main.tsx` подключает стили и запускает компонент `App`. Компонент `App` подключает провайдеры приложения и маршрутизатор. Провайдеры отвечают за работу с серверными данными, состоянием сессии и ошибками страницы. Маршрутизатор связывает URL-адреса приложения со страницами клиента и сотрудника.

Внутри клиентского проекта выделены каталоги `app`, `pages`, `entities`, `features`, `widgets` и `shared`. Каталог `app` содержит общую конфигурацию приложения, провайдеры и маршрутизацию. Каталог `pages` содержит route-level страницы приложения, которые собирают данные и действия для конкретного пользовательского экрана. Каталог `entities` используется для read-side модулей: чтения данных, query hooks, моделей отображения и read-only компонентов. Каталог `features` содержит пользовательские действия: формы, кнопки, mutation hooks, отправку команд на сервер и отображение результата действия. Каталог `shared` содержит общую инфраструктуру: API-transport, сгенерированные типы, обработку ошибок, конфигурацию маршрутов и переиспользуемые UI-элементы. Каталог `widgets` используется для крупных составных блоков интерфейса, которые могут переиспользоваться на нескольких страницах.

Такое разделение помогает не смешивать чтение данных и изменение состояния. Данные, которые нужны для отображения страницы, размещаются в read-side модулях `entities`. Действия пользователя, которые изменяют состояние системы, размещаются в `features`. Например, чтение текущей сессии относится к read-side логике, а отправка формы создания заявки относится к пользовательскому действию. При этом общая инфраструктура HTTP-запросов, обработки ошибок и сгенерированных API-типов остаётся в `shared`, чтобы не дублироваться между разными страницами и сценариями.

Верхний уровень клиентского приложения представлен в таблице 3.2.

**Таблица 3.2 — Верхний уровень клиентского приложения**

| Часть frontend  | Назначение                                                                                   |
| --------------- | -------------------------------------------------------------------------------------------- |
| `main.tsx`      | входная точка клиентского приложения                                                         |
| `app/App.tsx`   | подключение провайдеров и маршрутизатора                                                     |
| `app/providers` | общие провайдеры приложения: серверные данные, сессия, ошибки страницы                       |
| `app/router`    | маршрутизация страниц                                                                        |
| `pages`         | route-level страницы приложения                                                              |
| `entities`      | read-side модули: чтение данных, query hooks, модели отображения и read-only UI              |
| `features`      | command/user-action модули: формы, действия, mutation hooks и feedback                       |
| `shared`        | общая инфраструктура: API-transport, generated API types, ошибки, конфигурация, UI-примитивы |
| `widgets`       | крупные переиспользуемые составные UI-блоки                                                  |

Для локальной разработки клиентская и серверная части запускаются раздельно. Клиентское приложение работает через Vite, серверная часть запускается как ASP.NET Core-приложение, а запросы клиентской части к API направляются на сервер. Такая схема позволяет разрабатывать интерфейс и сервер независимо, сохраняя клиент-серверный характер приложения. Подробный порядок запуска рассматривается далее в разделе, посвящённом запуску и демонстрации работы приложения.

Тестовые и инструментальные проекты вынесены отдельно от основной реализации. Это позволяет проверять предметную логику, серверное взаимодействие и вспомогательные технические механизмы, не смешивая тестовую инфраструктуру с пользовательскими сценариями приложения. Наличие инструментального проекта также помогает поддерживать технические артефакты, например API-спецификацию и тестовую базу данных.

Связь структуры реализации с проектными решениями второй главы показана в таблице 3.3.

**Таблица 3.3 — Соответствие проектных зон и реализации**

Далее каждая из этих частей рассматривается подробнее с точки зрения реализованных сценариев, используемых механизмов и проверки работоспособности.
