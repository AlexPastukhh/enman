# Topic-драфт 3.2.4

## Реализация рассмотрения заявки сотрудником

**Статус:** draft v1 / уточнён по source-pass заметке пользователя / требует финального repo-check.
**Единая идея:** рассмотрение заявки сотрудником раскрывается как сценарное поведение: сотрудник открывает заявку, начинает рассмотрение, система фиксирует сотрудника и время, затем сотрудник принимает решение — одобряет или отклоняет заявку.

## 0. Source-pass

Для главы 3 нужно читать не только domain draft и slice drafts, но и сценарные спецификации. Иначе возникает риск описывать реализацию только “из классов”, а не из поведения приложения.

Для каждого пункта используется порядок:

```text
1. Сценарная текстовая спецификация
   → что должен делать пользователь/сотрудник.

2. Behavior items / scenario data
   → какие состояния, ошибки, блокировки и данные важны.

3. Domain draft
   → какие объекты и правила отвечают за это поведение.

4. Slice draft
   → как сценарий разложен на backend/client/API/test implementation.

5. Repo/code
   → что реально реализовано и какие фрагменты можно показать.
```

Для **3.2.4 “Рассмотрение заявки сотрудником”** основной сценарный источник — `SC-07B — Employee Request Review`. В нём описаны три flow:

```text
start review;
approve review;
reject review.
```

Важно: start review может запускаться из dashboard row или request details action area, но это одно command behavior, а не два разных сценария. Approve не создаёт `AgreementProposalExchange`; reject может иметь optional feedback; approve/reject без started review блокируются; другой сотрудник не может выполнять действия над review, начатым не им.

---

## 1. Основная сценарная цепочка

Пункт 3.2.4 нужно писать не просто как “у заявки есть состояния”, а как сценарное поведение:

```text
Сотрудник открывает заявку
→ начинает рассмотрение
→ система фиксирует сотрудника и время
→ сотрудник принимает решение
→ approve переводит request в Approved
→ reject переводит request в Rejected
→ договорный обмен не создаётся автоматически
```

Начало рассмотрения является отдельным действием. Оно не равно одобрению, не равно отклонению и не запускает договорный обмен. Его смысл состоит в том, что сотрудник берёт заявку в активную обработку, а система фиксирует ответственного сотрудника и момент начала работы.

Одобрение заявки завершает review положительным решением и переводит заявку в состояние `Approved`. Однако это действие не создаёт договорный обмен автоматически. Одобрение только открывает возможность следующего этапа. Договорный обмен начинается отдельным действием сотрудника, когда он отправляет первую версию договорного предложения.

Отклонение заявки завершает review отрицательным решением и переводит заявку в состояние `Rejected`. При этом в сценарной спецификации feedback при отклонении рассматривается как необязательный. Если текущий API делает обратную связь обязательной, это следует описывать как уточнение API-контракта, а не как доменное ограничение.

## 2. Границы и возможный drift

В сценарной спецификации rejection feedback сейчас **optional**, а в одном slice draft для reject было указано, что API requires non-empty feedback. Это потенциальный drift.

Для ВКР безопасная формулировка:

> В сценарной спецификации обратная связь при отклонении рассматривается как необязательная; если текущий API делает её обязательной, это следует описывать как уточнение API-контракта, а не как доменное ограничение.

Это позволяет не смешивать предметное правило и конкретное API-решение.

## 4. Визуальные материалы

Для 3.2.4 подходят:

1. **Диаграмма жизненного цикла рассмотрения заявки**  
   `not started -> started -> approved/rejected`.

2. **Схема ограничения исполнителя review**  
   “начал один сотрудник — завершает тот же сотрудник”.

3. **Скриншот кода метода start review**.

4. **Скриншот кода методов approve/reject или тестов, проверяющих блокировки**.

---

## 5. Короткий вывод

Таким образом, рассмотрение заявки сотрудником является отдельным этапом между созданием заявки и итоговым решением. Модель должна фиксировать, что review начат конкретным сотрудником, что approve/reject невозможны без started review и что другой сотрудник не может завершить review, начатый не им. Одобрение заявки не создаёт договорный обмен автоматически, а только позволяет перейти к следующему самостоятельному сценарию.
