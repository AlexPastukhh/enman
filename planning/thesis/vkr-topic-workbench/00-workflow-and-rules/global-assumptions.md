# Общие допущения и ограничения

Статус: актуально / research bridge учтён

## 1. Рабочая база тем идёт до полных драфтов

Сначала собираются темы, материалы, research-вопросы, визуалы и границы утверждений. Полный текст пишется после этого.

## 2. Верхний уровень workbench отражает обязательную структуру ВКР

Верхний уровень — это не “интересные технические темы”, а база содержания ВКР:

```text
введение;
глава 1;
глава 2;
глава 3;
заключение;
производные материалы для ПП/предзащиты.
```

## 3. Русский язык смысловых материалов

Все смысловые блоки ВКР-материалов пишутся на русском языке. Английские термины допускаются только как имена технологий, стандартов, файлов, классов или кода.

## 4. Research не является готовым текстом

Research-отчёты используются как источник ответов на вопросы темы. Их нельзя вставлять буквально большими блоками.

Правильно:

```text
вопрос темы → ответ из research → переработка под наш проект → место в карте будущего текста.
```

## 5. L1/L2 не являются понятиями ВКР

`L1` / `L2` — внутренние planning/implementation labels. В ВКР использовать предметные формулировки:

```text
клиентский поток;
рассмотрение заявки сотрудником;
договорно-документный обмен;
этап реализации;
программный срез.
```

## 6. DDD формулировать осторожно

Использовать:

```text
применяются отдельные принципы предметно-ориентированного проектирования.
```

Не превращать работу в теоретический текст о DDD.

## 7. Документохранилище формулировать осторожно

Можно писать:

```text
договорно-документный обмен;
версии договора;
ссылка на документ и метаданные;
прикреплённый готовый файл.
```

Нельзя без реализации:

```text
полноценное бинарное файловое хранилище;
upload/download;
secure file serving;
юридически значимый электронный документооборот;
электронная подпись;
автоматическая генерация договора.
```

## 8. Договорный этап

Договорный этап не описывать как полностью автоматический.

Корректно:

```text
после одобрения заявки сотрудник может начать договорный этап;
система поддерживает обмен версиями договора;
клиент видит версии, которыми стороны обменивались;
цель этапа — согласовать версию договора.
```

## 9. Внешняя проверка данных — точка расширения

Внешняя проверка данных рассматривается как точка расширения. В текущих ВКР-материалах допустимо описывать демонстрационную кнопку проверки только при явном указании, что реальная внешняя интеграция не реализована.

## 10. Email-уведомления

Не утверждать, что email-уведомления полностью реализованы, пока это не подтверждено репозиторием.

## 11. Предыдущие темы являются примерами

Если не сказано обратное, новые темы и драфты делать по последнему принятому примеру.

## 12. Визуалы персонализируют работу

Рисунки, таблицы и скриншоты должны показывать проектные решения, а не украшать текст.
