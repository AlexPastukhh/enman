## 4.1 Основные таблицы

| Таблица                        | Что хранит                                  |
| ------------------------------ | ------------------------------------------- |
| `client_accounts`              | аккаунты клиентов                           |
| `employees`                    | сотрудников, выполняющих служебные действия |
| `applicant_parties`            | сохранённых заявителей клиента              |
| `connection_requests`          | заявки                                      |
| `request_reviews`              | данные рассмотрения заявки                  |

| `agreement_proposals`          | версии договорных предложений               |

Можно не делать отдельную таблицу `agreement_document_refs`, если metadata документа хранятся прямо в `agreement_proposals`. Но для ВКР отдельная таблица понятнее: она явно показывает, что документ отделён от версии предложения и от физического файла.

## 4.2 Ключевые связи

```text
client_accounts 1 ── * applicant_parties

connection_requests 1 ── 0..1 request_reviews
connection_requests 1 ── 0..1 agreement_proposal_exchanges

agreement_proposal_exchanges 1 ── * agreement_proposals

employees 1 ── * agreement_proposals
```

Главная цепочка:

```text

→ заявители
→ заявки
→ договорный обмен
→ версии предложений
→ ссылки на документы
```

# 6. Важные проектные пояснения

## 6.1 Почему заявка ссылается на заявителя

Заявка должна сохранять `applicant_party_id`, потому что она оформляется от имени конкретного заявителя. Это также защищает историю: если пользователь позднее выберет другого текущего заявителя, старая заявка не изменится.

## 6.2 Почему review можно хранить отдельно

Рассмотрение принадлежит заявке, но его удобно хранить отдельно, потому что у него есть свои поля: кто начал рассмотрение, когда начал, результат, когда завершил. Связь остаётся 1:1 с заявкой.

## 6.3 Почему договорный обмен отдельный

Договорный обмен не является просто полем заявки. У него есть собственный статус, активная версия и история версий. Поэтому для него нужна отдельная таблица, связанная с заявкой.

## 6.4 Почему версии хранятся отдельно

Версии договорных предложений образуют историю обмена. Если хранить только текущий документ, будет потеряна история предыдущих версий. Поэтому каждая версия сохраняется отдельной записью.

## 6.5 Почему документ хранится как ссылка и метаданные

База данных должна хранить не сам файл, а сведения о нём: ключ хранения, исходное имя, тип содержимого, размер. Это позволяет отделить предметный процесс от физического хранения документов.

```dbml
Table client_accounts {
  id bigint [pk]
  email varchar [not null, unique]
  password_hash varchar [not null]
  activation_state varchar [not null]

}

Table employees {
  id bigint [pk]
  email varchar [not null, unique]
  full_name varchar [not null]
  is_active boolean [not null]
}

Table applicant_parties {
  id bigint [pk]
  client_account_id bigint [not null, ref: > client_accounts.id]
  type varchar [not null]
  verification_status varchar [not null]
  full_name varchar
  contact_email varchar [not null]
  phone_number varchar [not null]
  is_current_default boolean [not null]
  created_at timestamp [not null]
}

Table connection_requests {
  id bigint [pk]
  applicant_party_id bigint [not null, ref: > applicant_parties.id]
  status varchar [not null]
  details text [not null]
  object_address text [not null]
  created_at timestamp [not null]
}

Table request_reviews {
  id bigint [pk]
  connection_request_id bigint [not null, unique, ref: > connection_requests.id]
  started_by_employee_id bigint [not null, ref: > employees.id]
  started_at timestamp [not null]
  completed_by_employee_id bigint [ref: > employees.id]
  completed_at timestamp
  decision varchar
  rejection_feedback text
}

Table agreement_proposal_exchanges {
  id bigint [pk]
  connection_request_id bigint [not null, unique, ref: > connection_requests.id]
  client_account_id bigint [not null, ref: > client_accounts.id]
  status varchar [not null]
  active_proposal_version int
  started_by_employee_id bigint [not null, ref: > employees.id]
  started_at timestamp [not null]
  final_refusal_reason text
}

Table agreement_proposals {
  id bigint [pk]
  exchange_id bigint [not null, ref: > agreement_proposal_exchanges.id]
  version_number int [not null]
  sender_type varchar [not null]
  sender_id bigint [not null]
  state varchar [not null]
  comment text
  created_at timestamp [not null]

  indexes {
    (exchange_id, version_number) [unique]
  }
}

Table agreement_document_refs {
  id bigint [pk]
  proposal_id bigint [not null, unique, ref: > agreement_proposals.id]
  storage_key varchar [not null]
  original_file_name varchar [not null]
  content_type varchar [not null]
  size_bytes bigint [not null]
}
```

# 9. Clean text candidate

## 2.6 Проектирование структуры хранения данных и документов

В предыдущем пункте была рассмотрена модель предметной области: аккаунт клиента, заявитель, заявка, рассмотрение заявки, договорный обмен, версии договорных предложений и ссылка на документ. Для работы web-приложения эти объекты должны не только существовать в логике приложения, но и сохраняться в базе данных. Поэтому следующим шагом является проектирование структуры хранения данных и документов.

Структура хранения отличается от модели предметной области. Модель показывает смысл объектов и правила процесса, а структура хранения показывает, как сохранить состояние этих объектов, связи между ними и историю изменений. Например, в предметной модели заявка связана с заявителем и имеет статус. В структуре хранения это отражается через таблицу заявок, поле состояния и ссылку на запись заявителя.

Основными таблицами для хранения данных являются таблицы аккаунтов клиентов, сотрудников, заявителей, заявок, рассмотрений заявок, договорных обменов, договорных предложений и ссылок на документы. Такое разделение соответствует объектам предметной модели и позволяет сохранять как текущее состояние процесса, так и историю договорного обмена.

Заявитель хранится отдельно от аккаунта клиента. Аккаунт определяет пользователя системы и владельца данных, а заявитель содержит данные лица или организации, от имени которых создаётся заявка. Поэтому таблица заявителей должна содержать ссылку на аккаунт клиента. При создании заявки в ней сохраняется ссылка на выбранного заявителя. Благодаря этому ранее созданные заявки остаются связанными с тем заявителем, который был выбран в момент подачи, даже если пользователь позднее изменит текущего или дефолтного заявителя.

Заявка является центральной записью процесса обработки обращения. В таблице заявок необходимо хранить ссылку на заявителя, статус заявки, данные обращения и адрес объекта. Заявка не обязана хранить идентификатор аккаунта клиента напрямую, поскольку владелец может быть определён через связанного заявителя. Такой подход сохраняет связь “аккаунт клиента — заявитель — заявка” и соответствует предметной модели.

Рассмотрение заявки связано с конкретной заявкой. Его можно хранить в отдельной таблице, связанной с заявкой отношением один к одному. В этой таблице фиксируется сотрудник, начавший рассмотрение, время начала, результат рассмотрения, время завершения и возможный комментарий или причина отказа. Отдельное хранение рассмотрения делает структуру более понятной: заявка хранит общий статус, а рассмотрение — сведения о служебном этапе обработки.

Договорный обмен хранится отдельно от заявки, потому что имеет собственное состояние, активную версию и историю предложений. Таблица договорных обменов должна ссылаться на заявку, по которой обмен начат, а также хранить статус обмена и активную версию предложения. Одобрение заявки не создаёт договорный обмен автоматически: запись обмена появляется только при отдельном действии сотрудника, когда он отправляет первую версию договорного предложения.

Версии договорных предложений необходимо хранить отдельными записями. Каждая версия относится к конкретному договорному обмену, имеет локальный номер версии, автора, состояние, комментарий и время создания. Локальный номер версии должен быть уникален внутри одного договорного обмена. Это позволяет сохранять историю обмена и не смешивать версии разных заявок или разных договорных обменов.

Документы договорных предложений в структуре хранения должны быть представлены не байтами файла, а ссылкой и метаданными. Для каждой версии предложения нужно хранить идентификатор файла в хранилище, исходное имя файла, тип содержимого и размер. Сам механизм физического хранения файла относится к инфраструктурной части приложения. Такое разделение позволяет базе данных хранить сведения, необходимые для процесса, но не превращает предметную модель в файловое хранилище.

Связи между таблицами можно представить следующим образом: аккаунт клиента связан с несколькими заявителями; заявитель связан с заявками; заявка может иметь рассмотрение и договорный обмен; договорный обмен содержит несколько версий предложений; каждая версия связана со ссылкой на документ. Для наглядности эта структура может быть представлена в виде ERD-диаграммы.

Таким образом, структура хранения данных и документов обеспечивает сохранение состояния предметной модели. Она позволяет восстановить заявки, их рассмотрение, договорный обмен и историю версий документов, а также служит основой для проектирования API и пользовательского интерфейса.
