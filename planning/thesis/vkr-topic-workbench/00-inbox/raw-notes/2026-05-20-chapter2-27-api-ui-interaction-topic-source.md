# 6. Обновлённый clean text candidate

## 2.7 Проектирование программного взаимодействия и пользовательского интерфейса

После проектирования модели предметной области и структуры хранения данных необходимо определить, как пользователь и сотрудник будут работать с системой через API и пользовательский интерфейс. Если в предыдущих пунктах были рассмотрены объекты приложения и способ их хранения, то в данном пункте определяется программное взаимодействие между клиентской и серверной частями, а также состав основных экранов.

Программное взаимодействие должно строиться вокруг сценариев, выделенных ранее: работы с заявителями, подачи заявки, рассмотрения заявки сотрудником, принятия решения и договорного обмена. Экран пользовательского интерфейса отображает данные, полученные через API, а действие пользователя вызывает API-операцию, которая изменяет состояние предметной модели или возвращает ошибку. После выполнения операции интерфейс должен обновить данные и показать пользователю результат.

В API целесообразно различать операции получения данных и операции изменения состояния. Операции получения данных используются для отображения списков, карточек и деталей объектов: заявителей, заявок, договорных обменов и версий предложений. Операции изменения состояния выполняют действия пользователя или сотрудника: создание заявителя, создание заявки, начало рассмотрения, одобрение или отклонение заявки, начало договорного обмена, отправку версии документа или принятие предложения.

Основные группы API соответствуют ключевым объектам и действиям предметной модели. Для клиента нужны операции работы с заявителями, заявками и договорными обменами. Для сотрудника нужны операции просмотра заявок, начала рассмотрения, принятия решения и работы с договорным обменом. Отдельно выделяются операции работы с документами, поскольку версии договорных предложений связаны с файлами и их метаданными.

**Таблица 2.x — Проектные группы API**

| Группа API         | Назначение                          | Примеры операций                                                  |
| ------------------ | ----------------------------------- | ----------------------------------------------------------------- |
| Аккаунт и сессия   | идентификация пользователя          | войти, выйти, получить текущий профиль                            |
| Заявители          | управление сохранёнными заявителями | список заявителей, создать заявителя, выбрать текущего            |
| Заявки клиента     | работа клиента с заявками           | создать заявку, получить свои заявки, открыть заявку              |
| Заявки сотрудника  | служебная обработка заявок          | список заявок, открыть детали, начать рассмотрение                |
| Решение по заявке  | изменение состояния заявки          | одобрить, отклонить                                               |
| Договорный обмен   | этап после одобрения                | начать обмен, получить детали обмена                              |
| Версии предложений | история договорных документов       | отправить версию, принять предложение, отправить контрпредложение |
| Документы          | передача файлов и метаданных        | загрузить документ, получить сведения о документе                 |

Пользовательский интерфейс должен учитывать роль участника. Для гостя доступны вход и регистрация. Для клиента основными разделами являются создание заявки, список своих заявок, договорные обмены и личный кабинет. Для сотрудника основными разделами являются рабочий список заявок, договорные обмены и личный кабинет. Такое разделение навигации помогает не смешивать клиентские и служебные сценарии.

Клиентский интерфейс должен быть построен вокруг личного кабинета. Пользователь должен иметь возможность управлять заявителями, создавать заявку, просматривать список своих заявок и их состояние. После начала договорного обмена интерфейс должен показывать активное договорное предложение, историю версий и действия, доступные клиенту: принять предложение или отправить свою версию документа.

Сотруднический интерфейс должен предоставлять рабочую область обработки заявок. Сотрудник должен видеть список заявок, открывать подробности, начинать рассмотрение и фиксировать решение. После одобрения заявки интерфейс должен показывать отдельное действие для начала договорного обмена. Это важно, потому что одобрение заявки само по себе не создаёт договорный обмен.

| Заявители                   | список заявителей | создать заявителя      | появляется новая запись                 |
| Заявители                   | список заявителей | выбрать текущего       | меняется шаблон для новых заявок        |
| Создание заявки             | форма заявки      | отправить заявку       | создаётся заявка на рассмотрении        |
| Мои заявки                  | список заявок     | открыть заявку         | показывается статус и результат         |
| Детали заявки сотрудника    | данные заявки     | начать рассмотрение    | заявка становится доступной для решения |
| Рассмотрение заявки         | данные заявки     | одобрить или отклонить | меняется статус заявки                  |
| Договорный обмен            | активная версия   | принять предложение    | обмен завершается принятием             |
| Договорный обмен            | активная версия   | отправить свою версию  | обмен ожидает сотрудника                |
| Договорный обмен сотрудника | версия клиента    | отправить новую версию | обмен ожидает клиента                   |

При проектировании экранов важно учитывать не только основной успешный сценарий, но и состояния интерфейса: загрузку данных, пустой список, ошибку получения данных, отсутствие доступа и успешное выполнение действия. Например, экран “Мои заявки” должен уметь показать список заявок, сообщение об отсутствии заявок и ошибку загрузки. Экран договорного обмена должен показывать активную версию, историю версий и объяснять, почему действие сейчас недоступно.

Пользовательский интерфейс должен предоставлять обратную связь по результатам действий. Ошибки заполнения формы должны отображаться рядом с соответствующими полями, а ошибки общего характера — в области формы. При этом клиентская проверка не заменяет серверную: серверная часть должна окончательно проверять права доступа, состояние процесса и предметные правила. Если сервер отклоняет действие, интерфейс должен показать пользователю понятную причину отказа.

Недоступные действия могут быть скрыты или отключены в интерфейсе, но это не заменяет серверную проверку. Например, если действие “одобрить заявку” недоступно до начала рассмотрения, сервер также должен проверять это правило. Если действие отклонено сервером, интерфейс должен показать пользователю понятную причину отказа.

Работа с документами в интерфейсе связана с договорным обменом. В договорном обмене загрузка файла не является самостоятельным смысловым действием. Пользователь или сотрудник отправляет версию договорного предложения, а документ является частью этой версии. Поэтому интерфейс должен показывать не только имя файла, но и номер версии, автора, комментарий и состояние предложения. Физическое хранение файла остаётся внутренним механизмом приложения.

Для наглядного представления пользовательского интерфейса можно использовать схемы экранов клиента и сотрудника. Клиентская схема должна показывать переходы от личного кабинета к заявителям, заявкам и договорным обменам. Сотрудническая схема должна показывать переход от рабочего списка заявок к деталям заявки, рассмотрению, решению и договорному обмену. Дополнительно можно использовать общую схему взаимодействия пользовательского интерфейса и API.

Таким образом, проектирование программного взаимодействия и пользовательского интерфейса завершает переход от сценариев и требований к структуре приложения. API определяет, какие операции доступны системе, а пользовательский интерфейс показывает, как клиент и сотрудник выполняют эти операции в рамках своих ролей и текущего состояния процесса.
