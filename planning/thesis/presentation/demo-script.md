# Demo Script

Status: draft

## Цель демонстрации

Показать базовый реализованный поток web-приложения:

```text
регистрация клиента
-> вход
-> создание заявителя-физического лица
-> подача заявки
-> проверка сохранения данных
```

Если к моменту защиты будет реализован сценарий сотрудника, демонстрацию можно расширить до обработки заявки и создания проекта договора.

## Вариант 1. Демонстрация через Swagger/API

### Шаг 1. Запуск backend

Показать запущенное ASP.NET Core приложение и Swagger.

Что сказать:

> Backend предоставляет API для клиентских сценариев и взаимодействует с базой данных.

### Шаг 2. Регистрация клиента

Выполнить запрос регистрации клиента.

Показать:

- email;
- пароль;
- успешный ответ;
- созданный идентификатор аккаунта, если он возвращается API.

Что сказать:

> На этом шаге создается клиентский аккаунт. Пароль сохраняется не в открытом виде, а в виде хеша.

### Шаг 3. Вход клиента

Выполнить запрос входа.

Что сказать:

> После входа клиент получает доступ к операциям, требующим авторизации.

### Шаг 4. Создание заявителя

Выполнить создание заявителя-физического лица.

Показать:

- ФИО;
- email;
- телефон;
- связь с аккаунтом клиента.

Что сказать:

> Заявитель связан с текущим клиентским аккаунтом и затем используется при подаче заявки.

### Шаг 5. Подача заявки

Выполнить создание заявки.

Показать:

- выбранного заявителя;
- описание заявки;
- адрес объекта;
- статус заявки.

Что сказать:

> Система проверяет, что заявитель принадлежит текущему клиенту, и только после этого создает заявку.

### Шаг 6. Проверка данных

Показать запись в БД или ответ теста.

Что сказать:

> Данные сохраняются в связанных таблицах: аккаунты, заявители и заявки.

## Вариант 2. Расширенная демонстрация через UI

## Вариант 3. Полная демонстрация, если готов сотруднический сценарий

Показать:

1. Вход сотрудника.
2. Список заявок.
3. Открытие заявки.
4. Взятие заявки в обработку.
5. Одобрение или отклонение.
6. Создание проекта договора.
7. Email-уведомление клиенту.

## Что не утверждать без подтверждения

Не говорить, что рабочее место сотрудника, создание договора или email-уведомления полностью реализованы, если на момент защиты они не подтверждены кодом и демонстрацией.
