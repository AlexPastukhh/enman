## 2. Что это за тема

Эта тема раскрывает **жизненный цикл клиентской заявки**: какие смысловые этапы проходит заявка от создания клиентом до решения сотрудника и возможного перехода к договорному обмену.

Предыдущая тема 2.2.1 отвечала на вопрос:

```text
какие основные предметные понятия есть в системе
```

Текущая тема отвечает на вопрос:

```text
как меняется состояние центрального объекта — клиентской заявки
```

Главная мысль:

> Клиентская заявка является центральным объектом процесса. Её жизненный цикл начинается с создания заявки клиентом, продолжается рассмотрением сотрудником и завершается решением: одобрением или отклонением. При отклонении клиент получает результат и причину при наличии, а при одобрении заявка становится основанием для договорного обмена.

## 3. Важное уточнение: не путать смысловые этапы и enum/status из кода

В этом драфте сначала описываются **смысловые этапы заявки** для текста ВКР.

Точные технические статусы, enum-значения, названия полей и API-переходы нужно сверить по repo.

### Как писать в финальном тексте

Основной язык:

```text
заявка создана клиентом;
заявка поступила на рассмотрение;
заявка рассматривается сотрудником;
по заявке принято решение;
заявка одобрена;
заявка отклонена;
после одобрения доступен договорный этап.
```

### Как не писать без проверки

```text
Submitted;
Approved;
Rejected;
InReview;
StartReview как сущность;
RequestReview как отдельный корневой процесс;
автоматический запуск договора;
обязательная причина отказа;
изменяемое решение;
полный workflow согласования.
```

Repo/code terms можно использовать только как слой сверки:

```text
ConnectionRequest — возможный repo-term для клиентской заявки;
RequestReview — возможный repo-term для рассмотрения заявки;
StartReview — возможный сценарий/команда начала рассмотрения;
Decision / Review result — возможное техническое представление решения.
```

## 4. Принятые уточнения

1. Глава 2 является проектной главой, поэтому здесь описывается проектируемый жизненный цикл, а не код.
2. Основной язык драфта — русский предметный язык.
3. Английские repo-термины использовать только для сверки.
4. Заявка — центральный объект процесса.
5. Жизненный цикл заявки должен вытекать из сценариев 2.1.
6. Клиент создаёт заявку.
7. Заявка связана с заявителем.
8. Сотрудник рассматривает заявку.
9. Сотрудник может выполнить проверку данных заявки в рамках предусмотренного сценария.
10. Проверку данных не описывать как реальную внешнюю интеграцию, если она mock/демонстрационная.
11. Сотрудник принимает решение: одобрить или отклонить.
12. Причина отказа может быть указана, но не должна описываться как всегда обязательная без repo-check.
13. При одобрении заявка становится основанием для договорного обмена.
14. Договорный обмен не запускается “сам по себе” полностью автоматически.
15. Сотрудник может начать договорный этап после одобрения.
16. Договор не генерируется системой автоматически.
17. Точные статусы заявки нужно проверить по repo.
18. Не использовать старый `Submitted` без проверки.
19. Не использовать `Worker`, использовать “сотрудник” / возможный repo-term `Employee`.
20. Не заявлять ЭДО, ЭП, полноценную СЭД, автоматическую генерацию договора.

## 6. Содержание темы

### 6.1 Заявка как объект с жизненным циклом

Клиентская заявка проходит несколько этапов: от создания до решения.

Рабочая формулировка:

> В проектируемой системе заявка рассматривается как объект с жизненным циклом. Это позволяет отразить не только факт подачи обращения, но и его дальнейшую обработку сотрудником, результат рассмотрения и переход к договорному этапу при одобрении.

---

### 6.2 Создание заявки клиентом

Жизненный цикл начинается с действия клиента.

Клиент:

```text
входит в личный кабинет;
создаёт или выбирает заявителя;
заполняет данные заявки;
отправляет заявку в систему.
```

Смысл этапа:

```text
заявка получает связь с клиентом;
заявка получает связь с заявителем;
заявка становится доступной для дальнейшего рассмотрения;
клиент может видеть заявку в личном кабинете.
```

Осторожная формулировка:

> На первом этапе клиент создаёт заявку через личный кабинет. Заявка связывается с заявителем и становится доступной для дальнейшей обработки в системе.

Что не утверждать без проверки:

```text
точное название начального статуса;
есть ли черновик заявки;
можно ли редактировать заявку после отправки;
какие поля обязательны;
есть ли вложения на этапе подачи заявки.
```

---

### 6.3 Поступление заявки на рассмотрение

После создания заявка должна стать доступной сотруднику в рабочем сценарии.

Смысл этапа:

```text
сотрудник получает возможность увидеть заявку;
система отделяет созданную заявку от заявки, находящейся в обработке;
заявка ожидает рассмотрения или начала рассмотрения.
```

Рабочая формулировка:

> После создания заявка поступает в область обработки сотрудника. На этом этапе она ещё не содержит итогового решения, но уже может быть открыта сотрудником для проверки и рассмотрения.

Осторожность:

```text
не писать “сотрудник видит все заявки” без проверки;
лучше писать “сотрудник получает доступ к заявкам в рамках рабочего сценария”;
точный механизм назначения сотрудника проверить по repo.
```

---

### 6.4 Начало рассмотрения заявки

Рассмотрение — этап, на котором сотрудник начинает работать с заявкой.

Возможный repo-term:

```text
RequestReview
```

Возможный сценарий/команда:

```text
StartReview
```

Смысл этапа:

```text
сотрудник открывает заявку;
проверяет данные;
при необходимости использует предусмотренную проверку;
подготавливает решение;
система фиксирует, что заявка находится в обработке, если это подтверждено моделью.
```

Рабочая формулировка:

> Рассмотрение заявки отражает этап обработки обращения сотрудником. В рамках этого этапа сотрудник анализирует данные заявки и подготавливает решение об одобрении или отклонении.

Осторожность:

```text
не утверждать, что StartReview — отдельная сущность;
не утверждать, что review всегда создаётся отдельной записью;
не утверждать, что заявка имеет много рассмотрений;
не утверждать точные переходы без repo-check.
```

---

### 6.5 Проверка данных заявки

Проверка данных нужна, чтобы показать элемент автоматизации в сценарии сотрудника.

Смысл этапа:

```text
сотрудник может проверить данные заявки;
система может показать результат проверки;
проверка помогает принять решение;
точный характер проверки должен быть согласован с реализацией.
```

Безопасная формулировка:

> В рамках рассмотрения может быть предусмотрена проверка данных заявки. В текущем scope она рассматривается как демонстрационная точка расширения: система показывает место, где в будущем может быть подключена внешняя проверка, но не заявляет реальную интеграцию с внешними реестрами.

Что не писать:

```text
реализована внешняя верификация;
система автоматически подтверждает данные;
решение принимается без сотрудника;
проверка заменяет рассмотрение.
```

---

### 6.6 Принятие решения по заявке

Решение завершает рассмотрение.

Смысловые варианты:

```text
одобрение;
отклонение.
```

Решение должно быть связано:

```text
с заявкой;
с рассмотрением;
с сотрудником или рабочим сценарием сотрудника;
с причиной отказа при наличии;
с дальнейшим маршрутом заявки.
```

Рабочая формулировка:

> Итогом рассмотрения является решение по заявке. В проектной модели решение определяет дальнейший маршрут: при отклонении клиент получает результат рассмотрения, а при одобрении становится возможен переход к договорному обмену.

---

### 6.7 Отклонение заявки

При отклонении процесс заявки завершается на этапе рассмотрения.

Клиент должен видеть:

```text
статус или результат отказа;
причину отказа, если она указана;
отсутствие доступного договорного этапа.
```

Сотрудник:

```text
фиксирует отказ;
может указать причину отказа;
не запускает договорный обмен.
```

Осторожная формулировка:

> При отклонении заявка получает результат отказа. Причина отказа может быть указана сотрудником и отображена клиенту, если она сохранена в системе.

Что не утверждать:

```text
причина всегда обязательна;
клиент обязательно получает email;
можно повторно подать эту же заявку;
отказ можно отменить;
отказ имеет юридическое значение.
```

---

### 6.8 Одобрение заявки

При одобрении заявка не просто завершается, а становится основанием для следующего этапа.

Смысл этапа:

```text
заявка получает положительный результат;
клиент видит одобрение;
сотрудник может начать договорный этап;
договорный обмен связывается с одобренной заявкой.
```

Рабочая формулировка:

> При одобрении заявка становится основанием для договорного этапа. Это не означает автоматическую генерацию договора: сотрудник может начать договорный обмен и прикрепить подготовленную версию договорного предложения.

Что не утверждать:

```text
договор создаётся автоматически;
договорный обмен запускается без действия сотрудника;
система сама формирует договор;
происходит юридическое заключение договора.
```

---

### 6.9 Переход к договорному обмену

Переход к договорному обмену — связь между жизненным циклом заявки и следующей темой 2.2.3.

Смысл:

```text
договорный обмен возникает после положительного решения;
обмен связан с заявкой;
обмен содержит версии договорного предложения;
подробный lifecycle обмена раскрывается отдельно.
```

Рабочая формулировка:

> Жизненный цикл заявки завершается решением, однако при положительном результате заявка становится основанием для договорного обмена. Сам договорный обмен имеет собственный жизненный цикл и рассматривается в следующем пункте.

## 7. Смысловой жизненный цикл заявки

Смысловая схема без привязки к техническим enum-статусам:

```text
Клиент создаёт заявку
        ↓
Заявка поступает на рассмотрение
        ↓
Сотрудник начинает / выполняет рассмотрение
        ↓
Сотрудник проверяет данные заявки
        ↓
Сотрудник принимает решение
        ├─ отказ
        │    ↓
        │  клиент видит результат отказа
        │
        └─ одобрение
             ↓
           клиент видит положительный результат
             ↓
           сотрудник может начать договорный обмен
```

Важно:

```text
это смысловая схема;
точные статусы и названия переходов требуют repo-check;
в финальном тексте можно не перечислять enum-значения;
для диаграммы лучше использовать русские названия этапов.
```

## 8. Переходы между состояниями

| Этап                        | Кто инициирует            | Что происходит                                       | Следующий этап                    |
| --------------------------- | ------------------------- | ---------------------------------------------------- | --------------------------------- |
| Создание заявки             | клиент                    | заявка создаётся и связывается с заявителем          | поступление на рассмотрение       |
| Поступление на рассмотрение | система / сценарий подачи | заявка доступна сотруднику                           | начало рассмотрения               |
| Начало рассмотрения         | сотрудник                 | сотрудник открывает заявку и начинает обработку      | проверка данных / решение         |
| Проверка данных             | сотрудник                 | выполняется проверка данных заявки в рамках сценария | решение                           |
| Одобрение                   | сотрудник                 | фиксируется положительное решение                    | договорный обмен может быть начат |
| Отклонение                  | сотрудник                 | фиксируется отрицательное решение                    | клиент видит результат отказа     |
| Переход к договорному этапу | сотрудник после одобрения | начинается договорный обмен                          | lifecycle договорного обмена      |

Подпись:

```text

```

## 9. Связь жизненного цикла с ролями

| Этап жизненного цикла        | Клиент                                             | Сотрудник                                               |
| ---------------------------- | -------------------------------------------------- | ------------------------------------------------------- |
| Создание заявки              | создаёт заявку                                     | не участвует                                            |
| Поступление на рассмотрение  | видит созданную заявку                             | получает доступ к заявке в рабочем сценарии             |
| Рассмотрение                 | ожидает результата                                 | открывает и анализирует заявку                          |
| Проверка данных              | не выполняет                                       | выполняет проверку в интерфейсе рассмотрения            |
| Одобрение                    | видит положительный результат                      | принимает решение                                       |
| Отклонение                   | видит отказ и причину при наличии                  | принимает решение и указывает причину при необходимости |
| Переход к договорному обмену | получает доступ к договорному этапу, если он начат | начинает договорный этап после одобрения                |

Подпись:

```text
Таблица 2.x — Участие клиента и сотрудника в жизненном цикле заявки
```

## 10. Границы модели жизненного цикла

### Входит в текущий scope

```text
создание заявки клиентом;
связь заявки с заявителем;
поступление заявки на рассмотрение;
рассмотрение сотрудником;
проверка данных заявки в рамках сценария;
одобрение заявки;
отклонение заявки;
причина отказа при наличии;
отображение результата клиенту;
переход к договорному обмену после одобрения.
```

### Не входит в текущий scope

```text
многоэтапное согласование заявки;
автоматическое принятие решения без сотрудника;
реальная внешняя верификация данных;
автоматическая генерация договора;
юридически значимый отказ или одобрение;
email/push-уведомления как подтверждённая функция;
полный аудит изменения статусов;
повторное рассмотрение и апелляция;
назначение заявок между сотрудниками, если не подтверждено repo.
```

## 11. Что требует обоснования

### 11.1 Почему заявка должна иметь жизненный цикл

Без жизненного цикла заявка превращается в статичную запись.

Будущая формулировка:

> Жизненный цикл заявки позволяет описать последовательность обработки обращения: от создания клиентом до решения сотрудника и возможного перехода к договорному этапу.

---

### 11.2 Почему рассмотрение отделяется от создания заявки

Создание и рассмотрение выполняют разные участники.

Будущая формулировка:

> Создание заявки выполняется клиентом, а её рассмотрение — сотрудником. Поэтому в проектной модели эти этапы разделяются.

---

### 11.3 Почему решение является точкой ветвления

После решения процесс идёт по разным маршрутам.

Будущая формулировка:

> Решение сотрудника является точкой ветвления жизненного цикла заявки: отказ завершает процесс рассмотрения, а одобрение создаёт основание для договорного обмена.

---

### 11.4 Почему договорный обмен не запускается автоматически полностью

В проекте договорный этап инициируется сотрудником.

Будущая формулировка:

> Одобрение заявки не означает автоматическое создание договора. Оно только создаёт основание для договорного этапа, который сотрудник может начать в рамках своего рабочего сценария.

---

### 11.5 Почему проверка данных описывается осторожно

Проверка данных может быть демонстрационной точкой расширения.

Будущая формулировка:

> Проверка данных заявки рассматривается как часть сценария рассмотрения. В текущем scope она не заявляется как полноценная внешняя интеграция, а показывает место, где такая интеграция может быть добавлена в дальнейшем.

## 14. Черновые фрагменты будущего текста

### Фрагмент 1 — ввод

После описания предметной модели необходимо рассмотреть жизненный цикл клиентской заявки. Это позволяет показать, как заявка проходит путь от создания клиентом до решения сотрудника.

### Фрагмент 2 — создание заявки

Жизненный цикл заявки начинается с её создания клиентом через личный кабинет. При создании заявка связывается с заявителем и становится доступной для дальнейшей обработки в системе.

### Фрагмент 3 — рассмотрение

После создания заявка поступает на рассмотрение сотруднику. В рамках рассмотрения сотрудник анализирует данные заявки и при необходимости выполняет предусмотренную проверку данных.

### Фрагмент 4 — решение

Итогом рассмотрения является решение по заявке. Решение определяет дальнейший маршрут: при отклонении клиент видит результат отказа, а при одобрении заявка становится основанием для договорного этапа.

### Фрагмент 5 — отказ

При отклонении заявки сотрудник может указать причину отказа. Если причина сохранена в системе, она отображается клиенту вместе с результатом рассмотрения.

### Фрагмент 6 — одобрение

При одобрении заявка не приводит к автоматическому созданию договора, но создаёт основание для договорного обмена. Сотрудник может начать договорный этап и отправить клиенту подготовленную версию договорного предложения.

### Фрагмент 7 — переход

Таким образом, жизненный цикл заявки завершается решением, но при положительном результате связан со следующим процессом — договорным обменом, который имеет собственный жизненный цикл.
