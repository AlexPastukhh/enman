# Тема: UI-flow подачи и рассмотрения заявки

**Статус:** быстрый topic-драфт v1 / блок 2.6.2 / нужен repo-check по create request page, request details page, employee review UI, approve/reject buttons, check data button, validation/business errors.

---

## 1. Зачем тема нужна

Эта тема объясняет, как пользовательский интерфейс поддерживает основной процесс заявки: от создания заявки клиентом до рассмотрения сотрудником и принятия решения.

Главная мысль:

> UI-flow заявки должен соответствовать жизненному циклу процесса: клиент создаёт заявку и отслеживает её состояние, сотрудник открывает заявку, начинает рассмотрение, выполняет проверку данных и принимает решение. Frontend показывает формы, статусы, кнопки и ошибки, но не управляет бизнес-переходами напрямую.

---

## 2. Клиентский flow подачи заявки

Основной путь клиента:

```text
личный кабинет
→ выбор / создание заявителя
→ форма создания заявки
→ отправка заявки
→ список моих заявок
→ карточка заявки
→ отслеживание статуса
```

Frontend отвечает за:

```text
форму заявки;
валидацию обязательных полей на уровне UI;
отправку create request command;
показ loading/success/error;
переход к карточке или списку заявок.
```

Backend отвечает за:

```text
проверку пользователя;
проверку связи клиента и заявителя;
request validation;
создание заявки;
начальный статус заявки;
возврат result DTO или ошибки.
```

Тезис:

> Клиентский UI помогает пользователю подать заявку, но итоговое создание заявки выполняется backend-ом через command API.

---

## 3. Форма создания заявки

Форма может включать:

```text
выбор заявителя;
данные объекта;
контактные данные, если есть;
описание заявки;
прикрепления, если подтверждено моделью;
кнопку отправки.
```

UI states:

```text
empty form;
field validation error;
submitting;
success;
server validation error;
unexpected error.
```

Важно:

```text
frontend validation — подсказка;
backend validation — обязательная проверка;
frontend не задаёт status заявки;
status появляется как результат create command.
```

Тезис:

> Форма создания заявки должна собирать данные пользователя, но не определять служебное состояние заявки. Статус и связи заявки устанавливаются на backend.

---

## 4. Карточка заявки для клиента

Клиентская карточка заявки отвечает на вопрос:

```text
что сейчас происходит с моей заявкой?
```

Показывает:

```text
данные заявки;
статус;
дату создания;
состояние рассмотрения;
решение;
причину отказа, если есть;
переход к договорному обмену, если заявка одобрена;
доступные действия клиента.
```

Не показывает:

```text
служебные действия сотрудника;
кнопки approve/reject;
внутренние review поля;
storage path файлов;
чужие данные.
```

Тезис:

> Для клиента карточка заявки является экраном отслеживания состояния процесса, а не экраном управления рассмотрением.

---

## 5. Сотруднический flow рассмотрения

Основной путь сотрудника:

```text
рабочая зона сотрудника
→ список заявок
→ карточка заявки
→ начать рассмотрение
→ проверить данные
→ одобрить или отклонить
→ после одобрения перейти к договорному обмену
```

Frontend отвечает за:

```text
список заявок;
открытие карточки;
показ availableActions;
кнопки start review / check / approve / reject;
форму причины отказа;
показ результата команды;
обновление read DTO после действия.
```

Backend отвечает за:

```text
проверку роли сотрудника;
проверку актуального состояния заявки;
business rules;
изменение состояния;
возврат command result или business-state error.
```

Тезис:

> Сотруднический UI запускает действия обработки заявки, но каждое действие подтверждается backend-ом через command API.

---

## 6. Карточка заявки для сотрудника

Сотрудническая карточка заявки показывает:

```text
данные заявки;
данные заявителя;
статус заявки;
состояние review;
результат mock-проверки, если есть;
доступные действия;
блок решения;
причину отказа;
переход к договорному обмену после одобрения.
```

Ключевые кнопки:

```text
Начать рассмотрение;
Проверить данные;
Одобрить;
Отклонить;
Начать договорный обмен.
```

Тезис:

> Для сотрудника карточка заявки является рабочим экраном обработки, где отображаются данные заявки и доступные действия текущего этапа.

---

## 7. Проверка данных в UI

Mock-проверка данных — вспомогательное действие.

Flow:

```text
сотрудник нажимает “Проверить данные”
→ frontend вызывает command-like API
→ backend выполняет проверку
→ frontend показывает результат
→ сотрудник отдельно принимает решение
```

Важно:

```text
проверка не одобряет заявку автоматически;
проверка не отклоняет заявку автоматически;
результат проверки помогает сотруднику;
решение approve/reject — отдельная command.
```

Тезис:

> Проверка данных должна отображаться как вспомогательный результат, а не как автоматическое решение по заявке.

---

## 8. Одобрение заявки

Flow:

```text
сотрудник нажимает “Одобрить”
→ frontend отправляет approve command
→ backend проверяет роль, доступ и состояние
→ domain проверяет допустимость перехода
→ заявка получает статус одобрения
→ frontend обновляет карточку
→ появляется возможность договорного обмена
```

UI после успеха:

```text
показать новый статус;
скрыть approve/reject;
показать start exchange, если доступно;
обновить availableActions.
```

Тезис:

> Одобрение заявки в UI является запуском команды. Frontend не устанавливает статус Approved самостоятельно.

---

## 9. Отклонение заявки

Flow:

```text
сотрудник нажимает “Отклонить”
→ UI показывает поле причины отказа
→ frontend отправляет reject command
→ backend проверяет данные и состояние
→ заявка получает статус отклонения
→ клиент видит итог и причину отказа
```

UI states:

```text
reason required;
submitting;
validation error;
business-state error;
success.
```

Тезис:

> Отклонение заявки должно фиксировать результат рассмотрения и, при наличии требования, причину отказа, которая затем отображается клиенту.

---

## 10. AvailableActions и stale UI

UI может показать кнопку на основе старого read DTO.

Пример:

```text
frontend получил canApprove = true;
другой сотрудник уже отклонил заявку;
первый сотрудник нажал approve;
backend возвращает ActionNoLongerAvailable;
frontend обновляет карточку.
```

Тезис:

> UI должен быть готов к тому, что доступное действие устарело. В этом случае frontend показывает понятную ошибку и запрашивает актуальные данные.

## 13. Черновой текст

UI-flow заявки строится вокруг двух точек зрения. Клиент использует интерфейс для создания заявки и отслеживания её состояния. Сотрудник использует интерфейс для обработки заявки, запуска проверки данных и принятия решения.

Создание заявки выполняется через форму клиентской зоны. Frontend собирает данные, показывает ошибки заполнения и отправляет команду на backend. При этом frontend не задаёт статус заявки: начальное состояние создаётся серверной частью после проверки пользователя, заявителя и входных данных.

После подачи заявки центральным экраном становится карточка заявки. Для клиента она показывает статус, результат рассмотрения и дальнейшие действия. Для сотрудника карточка заявки является рабочим экраном, где доступны действия начала рассмотрения, проверки данных, одобрения и отклонения.

Доступные действия могут приходить из read DTO, но они не являются гарантией выполнения команды. Если состояние заявки изменилось после загрузки карточки, backend возвращает business-state error, а frontend обновляет данные экрана.
