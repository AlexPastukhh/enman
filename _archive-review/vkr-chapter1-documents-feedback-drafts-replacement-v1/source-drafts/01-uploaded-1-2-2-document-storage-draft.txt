1. Что это за тема

Эта тема уточняет, как в ВКР говорить о договорном документе, версии договора и файловом хранении.

В теме 1.2.1 уже зафиксирована основная процессная цепочка:

заявка
→ рассмотрение сотрудником
→ решение
→ при одобрении сотрудник начинает договорный этап
→ сотрудник и клиент обмениваются версиями договора
→ одна из версий согласуется для дальнейшего подписания

Текущая тема отвечает на вопросы:

что представляет собой версия договора;
как версия договора связана с заявкой и решением;
кто может быть отправителем версии;
где хранятся метаданные документа;
где хранится сам файл;
почему это не полноценная СЭД и не промышленное файловое хранилище.

Главная мысль:

В рамках ВКР договорный документ рассматривается как версия договора, отправленная одной из сторон в ходе договорного обмена. Метаданные версии используются для связи документа с заявкой, решением, отправителем и процессом согласования, а сам файл хранится отдельно. В текущей реализации файловое хранение выполнено простым способом и не должно описываться как полноценная СЭД, юридически значимый ЭДО или промышленное файловое хранилище.

2. Принятые уточнения

Метаданные документа хранятся в SQL Server.

Сам файл хранится в файловом хранилище.

В текущей реализации файловое хранилище простое: файл размещается в директории.

Версия договора имеет отправителя.

Отправителем версии может быть клиент или сотрудник организации.

Со стороны организации договорный обмен могут обслуживать разные сотрудники.

Клиент в конкретном договорном обмене один.

Точный состав метаданных нельзя придумывать вручную: его нужно сверять по data-файлам слоя сценариев.

В главе 1 технические детали SQL Server и директории не должны становиться главным фокусом.

В главах 2–3 можно подробнее раскрыть реализацию хранения файла и метаданных.

3. Зачем эта тема нужна

На уровне темы

Тема нужна, чтобы избежать двух ошибок.

Первая ошибка — описать договорный документ слишком слабо:

у нас просто прикрепляется файл

Это плохо, потому что файл не существует сам по себе. Он является версией договора внутри процесса согласования.

Вторая ошибка — описать реализацию слишком сильно:

реализована полноценная СЭД;
реализовано промышленное файловое хранилище;
реализован юридически значимый электронный документооборот;
реализована электронная подпись.

Это тоже неверно, потому что текущая реализация проще и уже по scope.

Правильный центр темы:

система поддерживает договорный обмен версиями договора;
версия договора имеет отправителя;
метаданные версии хранятся в SQL Server;
сам файл хранится в файловом хранилище;
файловое хранилище реализовано простым способом — через директорию;
клиент и сотрудники видят версии договора в рамках обмена;
расширенное файловое хранение, ЭП, внешний ЭДО и сложный аудит относятся к дальнейшему развитию.

На уровне пункта 1.2

Пункт 1.2 должен показать договорно-документный этап и обратную связь. Эта тема уточняет, что договорная часть работы — это не отдельный архив файлов, а договорный обмен внутри процесса обработки заявки.

На уровне главы 1

Тема готовит пункт 1.3, где будут описываться проблемы ручного ведения:

если заявка, решение, версии договора, файлы и обратная связь ведутся раздельно,
теряется связность процесса.

Также тема готовит пункт 1.4:

готовые СЭД и ECM-системы умеют значительно больше,
но для ВКР нужен узкий договорный контур,
связанный с заявкой и договорным обменом.

На уровне всей ВКР

Тема готовит материал для следующих глав:

4. Содержание темы

4.1 Версия договора как единица договорного обмена

В основном тексте лучше использовать термин:

версия договора

А не постоянно писать:

документная версия

“Документная версия” можно использовать как вспомогательный термин, но для текста ПЗ естественнее звучит “версия договора”.

Рабочая формулировка:

В договорном этапе документ рассматривается как версия договора, отправленная одной из сторон. Версия договора связана с конкретной одобренной заявкой и участвует в процессе согласования.

Почему именно версия:

договорный этап может включать несколько вариантов;
версию может отправить сотрудник;
версию может отправить клиент;
участники могут уточнять условия;
одна из версий должна быть согласована для дальнейшего подписания.

4.2 Отправитель версии договора

У версии договора есть отправитель.

Отправителем может быть:

клиент;
сотрудник организации.

При этом клиент в договорном обмене один, а со стороны организации процесс могут обслуживать разные сотрудники.

Корректная формулировка:

Версия договора имеет отправителя: клиент или сотрудник организации. Со стороны организации договорный обмен могут обслуживать разные сотрудники, однако каждая конкретная версия сохраняет информацию о том, кем она была отправлена.

Это важно для прослеживаемости:

кто отправил версию;
какая сторона предложила вариант;
какие версии были переданы в процессе согласования;
какая версия стала основой для дальнейшего подписания.

4.3 Готовый файл, а не автоматическая генерация договора

Система не должна описываться как генератор договора.

Корректно:

сотрудник или клиент прикрепляет уже подготовленный файл;
система связывает файл с версией договора;
метаданные версии хранятся в SQL Server;
сам файл хранится в файловом хранилище;
система показывает версии участникам обмена;
система сохраняет связь версии с заявкой, отправителем и этапом согласования.

Некорректно:

система автоматически формирует договор;
договор создаётся по шаблону;
договор генерируется сразу после одобрения заявки;
договор создаётся без участия сотрудника.

4.4 Разделение метаданных и файла

Уточнённая модель:

SQL Server
→ хранит метаданные версии договора и сведения о файле;

файловое хранилище
→ хранит сам файл;

текущая реализация файлового хранения
→ простая директория, достаточная для дипломного проекта.

Формулировка для topic-драфта:

В текущей реализации сведения о версии договора и прикреплённом документе хранятся в базе данных SQL Server, а сам файл размещается в файловом хранилище. Файловое хранение реализовано простым способом — через размещение файла в директории. Такой подход позволяет показать связь версии договора с процессом согласования, не заявляя реализацию промышленного файлового хранилища.

Формулировка для будущего текста главы 1 должна быть мягче:

В системе сведения о версии договора отделяются от самого файла: метаданные используются для связи документа с заявкой, отправителем и договорным обменом, а сам файл хранится отдельно. Подробности реализации файлового хранения рассматриваются в проектной и реализационной частях работы.

Формулировка для главы 3 может быть конкретнее:

Метаданные версии договора хранятся в SQL Server, а файл размещается в файловом хранилище, реализованном простым способом через директорию.

4.5 Метаданные документа

Точный состав метаданных нужно брать из data-файлов слоя сценариев.

В драфте нельзя утверждать полный список полей без проверки.

Допустимая формулировка до repo-check:

метаданные могут включать сведения о файле, отправителе, связи с версией договора и связи с договорным обменом;
точный состав метаданных уточняется по data-файлам слоя сценариев.

Для визуала можно показывать смысловые группы, а не точные поля:

сведения о файле;
отправитель;
связь с договорным обменом;
связь с заявкой;
расположение файла.

Не нужно без проверки писать как факт:

точно есть поле X;
точно есть поле Y;
точно есть статус версии;
точно есть комментарий к версии.

4.6 Граница файлового хранения

Входит в текущий scope:

договорный обмен;
версии договора;
связь версии с заявкой;
отправитель версии;
метаданные версии в SQL Server;
файл в простом файловом хранилище;
просмотр версий клиентом и сотрудниками;
сведения о прикреплённом документе.

Не заявляем как реализованное:

полноценная СЭД;
юридически значимый электронный документооборот;
электронная подпись;
интеграция с внешней СЭД/ЭДО;
сложная политика хранения файлов;
полный аудит файловых операций;
отдельный промышленный storage service;
сложная безопасная выдача файлов.

5. Что требует обоснования

5.1 Почему версия договора должна быть связана с заявкой

Договорный обмен возникает после одобрения конкретной заявки.

нет одобренной заявки
→ нет основания для договорного обмена;

есть одобренная заявка
→ сотрудник может начать обмен версиями договора.

Будущая формулировка:

Версия договора должна сохранять связь с заявкой, потому что договорный обмен появляется не сам по себе, а как продолжение положительного решения по конкретному обращению клиента.

5.2 Почему нужен обмен версиями, а не один документ

Договор может требовать согласования.

сотрудник отправляет версию договора;
клиент просматривает её;
если всё устраивает — соглашается;
если нужны уточнения — задаёт вопрос или отправляет свою версию;
участники приходят к согласованному варианту.

Будущая формулировка:

Использование версий договора позволяет описать не только факт наличия файла, но и сам процесс согласования. Участники могут обмениваться вариантами документа, уточнять условия и приходить к согласованной версии.

5.3 Почему важно хранить метаданные отдельно от файла

Метаданные позволяют системе работать с документом как с частью процесса:

показать список версий;
показать отправителя;
связать версию с договорным обменом;
связать договорный обмен с заявкой;
отобразить документ клиенту и сотруднику;
поддерживать историю согласования.

Файл при этом является содержимым документа, а метаданные связывают это содержимое с предметным процессом.

Будущая формулировка:

Разделение файла и метаданных позволяет системе не просто хранить документ, а связывать его с договорным обменом: фиксировать отправителя, показывать список версий и сохранять связь с заявкой.

5.4 Почему простое файловое хранение допустимо для ВКР

Цель работы состоит не в разработке промышленного файлового хранилища, а в автоматизации связанного процесса заявки, решения и договорного обмена.

Корректная мысль:

Для целей ВКР простое файловое хранение достаточно, поскольку оно позволяет продемонстрировать сценарий обмена версиями договора. Расширенное хранение файлов, сложная политика доступа, аудит и интеграция с внешней СЭД могут быть выделены как направления дальнейшего развития.

5.5 Почему это не полноценная СЭД

Система поддерживает договорный обмен, но не реализует весь контур электронного документооборота.

Не заявляем:

электронную подпись;
юридически значимый обмен;
внешнюю СЭД;
маршруты уровня корпоративной ECM-системы;
политики хранения уровня промышленного архива.

Будущая формулировка:

В рамках ВКР реализуется ограниченный договорный контур, связанный с обработкой заявки. Поэтому систему корректнее описывать как web-приложение с поддержкой договорного обмена, а не как полноценную систему электронного документооборота.

7. Границы утверждений

Можно писать

система поддерживает договорный обмен версиями договора;
версия договора связана с одобренной заявкой;
версию договора отправляет клиент или сотрудник;
со стороны организации обмен могут обслуживать разные сотрудники;
у версии сохраняется отправитель;
метаданные документа хранятся в SQL Server;
сам файл хранится в файловом хранилище;
файловое хранилище реализовано простым способом — через директорию;
клиент и сотрудники видят версии, которыми обменивались;
цель обмена — согласовать версию договора;
полноценная СЭД относится к дальнейшему развитию;

Нельзя писать без проверки

система автоматически генерирует договор;
реализована полноценная СЭД;

10. Черновые фрагменты будущего текста

Фрагмент 1 — переход к версии договора

После одобрения заявки сотрудник может начать договорный этап, в рамках которого стороны обмениваются версиями договора. В текущем проекте версия договора рассматривается как уже подготовленный документ, который прикрепляется к обмену и становится доступен участникам процесса.

Фрагмент 2 — отправитель версии

Каждая версия договора имеет отправителя. Отправителем может быть клиент или сотрудник организации. При этом со стороны организации договорный обмен могут обслуживать разные сотрудники, поэтому фиксация отправителя важна для понимания истории согласования.

Фрагмент 3 — разделение файла и метаданных

Сведения о версии договора и прикреплённом документе хранятся отдельно от самого файла. Метаданные позволяют связать документ с заявкой, договорным обменом и отправителем, а файл представляет собой содержимое отправленной версии договора.

Фрагмент 4 — техническая реализация для главы 3

В реализации метаданные версии договора хранятся в SQL Server, а сам файл размещается в файловом хранилище. В рамках дипломного проекта файловое хранение реализовано простым способом — через хранение файлов в директории.

Фрагмент 5 — граница scope

В рамках ВКР договорный этап рассматривается как обмен версиями договора между клиентом и сотрудниками организации. Полноценное файловое хранилище, юридически значимый электронный документооборот, электронная подпись и интеграция с внешними СЭД относятся к возможным направлениям дальнейшего развития.

Фрагмент 6 — переход к обратной связи

Поскольку версия договора должна быть доступна участникам обмена, важной частью процесса становится обратная связь с клиентом. Клиент должен понимать результат рассмотрения заявки, видеть доступные версии договора и иметь возможность отреагировать на предложенный вариант.
