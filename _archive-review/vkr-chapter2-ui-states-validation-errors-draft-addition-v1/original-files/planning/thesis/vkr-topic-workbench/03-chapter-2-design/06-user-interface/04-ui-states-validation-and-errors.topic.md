# Тема: UI-состояния, валидация и обработка ошибок

**Статус:** быстрый topic-драфт v1 / блок 2.6.4 / завершает 2.6 / нужен repo-check по отображению loading, validation errors, business-state errors, forbidden/not found, file errors, disabled actions, form states.

---

## 1. Зачем тема нужна

Эта тема объясняет, как frontend должен показывать пользователю состояния интерфейса: загрузку, успешное выполнение действия, ошибки формы, ошибки доступа, устаревшие действия и проблемы с файлами.

Главная мысль:

> UI должен отображать не только успешные сценарии, но и промежуточные и ошибочные состояния. Frontend показывает loading, validation errors, business-state errors, forbidden/not found, file errors и empty states, но не принимает бизнес-решения самостоятельно.

---

## 2. Основные UI-состояния

```text
1. Loading
   Данные загружаются или команда выполняется.

2. Empty state
   Данных пока нет: нет заявок, нет версий, нет файлов.

3. Success
   Команда выполнена успешно.

4. Validation error
   Ошибка заполнения формы.

5. Business-state error
   Действие больше недоступно или невозможно в текущем состоянии.

6. Forbidden / not found
   Нет доступа или объект недоступен.

7. File error
   Файл не загружен, недоступен или download невозможен.

8. Unexpected error
   Общая ошибка сервера или сети.
```

Тезис:

> Интерфейс должен явно показывать состояние сценария, чтобы пользователь понимал, выполняется ли действие, завершилось ли оно успешно или требует исправления.

---

## 3. Loading states

Loading нужен для:

```text
загрузки списка заявок;
загрузки карточки заявки;
загрузки договорного обмена;
отправки формы;
одобрения / отклонения;
запуска проверки данных;
upload файла;
download файла.
```

Frontend может:

```text
показывать spinner;
disable кнопку;
показывать текст “Загрузка...”;
не давать повторно отправить форму;
оставлять страницу в понятном состоянии.
```

Тезис:

> Loading state нужен не только для удобства, но и для защиты от повторной отправки команд, например двойного клика по кнопке одобрения или загрузки файла.

---

## 4. Empty states

Пустые состояния нужны, когда данных ещё нет.

Примеры:

```text
у клиента нет заявителей;
у клиента нет заявок;
у сотрудника нет заявок в списке;
договорный обмен ещё не начат;
в exchange ещё нет версий;
у версии нет доступного файла, если такая ситуация возможна.
```

Тезис:

> Empty state должен объяснять пользователю, почему список пустой и какое следующее действие возможно.

---

## 5. Validation errors

Validation errors связаны с формой.

Примеры:

```text
не заполнено обязательное поле;
неверный формат;
слишком длинное значение;
не выбрана причина;
не выбран файл;
файл не соответствует ограничениям, если они есть.
```

UI должен:

```text
подсветить поле;
показать сообщение рядом с полем;
сохранить введённые данные;
не показывать validation error как системный сбой.
```

Тезис:

> Ошибки валидации должны отображаться рядом с соответствующими полями формы. Это позволяет пользователю исправить данные без потери контекста.

---

## 6. Business-state errors

Business-state error возникает, когда действие уже недоступно.

Примеры:

```text
заявка уже рассмотрена другим сотрудником;
review уже начат;
договорный обмен уже создан;
версия предложения уже неактуальна;
availableAction устарел;
файл больше недоступен в этом состоянии.
```

UI должен:

```text
показать понятное сообщение;
обновить карточку заявки или exchange;
скрыть устаревшие кнопки;
повторно запросить read DTO.
```

Тезис:

> Business-state error означает, что интерфейс работал со старым состоянием. Поэтому после такой ошибки frontend должен обновить данные экрана.

---

## 7. Forbidden / not found

Ошибки доступа показываются осторожно.

```text
401 — пользователь не вошёл;
403 — нет права выполнить действие;
404 — объект не найден или не должен быть раскрыт.
```

UI может:

```text
перенаправить на login;
показать “Нет доступа”;
показать “Объект не найден”;
вернуть пользователя к списку;
не раскрывать детали чужого объекта.
```

Тезис:

> UI не должен показывать пользователю лишнюю информацию о чужих заявках, договорных обменах или файлах.

---

## 8. File errors

Файловые ошибки:

```text
файл не выбран;
upload failed;
download failed;
file unavailable;
нет доступа к файлу;
physical file отсутствует;
metadata есть, но файл недоступен;
тип или размер файла не подходит, если ограничения есть.
```

UI должен показывать:

```text
безопасное сообщение;
повторить попытку, если уместно;
не показывать storage path;
не показывать storage key;
не показывать server directory.
```

Тезис:

> Файловые ошибки должны быть понятны пользователю, но не должны раскрывать внутреннюю структуру хранения файлов.

---

## 9. Disabled actions

Кнопки могут быть disabled или скрыты.

Примеры:

```text
Approve disabled, если заявка не на рассмотрении;
Reject disabled, если нет права;
Start exchange скрыта, пока заявка не approved;
Upload скрыт, если нельзя отправить версию;
Download disabled, если файл недоступен.
```

Важно:

```text
disabled кнопка — только UI-подсказка;
backend всё равно проверяет command;
прямой API-запрос должен быть отклонён, если действие недоступно.
```

Тезис:

> Скрытие или отключение кнопки улучшает UX, но не является механизмом безопасности. Проверка действия остаётся на backend.

---

## 10. Success states

После успешной команды UI должен показать результат.

Примеры:

```text
заявка создана;
рассмотрение начато;
проверка выполнена;
заявка одобрена;
заявка отклонена;
договорный обмен начат;
версия предложения отправлена;
файл загружен.
```

После success UI может:

```text
обновить карточку;
обновить список;
перейти к договорному обмену;
показать success message;
очистить форму;
обновить availableActions.
```

Тезис:

> Успешное выполнение команды должно приводить к синхронизации интерфейса с актуальным состоянием backend.

## 14. Черновой текст

Пользовательский интерфейс должен учитывать не только успешное выполнение сценариев, но и промежуточные и ошибочные состояния. При загрузке данных frontend показывает loading state, при отсутствии данных — empty state, а при выполнении команды — состояние отправки, чтобы пользователь не отправил действие повторно.

Ошибки валидации отображаются рядом с полями формы. Например, если пользователь не заполнил обязательное поле или не выбрал файл, frontend должен показать ошибку в контексте формы. При этом frontend validation является только подсказкой: окончательная проверка выполняется backend-ом.

Отдельно обрабатываются ошибки бизнес-состояния. Они возникают, когда действие было доступно на момент чтения данных, но стало недоступным к моменту выполнения команды. В этом случае frontend должен показать сообщение и обновить данные экрана.

Файловые ошибки должны отображаться безопасно. Пользователь может увидеть сообщение о недоступности файла, но интерфейс не должен показывать storage path, storage key или внутренние детали файлового хранилища.

