Спецификация пользовательских сценариев

Дата: 12.01.2026

1. Термины и обозначения

ФЛ — физическое лицо.
ИП — индивидуальный предприниматель.
ЮЛ — юридическое лицо.
Клиентская валидация — проверка формата/заполненности полей в интерфейсе до отправки данных на сервер.
Серверная валидация — проверка на стороне сервера (например, уникальность email, корректность учетных данных, проверка кода).
Базовая серверная валидация — минимальная проверка на стороне сервера, повторяющая ключевые клиентские правила (формат, обязательность полей) и дополняющая их проверками, требующими доступа к БД/политикам (уникальность, целостность). Нужна для консистентности данных: если клиентская валидация была обойдена/пропущена, сервер не позволит сохранить некорректные данные.

2. Инварианты (глобальные условия)

Инварианты должны выполняться на протяжении работы системы; нарушение любого инварианта считается ошибкой.

1. Приложение запущено и работает без необработанных исключений (нет экранов/окон с ошибками/stack trace).
2. Доступ к страницам соответствует статусу аутентификации и роли:
  Неаутентифицированный пользователь не имеет доступа к страницам личного кабинета, созданию запросов и админ-панели.
  Админ-интерфейс доступен только пользователю с ролью Admin.
3. Сообщения об ошибках/успехе отображаются в явном виде и не перекрывают элементы управления.
4. Если для формы предусмотрена клиентская валидация, то форма не отправляется при наличии ошибок валидации.
5. При успешном завершении действий пользователь получает проверяемый результат: переход на соответствующую страницу и/или подтверждающее сообщение.

Сценарий 1. Регистрация

Действующее лицо: Пользователь (неаутентифицированный).

Предусловие:

1. Приложение открыто.
2. Пользователь не вошел в систему.
3. В хедере доступна кнопка/ссылка «Регистрация».

Основной сценарий:

1. Пользователь нажимает «Регистрация» в хедере.
2. Открывается форма регистрации.
3. Пользователь выбирает тип регистрации: ФЛ / ИП / ЮЛ.
4. Пользователь вводит email корректного формата, который ранее не использовался для регистрации в приложении.
5. Пользователь вводит пароль корректного формата и достаточной длины.
6. Клиентская валидация не отображает ошибок.
7. Пользователь нажимает кнопку «Зарегистрироваться».
8. Серверная (базовая) валидация выполняется на сервере: повторная проверка форматов/обязательных полей и специальные проверки (например, уникальность email). При ошибках сервер возвращает соответствующие сообщения и регистрация не завершается.
9. При успешной серверной валидации пользователь перенаправляется на страницу, где отображается сообщение «Регистрация успешна» и ссылка для перехода на страницу входа.

Альтернативные сценарии:

1A. Email уже использовался:

1. Пользователь вводит email, который уже зарегистрирован, и нажимает «Зарегистрироваться».
2. Перенаправление не происходит.
3. Сервер возвращает ошибку уникальности email: отображается сообщение «Почта уже использовалась для регистрации».
4. Отображается ссылка «Уже есть аккаунт?» (переход на страницу входа).

1B. Некорректные данные (валидация):

1. Пользователь вводит email/пароль некорректного формата и/или не заполняет обязательные поля.
2. Отображаются ошибки клиентской валидации у соответствующих полей.
3. Регистрация не выполняется.

Постусловие:

При основном сценарии: учетная запись создана; пользователь видит страницу успешной регистрации и может перейти на страницу входа.
При альтернативных сценариях: учетная запись не создана; пользователь остается на форме регистрации и видит проверяемую причину отказа.

Примечание (серверная валидация): Важна дублирующая базовая проверка на сервере даже при полном наборе клиентских проверок — это защищает от некорректных записей при обрыве сети, вмешательстве клиентов или ошибках в клиентской логике.

Сценарий 2. Вход и восстановление пароля

2.1. Вход

Действующее лицо: Пользователь.

Предусловие:

1. Приложение открыто.
2. Пользователь находится на странице входа (или может перейти на нее).

Основной сценарий:

1. Пользователь вводит email корректного формата.
2. Пользователь вводит пароль корректного формата.
3. Клиентская валидация не отображает ошибок.
4. Пользователь нажимает кнопку «Войти».
8. После отправки данные принимаются сервером и выполняется базовая серверная валидация: повторная проверка форматов/обязательных полей и бизнес-проверки, требующие доступа к БД. При ошибках сервер возвращает сообщения, и пользователь остается на форме с ошибками.
9. Пользователь перенаправляется на страницу подтверждения телефона.

Альтернативные сценарии:

2A. Email не зарегистрирован:

1. Пользователь вводит корректный email, которого нет в системе, вводит пароль и нажимает «Войти».
2. Отображается сообщение: «Пользователь с такой почтой не зарегистрирован» (или эквивалент).
3. Пользователь остается на странице входа.

2B. Неверный пароль:

1. Пользователь вводит зарегистрированный email и неверный пароль, нажимает «Войти».
2. Отображается сообщение: «Неверный пароль» (или эквивалент).
3. Пользователь остается на странице входа.

2C. Некорректный формат данных (клиентская валидация):

1. Пользователь вводит email/пароль в некорректном формате.
2. Отображаются ошибки валидации.
3. Вход не выполняется.

Постусловие:

При основном сценарии: пользователь аутентифицирован; доступен функционал авторизованного пользователя.
При альтернативных сценариях: пользователь не аутентифицирован; отображается причина отказа.
